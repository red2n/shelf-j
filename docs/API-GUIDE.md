# Shelf-J — API Guide

> A business-capability tour of the entire API surface: what you can *do* with each part of it, not how it's implemented. Pair this with [README.md](../README.md) (the product tour these capabilities serve) and [docs/UI-GUIDE.md](UI-GUIDE.md) (the screens that call this API). For request/response schemas, data model, and event payload internals, read the actual code under `services/*/src/main/java/com/shelfj/*/api/` and `dto/` — this guide intentionally stays at the capability level so it doesn't drift out of sync with the code.

Every call goes through one public entry point and lands on one of 12 independent business capabilities behind it. Nothing else is reachable from outside the platform.

## Health, on every service

Four endpoints, and which one a caller wants depends on what it would do with the answer.

- `GET /health/live` — is this process wedged? One check, no dependency, ever. **This is what a Kubernetes liveness probe calls**, because the only remedy for a failing liveness probe is to kill the container, and killing a healthy process because its database is slow turns a database problem into a restart storm.
- `GET /health/ready` — can it serve right now? The database and the Kafka consumers. Failing it takes the replica out of the load balancer and nothing else. The database answer comes from a background prober, so the probe never queues behind real traffic for a connection, and a pool that is merely **busy** keeps the replica in rotation — pulling a saturated replica moves its traffic to its neighbours and empties their pools next.
- `GET /health/started` — has it finished booting? Holds liveness off while the JVM and the inline Flyway migration start.
- `GET /health` — every check at once, the database included. For a dashboard or a person. **Never for a liveness probe.**

Probes are not published: through the gateway these need a token like any other path.

- `GET /admin/health` (PLATFORM_ADMIN, OWNER, MANAGER) — the deep check, and **no probe calls it**. Makes a real round trip to the database and times it, reports the Kafka consumers, prints the connection pool's own figures (`active`, `idle`, `total`, `max`, `waiting`) and what readiness is currently saying. The two failures that look identical from a probe and want opposite remedies are told apart here: a database that is down fails the round trip, while a pool that is empty shows a fast round trip with `active` at `max` and `waiting` above zero — the fix for which is a bigger pool or fewer callers, never a restart.

## The gateway (the one public door)

The gateway is the single public door to the whole platform — nothing else is internet-reachable. Every call comes in as `/api/{service}/{path...}` (an equivalent `/api/v1/{service}/{path...}` form exists too; the version prefix is currently informational, and the unversioned alias is marked `Deprecation`/`Link`-to-`/api/v1` on every response to steer clients forward). The gateway only proxies to the 12 declared business services (an explicit allowlist — `iam-svc, tenant-svc, product-svc, inventory-svc, pricing-svc, cart-svc, order-svc, payment-svc, purchase-svc, customer-svc, notification-svc, reporting-svc`); anything else, even if it happens to be registered in service discovery, is unreachable. It terminates and verifies the JWT, strips any client-supplied identity headers, and re-stamps `X-Tenant-Id` / `X-User-Id` / `X-User-Email` / `X-Roles` / `X-Store-Ids` / `X-Permissions` from the verified token so every business service can trust those headers unconditionally (`ProxyResource.FORWARDED_HEADERS` is the one list of what reaches a service — a header stamped but not listed is dropped, which is how `X-Store-Ids` went missing for as long as it did, SJ-D46); it also forwards `Idempotency-Key` and the real `Content-Type` (so binary uploads like product images pass through intact) untouched.

**Vulnerability reporting (RFC 9116):** `GET /.well-known/security.txt` is public on the gateway, and the web app's nginx passes the same path through, so a researcher finds it on whichever host they reach. It is written from configuration, never from defaults — `SECURITY_TXT_CONTACT` (comma-separated `mailto:`, `https:` or `tel:` URIs), `SECURITY_TXT_EXPIRES` (an ISO instant in the future and no more than 366 days out, as RFC 9116 §2.5.5 recommends), and optionally `SECURITY_TXT_POLICY`, `SECURITY_TXT_CANONICAL` (both `https:`) and `SECURITY_TXT_PREFERRED_LANGUAGES`. Missing, expired or malformed settings answer `404` and log why, rather than publishing an invented address or a stale file; a value containing a line break is refused, so settings cannot add fields. `Cache-Control: max-age=3600`. What happens to a report is in [SECURITY.md](../SECURITY.md).

Guest/customer storefront access is carved out by an explicit path whitelist keyed on an `X-Storefront-Tenant` header (catalog browse, price resolve, active promotions, per-store storefront config, stock availability, and — for a signed-in customer only — placing an order and paying online); everything else requires a verified staff or customer Bearer token.

Protective features: Redis-backed rate limiting (default 100 req/min per caller, so it holds across gateway replicas), brute-force login lockout (5 failed attempts → 15-minute block on `/auth/login`), a **card-data guard** (every body and query string is scanned for a payment card number — 15/16/19 digits, Luhn-valid, an issuer range issued at that length — and one found is answered `400 CARD_DATA_NOT_ACCEPTED` without being forwarded, echoed or logged; EAN-13/GTIN-14 barcodes, IMEIs and all-digit ids are deliberately not cards; with the log scrubber in every service, this is what makes the PCI DSS SAQ-A scope a fact rather than a design intention), a **body-size cap** (1 MB on every route; only a route that takes a document is allowed more — `shelfj.gateway.upload-routes`, today `/api/purchase-svc/e-invoices=21000000` and each network's delivery route beside it, `/api/purchase-svc/e-invoices/inbound/peppol`, `…/fr_pdp` and `…/simulated`, at the same, and `/api/payment-svc/admin/settlements=6000000` for an acquirer's settlement file (11.10); the list is `GatewayConfig`'s default and lives nowhere else, since a one-route copy in the packaged properties once shadowed it and held every network's delivery to 1 MB (SJ-D64) — matched on the normalised path exactly, so neither its sub-routes nor a `..` walk out of it take its cap; a body over its cap is refused `413 PAYLOAD_TOO_LARGE` on its declared length before a byte is read, or counted up to the cap when it declares none), a deny-by-default CORS policy (only explicitly configured browser origins get CORS headers), a per-upstream circuit breaker (opens after 5 consecutive connect/read failures for 10s and fails fast with a clean 503 instead of piling up timeouts), connect/read timeouts (2s/10s, surfaced as 502/504 rather than hangs), and a tenant-status gate that polls tenant-svc's `storefront/active` flag (cached 15s, fails open) so a suspended tenant's storefront stops serving without the gateway holding its own tenant data.

**Errors are RFC 9457 problem details:** every error, from any service or the gateway itself, is `application/problem+json` — `type` (`urn:shelfj:problem:CODE`), `title`, `status`, `detail`, `instance`, the stable `code`, `details`, `requestId`, and the legacy `error`/`meta` members clients read before. A response with data is the plain envelope. Every service's `/openapi` (and the gateway's) is OpenAPI 3.1 with the `Problem` schema.

**Script integrity on the web shell (PCI DSS v4.0.1 11.6.1; SAQ-A's condition that the site cannot be altered by scripts):** the web image lists every script it serves with a reason and a SHA-256 in `/script-inventory.json`, generated from the bundle at image build by `infra/script-inventory.sh` (a script without a reason fails the build). The gateway's `ScriptIntegrityMonitor` reads the shell's entry page and inventory on a schedule (`shelfj.gateway.script-integrity.web-url`, `…interval-minutes`, default daily), reports an unlisted, changed or missing script as drift, logs it at ERROR and exposes it as the gauge `shelfj_script_integrity_drift` (Prometheus rules `ScriptIntegrityDrift`, `ScriptIntegrityUnchecked`). `GET /admin/security/script-integrity` returns the last report and `POST /admin/security/script-integrity/check` runs one now — gateway-local routes, PLATFORM_ADMIN only (`403` otherwise; `409 SCRIPT_INTEGRITY_NOT_CONFIGURED` with no web url).

## Platform-wide conventions

These apply across (almost) every endpoint below and are called out per-service only where a service deviates from them:

- **Tenant scoping**: every request is scoped to the caller's tenant, taken from the gateway-verified identity (or, on public storefront paths, from the resolved storefront tenant) — never from a client-supplied body field.
- **Default-deny RBAC**: role model is `PLATFORM_ADMIN` (cross-tenant), `OWNER`, `MANAGER`, `STOREKEEPER`, `CASHIER`, `CUSTOMER`. The shared `AdminAuthorizationFilter` enforces four tiers: **(1)** most of the `/admin/...` subtree — every HTTP method, *including GETs* — requires a management role (`PLATFORM_ADMIN`/`OWNER`/`MANAGER`), with bootstrap/receipt exemptions (`POST /admin/tenant` during onboarding, `POST .../receipts`); **(2)** **staff-operable admin surfaces** require any staff role (`STOREKEEPER`/`CASHIER` included): `/admin/inventory/**` (warehouse), `/admin/cash/**` (till — resource layer may still demand MANAGER+ for close/drops), plus support GETs `GET /admin/tenant`, `GET /admin/tenant/obligations`, `GET /admin/tenant/retention` (the schedule the purging services read), `GET /admin/stores…`, `GET /admin/products/variants/resolve`; **(3)** `POST .../refunds` and `POST .../void` require a management role even outside `/admin/`; **(4)** any other mutating request needs at least a staff role, except a small open allowlist (identity endpoints, onboarding, `/prices/resolve*`, `/orders`, `/cart*`, `/payments/online`, `/inventory/reservations*`); **(5)** **reads default-deny too** — since SJ-D11 a non-`/admin` GET needs at least a staff role unless it is on the curated open-read allowlist (storefront catalogue and config, availability, promotions, own cart, own orders, `/auth/me`, onboarding status). A GET added tomorrow ships closed. *(This paragraph previously ended "Non-`/admin` GETs outside the staff-admin list are not gated by this filter", which stopped being true when reads were closed and was found still standing during a live verification pass.)*
- **Granular permissions and custom roles (20.10)**: the five roles stay as *tiers* — the filter above reads them, and nothing about that changed. What a tenant may now do is define a **role of its own that stands on a tier and holds fewer of that tier's permissions** — a shift lead who is a `MANAGER` in every way but cannot void a sale or post a journal, a trainee who is a `CASHIER` who cannot open the drawer. A custom role can only *narrow* its tier, never widen it, so nothing a tier refuses by path becomes reachable by naming a permission. The catalogue (`GET /admin/roles/permissions` on tenant-svc; `Permissions` in common-web) is twelve decisions: `sales.void`, `sales.refund`, `till.no_sale`, `till.manage`, `stock.adjust`, `purchasing.approve`, `purchasing.invoices.decide`, `finance.journal`, `finance.payments` (17.10: propose, approve and pay supplier payment runs, and change a supplier's bank details), `pricing.write`, `customers.privacy`, `staff.manage`. Defaults by tier: a manager holds all twelve, a storekeeper `stock.adjust`, a cashier `till.no_sale`, and both of those `purchasing.approve` as well — the spend ceiling in `shelfj.purchase.approval.limits`, not the tier, decides who may approve how much, so the permission is what a custom role takes away and the ceiling is what it still has to clear (rejection needs neither, as before); an owner and the platform hold everything and **are never narrowed**. Each is checked at the one place the action happens with `TenantContext.requirePermission(code)`, *after* the tier gate, and refuses with `403 PERMISSION_DENIED` naming the permission. How it travels: iam-svc mints a `perms` claim for a login that holds any custom role (present and possibly empty — a role narrowed to nothing is a real value); the gateway strips any client-supplied `X-Permissions` and stamps the claim (`-` when empty); a service judges a caller by the header when it is present and by the tiers' defaults when it is absent, so a token minted before the claim existed, and every direct call in an integration test, behaves exactly as before. A token carries what it was minted with: a role redefined reaches its holders at their **next sign-in**.
- **Tenant defaults (SJ-D53)**: where a request may leave out a currency or country — a price list, a customer's VAT status, a supplier, store credit, a Z-report, a gift card, an order, a supplier CSV import — the tenant's own, as declared at onboarding, is used. It is read from tenant-svc, never assumed: the platform used to fill a gap with `GBP` (and `EUR`, and `GB`), which put a yen tenant's price lists and store credit in pounds without an error. When the tenant's profile cannot be read the write is refused with `503 TENANT_PROFILE_UNAVAILABLE` and nothing is stored; naming the currency or country explicitly needs no profile, but a named one must be a real ISO 4217 or ISO 3166-1 alpha-2 code (`400 CURRENCY_INVALID`, `400 COUNTRY_INVALID`) — a blank one means the tenant's own. An event that describes money without its currency is treated as malformed by its consumers. **SJ-D54:** the same literals had stayed in the schema — thirteen `DEFAULT 'GBP'`, `'USD'` and `'GB'` column defaults across customer-, order-, payment-, pricing- and purchase-svc — and are dropped, so a write that ever leaves the column out fails instead of storing pounds.
- **Pagination**: list endpoints are cursor-paginated — `?after=<meta.nextCursor>&limit=1-100` (default ~20).
- **Idempotency**: money- or stock-moving POSTs (place order, reserve/receive/adjust stock, record payment/refund/cash movement, goods receipt) accept an `Idempotency-Key` header so a retried POST is safe; placing an order requires one. Gift-card redemption has no key of its own and is instead idempotent on the order it is redeemed against. Together these are what let the POS replay a whole sale it captured offline.
- **Eventing**: domain events are written to each service's own outbox table in the same transaction as the state change and published to Kafka at-least-once; consumers dedupe on event id. No service calls another synchronously for these flows.
- **Tenant data export (21.14, EU Data Act ch.VI)**: every one of the twelve business services serves what it holds for the caller's business at `/admin/tenant-data`, to the **owner** alone (anyone else `403`), because it carries every staff member's and customer's records.
  - `GET /admin/tenant-data` — the manifest: each table in the order an import loads it (after the tables it refers to), with its columns (name, type, generated), key, `rows` and `checksum` (the md5 of its rows in key order without `tenant_id`, so an import into another business reads back the same figure), `derived` for projections rebuilt from events, `importSkippedReason` and `dependsOn`; and the register art.26 asks for: `excludedTables`, `excludedColumns` and `keptAtErasure`, each with its reason. The catalog is read from the service's own schema, so a new table or column is exported the day it is migrated; one the service cannot tie to a business, or an exclusion naming something the schema no longer has, fails the manifest with `500 TENANT_DATA_CATALOG_INCOMPLETE` naming it rather than serving an export that is quietly missing a table. Every service's integration tests check this.
  - `GET /admin/tenant-data/tables/{table}?after=&limit=` — the table's rows as JSON objects keyed by column, in key order (`limit` 1–1000, default 500); `meta.nextCursor` fetches the next page. `404 TENANT_DATA_TABLE_UNKNOWN` for a table not exported (the name is looked up in the catalog, never put into SQL); `400 TENANT_DATA_CURSOR_INVALID` for a cursor the pages did not give.
  - `POST /admin/tenant-data/tables/{table}` `{rows: [...]}` — loads a page, as it was served, into the caller's business, all or nothing: rows keep their ids and take the importing business as theirs. `409 TENANT_DATA_IMPORT_SKIPPED` for a table not imported (a business's own record, a notice to leave), `TENANT_DATA_IMPORT_CONFLICT` for a row already here (a page sent twice), `TENANT_DATA_IMPORT_MISSING_PARENT` for a row whose parent is not loaded yet, `TENANT_DATA_IMPORT_NOT_THIS_TENANT` for a child row of a parent the business does not have; `400 TENANT_DATA_IMPORT_INVALID` (not rows, or a value that does not fit), `TENANT_DATA_PAGE_TOO_LARGE` (over 1000).
  - Left out everywhere: `outbox`, `processed_events`, `flyway_schema_history`. Left out by name: credentials (a staff password hash, login and one-time codes, HMRC tokens, a fiscal device's signing key, device push tokens, unsubscribe tokens), delivery machinery (idempotency keys, payment provider webhooks) and platform reference data (allergens, units, the law as recorded). When tenant-svc says a business's retrieval period has ended (`TenantDataErasureDue`), each service erases every table the business's rows sit in, children first, in one transaction with a `TenantDataErased` announcing the counts.

## cart-svc

### Cart (`/cart`)
Server-side pre-checkout cart, keyed by cart id, session id, or the caller's authenticated identity. Note: every call requires a verified token (cart paths are not on the gateway's public storefront whitelist, and no anonymous/guest token exists), so a tokenless guest cannot reach this service — the current Flutter storefront keeps its pre-checkout cart on-device and never calls cart-svc. The session-cart + merge endpoints exist for authenticated clients that want a server-side cart.

- `POST /cart` — create or fetch the caller's active cart.
- `GET /cart` — view the cart and its line items (identified by cart id, session id, or the caller's authenticated identity).
- `POST /cart/items` — add an item to the cart (increments quantity if the variant is already in it).
- `PUT /cart/items/{itemId}` — change the quantity of a cart line.
- `DELETE /cart/items/{itemId}` — remove a line from the cart.
- `POST /cart/merge` — merge a session-keyed cart into the authenticated customer's cart (post-login merge).

**Business rules**
- Cart is not on the gateway's public storefront whitelist — every call needs a verified token.
- Once an order is placed, the cart is asynchronously marked checked-out (via `OrderPlaced`), not synchronously cleared by the checkout call.

**Events**
- Consumes: `OrderPlaced` (marks the cart checked-out), `StoreStatusChanged`, `TenantStatusChanged` (local suspension gate).
- Publishes: none.

## customer-svc

### Profile & Addresses (`/customers`)
Customer master data for the storefront and POS.

- `POST /customers` — register a new customer profile.
- `GET /customers` — list customers.
- `GET /customers/lookup?email=&phone=` — find a customer by email or phone (POS/CRM lookup).
- `GET /customers/{id}` — get a customer profile.
- `PUT /customers/{id}` — update a customer profile.
- `DELETE /customers/{id}` — GDPR erasure/anonymize a customer (SJ-D43: also deletes their saved addresses and publishes `CustomerErased` so order-svc and notification-svc redact what they hold about them; the event names the login as well as the customer id, so the redaction reaches web orders — SJ-D44).
- `POST /customers/me` — the signed-in shopper's own record in this shop, created on first use from the token's login and email, or adopted from the unlinked record the till already held for that address (SJ-D44). Identity comes from the token only. order-svc calls this at checkout so an online order carries a customer id the shop can resolve; loyalty, the confirmation email and erasure all key on it.
- `GET /customers/me` — the same record, never created: 404 for a shopper who has not bought here.
- `PUT /customers/me` — **the shopper's own profile (12.10)**: name, phone, date of birth and gender, found by the token's login; the email is the login's and is not writable here. `CUSTOMER_NOT_FOUND` (404) until the record is claimed. Free text is bounded (`@Size`: names 100, phone 32).
- `GET /customers/me/addresses` · `POST /customers/me/addresses` · `PUT /customers/me/addresses/{id}` · `DELETE /customers/me/addresses/{id}` — **the shopper's own address book (12.10)**, keyed on the token's login: another shopper's address id is `ADDRESS_NOT_FOUND` (404), not forbidden, and the same login at another shop has no book there. Marking one address default clears the previous default. At most **ten** per shopper — `CUSTOMER_ADDRESS_LIMIT` (409), decided under the customer's row lock so a race for the last place cannot overfill it. Lines are bounded at 120 characters, type and postcode at 20. Admitted by the shared filter by shape (`/customers/me/addresses` and one id-addressed child), so nothing else under `/customers/me/` is open by accident. Reachable from a storefront because the gateway's signed-in-customer allowlist (`JwtAuthFilter.isStorefrontCustomerAccount`) derives the tenant from `X-Storefront-Tenant` for exactly these shapes and methods — the first live run of the flow got `NO_TENANT` on `PUT /customers/me` before that list was taught them, which is the check to make whenever a shopper-facing route is added.
- `GET /customers/me/export` · `GET /customers/{id}/export` — UK GDPR art.20 data export, for the shopper and for staff handling a request that arrived by phone or letter. One JSON document: profile, addresses, loyalty and store credit with both ledgers, marketing preferences with their evidence trail, and every order (fetched from order-svc by both ids). Fails closed: an unreachable order-svc is a 503 `EXPORT_ORDERS_UNAVAILABLE` and no file, never a partial export.

### Marketing consent (`/customers/me/marketing`, `/customers/{id}/marketing`, `/marketing/unsubscribe`)

PECR reg.22/23 and UK GDPR art.7(1). `marketing_preferences` is what is true now; the append-only `marketing_consent_log` is the evidence — who, when, how (`SIGNUP`, `CHECKOUT`, `PREFERENCE_CENTRE`, `STAFF`, `UNSUBSCRIBE_LINK`, `IMPORT`) and the wording shown. Four channels (`EMAIL`, `SMS`, `PHONE`, `POST`); basis `CONSENT` or `SOFT_OPT_IN`, kept apart because the law keeps them apart. **Silence is not consent:** a channel with no row is refused.

- `GET /customers/me/marketing` · `PUT /customers/me/marketing` — the shopper's preference centre. Channels left out of a `PUT` are untouched. Body: `{ channels: [{ channel, granted, basis? }], notice? }`.
- `GET /customers/{id}/marketing` · `PUT /customers/{id}/marketing` — the staff view, and consent taken over the counter; the acting staff member is recorded.
- `GET /customers/{id}/marketing/allowance?channel=` — whether one marketing message may be sent. Asked by notification-svc before every `MARKETING` send; answers no for an unknown channel, no preference, an opt-out or an erased record, and returns the per-send `unsubscribeToken` the message must carry when the answer is yes.
- `POST /marketing/unsubscribe` — the opt-out link. Public and unauthenticated by design (the token is the capability); stops every channel unless one is named; a second click is not an error. The gateway locks an address out after five wrong tokens (`429 TOKEN_LOCKED`), the same way it does wrong passwords.
- `POST /customers/{id}/addresses` — add a delivery/billing address.
- `GET /customers/{id}/addresses` — list a customer's addresses.
- `PUT /customers/{id}/addresses/{addressId}` — update an address.
- `DELETE /customers/{id}/addresses/{addressId}` — remove an address.

### Loyalty (`/customers/{id}/loyalty`)
- `GET /customers/{id}/loyalty` — view loyalty point balance.
- `POST /customers/{id}/loyalty/earn` — manually credit loyalty points.
- `POST /customers/{id}/loyalty/redeem` — redeem points (e.g. against a sale).
- `POST /customers/{id}/loyalty/adjust` — management correction to a balance.
- `GET /customers/{id}/loyalty/ledger` — loyalty transaction history.

### Store Credit (`/customers/{id}/store-credit`)
- `GET /customers/{id}/store-credit` — view store-credit balance (per currency).
- `POST /customers/{id}/store-credit/issue` — issue store credit (e.g. for a return).
- `POST /customers/{id}/store-credit/redeem` — spend store credit against a sale.

**Business rules**
- GDPR erasure is restricted to `PLATFORM_ADMIN`/`OWNER`/`MANAGER` — deliberately stricter than the shared default, since this path isn't under `/admin/` and would otherwise be open to any staff role.
- Loyalty earn/redeem/adjust and store-credit issue/redeem are deliberately left open to any staff role for normal POS checkout use.
- Loyalty is auto-accrued once per order from the `OrderConfirmed` event (deduped by event id); guest orders (no customer id) earn nothing.

**Events**
- Consumes: `OrderConfirmed` (auto-accrues loyalty points).
- Publishes: `CustomerRegistered` (also for a record created by `POST /customers/me`), `LoyaltyEarned`, `LoyaltyRedeemed`, `LoyaltyAdjusted`, `StoreCreditIssued`, `StoreCreditRedeemed`, `CustomerErased` (SJ-D43; ids only — `customerId` and, when linked, `loginId` — no email/phone, since the event outlives the erasure it announces).
- Calls: order-svc `GET /orders/export` (the sales half of a data export; fail-closed).

## iam-svc

**Password policy (NIST SP 800-63B-4, OWASP ASVS 5.0 V6):** a password that is the only factor is at least 15 characters (`400 PASSWORD_TOO_SHORT`) and at most 128 (`PASSWORD_TOO_LONG`), any character including spaces, no composition rules, no expiry; it must not be, or contain, the login (`PASSWORD_IS_IDENTITY`); and it is screened against known breaches through the Pwned Passwords range lookup — only the first five characters of the SHA-1 leave the service (`PASSWORD_BREACHED`; a screen that cannot be reached lets the password through and logs the miss). The same policy holds at `POST /auth/register`, `POST /auth/admin/staff-users`, platform-admin creation and `PUT /auth/change-password`. Config: `shelfj.iam.password.min-length`, `max-length`, `breach-check.enabled|url|timeout-ms`. Below eight characters bean validation answers first (`VALIDATION_FAILED`).

### Authentication (`/auth`)
- `POST /auth/admin/staff-users` — find-or-create a staff account by email (a management action; the store-level role is granted separately via tenant-svc).
- `POST /auth/register` — self-register a new customer account.
- `POST /auth/login` — tenant staff / customer login.
- `POST /auth/platform-login` — platform-console login, kept deliberately separate so a `PLATFORM_ADMIN` credential never works on a store/POS login screen and vice versa.
- `POST /auth/refresh` — exchange a refresh token for a new access token.
- `POST /auth/logout` — revoke a refresh token.
- `POST /auth/login`, `POST /auth/platform-login` — when the login holds a second factor (20.12) the answer is `200 { mfaRequired: true, mfaToken, mfaMethods }` and **no tokens**; when it must have one and has none, `{ mfaEnrolmentRequired: true, accessToken }` where the token (scope `mfa-enrol`, ten minutes, no role or tenant) reaches only `/auth/mfa/**`.
- `POST /auth/mfa/login` — public: answer a waiting sign-in — `{ mfaToken, method: TOTP | RECOVERY_CODE | PASSKEY, code | assertion }` → the token pair (`amr`: `pwd` + `otp` or `hwk`). Five wrong answers end the wait (`401 MFA_CHALLENGE_EXPIRED`); twenty in fifteen minutes over all of a login's sign-ins lock its second factor (`429 MFA_LOCKED`).
- `POST /auth/mfa/login/passkey-options` — public: the WebAuthn challenge for a waiting sign-in.
- `GET /auth/mfa` — the caller's own factors: `totp`, `passkeys[]`, `recoveryCodesLeft`, `required`.
- `POST /auth/mfa/totp` → `{ secret, otpauthUri }` (pending) · `POST /auth/mfa/totp/confirm { code }` → `{ recoveryCodes?, tokens? }` (recovery codes with the first factor; the real session when called with an enrolment token) · `POST /auth/mfa/totp/remove { password }`.
- `POST /auth/mfa/passkeys/options` → creation options + `registrationToken` · `POST /auth/mfa/passkeys { registrationToken, name, clientDataJson, attestationObject }` · `POST /auth/mfa/passkeys/{id}/remove { password }`.
- `POST /auth/mfa/recovery-codes { password }` — ten new codes; the old ones stop working.
- `GET /auth/admin/mfa-policy` (OWNER, MANAGER) · `PUT /auth/admin/mfa-policy { requiredTiers: [OWNER|MANAGER|STOREKEEPER|CASHIER] }` (OWNER) — who must have a second factor. Removing the last factor is then `409 MFA_REQUIRED_BY_POLICY`, and a password-only session is not renewed (`401 MFA_REQUIRED`).
- `DELETE /auth/admin/staff-users/{userId}/mfa` — the lost phone: OWNER for their own staff, PLATFORM_ADMIN for anybody, never oneself (`400 MFA_RESET_SELF`); ends the person's sessions.
- `GET /auth/.well-known/jwks.json` — public: the token signing keys' public halves (RFC 7517), `Cache-Control: max-age=300`. Access tokens are RS256 and carry the `kid` of the key that signed them; the gateway and the MQTT broker verify against this set.
- `GET /auth/admin/signing-keys` — PLATFORM_ADMIN: the signing key register (kid, status `ACTIVE`/`RETIRING`/`RETIRED`, dates) — never key material.
- `POST /auth/admin/signing-keys/rotate` — PLATFORM_ADMIN: mint a new signing key now; the old one keeps verifying until the tokens it signed have expired.
- `PUT /auth/change-password` — change the caller's own password.
- `POST /auth/delete-account` — a customer deletes their own login (SJ-D43; requires the password again). Refused (403) for a staff account — that's removed by the business that employs its holder, not self-service.

### Bootstrap (`/bootstrap`)
- `POST /bootstrap/admin` — one-time creation of the first `PLATFORM_ADMIN` for a fresh deployment (refuses once one already exists; not JWT-gated by necessity).

### Identity (`/auth/me`)
- `GET /auth/me` — the caller's own identity, roles, **permissions** (20.10: the token's own claim when a custom role narrowed it, else the roles' defaults; an owner holds every permission) and profile, as verified by the gateway (the gateway forwards the token's identity, never the token).
- **The permission claim.** A login that holds any custom role carries `perms` in its access token: the union, over its assignments, of the custom role's permissions where there is one and the tier's defaults where there is not. A login with no custom role carries no claim and is judged by its tiers' defaults. An owner never carries one. Consumed events: `StaffAssigned` (now with `roleCode`, `permissions` and `roleUpdatedAt` beside the tier), `RoleDefined` (rewrites every assignment made through the role, **only forward** by the role's `updatedAt` — SJ-D52 found three redefinitions in one second applied out of order, and the outbox now also keys records by aggregate — so the next login carries the newest set), and `StaffRemoved` — **SJ-D51**: removing an assignment in tenant-svc used to stop at tenant-svc's table, and the role stayed on the login for good; a cashier taken off a store could sign in as its cashier the next morning. It is unbound now, and when the last staff role at the tenant goes the login is unbound from the tenant too (a shopper's token that still named a tenant would make the gateway record their next order at another shop against the business that let them go).

### POS Sessions (`/auth/pos/sessions`)
- `POST /auth/pos/sessions` — start a cashier POS session.
- `PUT /auth/pos/sessions/{id}/activity` — heartbeat a session to keep it alive.
- `DELETE /auth/pos/sessions/{id}` — end a POS session.
- `GET /auth/pos/sessions` — list active POS sessions.
- `POST /auth/pos/sessions/sweep` — force-expire sessions idle past their configured timeout and revoke their tokens (platform-wide maintenance sweep).

**Business rules**
- The bootstrap admin endpoint is a self-disabling one-shot: it refuses if any `PLATFORM_ADMIN` already exists, so it's safe to leave enabled.
- The idle-session sweep ignores tenant scope by design (it's a platform-wide op), so it's restricted to `PLATFORM_ADMIN`.
- Provisioning a staff user only mints the identity; the actual store role is granted asynchronously when tenant-svc publishes `StaffAssigned`.

**Events**
- Consumes: `TenantCreated`, `StaffAssigned` (grants the store role), `StoreStatusChanged`, `TenantStatusChanged`.
- Publishes: `UserRegistered`, `AccountDeleted` (SJ-D43; id only, on self-service account deletion).

### Reports (`/admin/inventory/reports`)
These are answered from inventory-svc's own tables rather than from reporting-svc, whose projections carry neither the reason code, the actor, nor any cost. See [reporting-api-gap-analysis.md](reporting-api-gap-analysis.md) for why each landed where it did.
- `GET /admin/inventory/reports/low-stock?storeId&limit` — items below their **own** reorder level, live, with `signal` naming which of threshold / safety stock / reorder point bound the row. Items that have run out entirely are included: they have no batch rows at all, and they are the most urgent line in the report. **Item lifecycle:** variants of a product the catalogue has discontinued or delisted are left out, however low they run, as they are from `POST /admin/inventory/planning/run`; a line reinstated or launched comes back.
- `GET /admin/inventory/reports/valuation?storeId&groupBy=STORE|VARIANT&limit` — what the holding is worth on its configured FIFO or AVERAGE basis. Stock carrying no cost comes back as `unvaluedQty` rather than valued at zero, which would understate a balance-sheet figure.
- `GET /admin/inventory/reports/shrinkage?storeId&from&to&groupBy=REASON|ACTOR|STORE` — write-offs over a period. Losses and finds stay on separate columns: a store that wrote off 100 units and found 100 others is not one that did nothing. `.../shrinkage/by-variant` drills a summary row down to what was actually written off.
- `GET /admin/inventory/reports/stock-turn?from&to&storeId&groupBy=STORE|VARIANT&limit` — cost of goods sold over a window against the average value held to produce it, plus `turnoverRatio` and `daysOnHand`. **`from` and `to` are required** — a turnover ratio has no meaning without a window, and `daysOnHand` divides by its length; both take a full ISO-8601 instant, not a bare date. COGS is taken from the cost price of the batches each sale actually drew down, so a historical window is answered with the costs of the day. Two fields say when a figure should not be trusted: `historyComplete` is false when the movement ledger was purged past the window's start, making opening values a floor; `uncostedSaleQty` reports quantity sold out of batches with no cost price, excluded from COGS rather than costed at zero. `turnoverRatio` and `daysOnHand` are **null**, not zero, when there was no stock to turn.
- `GET /admin/inventory/reports/gross-margin?from&to&storeId&groupBy=STORE|VARIANT&limit` — gross margin and GMROI (19.7): what the sales in the window earned, net of VAT, discounts and returns, against the cost of the batches they drew down. `revenue`, `cogs`, `grossMargin`, `marginPercent` (of revenue), `averageValue` (the same average holding stock turn reports), `gmroi` (margin ÷ average holding over the window) and `annualisedGmroi`, lowest margin first. Revenue arrives on each `OrderFulfilled` line as `netAmount` and is stored beside the movement it paid for, in the same transaction and under the same per-line dedupe; a return takes back its share of the line's revenue and the cost of the units, never more than the line has unreturned. Money keeps the scale it arrived in — revenue the currency's, cost the cost price's. Voided sales earn nothing. `unpricedSaleQty` counts quantity sold with no revenue recorded (sales from before orders carried it, or a line whose figure was malformed): their cost stays in COGS, so the margin is understated rather than invented. `marginPercent` is null when nothing was earned and `gmroi` when nothing was held. Management roles only, like every report under this path; `from`/`to` required.
- `GET /admin/inventory/reports/dead-stock?storeId&asOf&groupBy=BUCKET|STORE|VARIANT&limit` — stock on hand aged into the 0-30 / 31-60 / 61-90 / 91-180 / 180+ ladder. Age runs from the last **sale** of that item at that store, not from receipt: stock that arrived two years ago and sold this morning is not dead. Where nothing has ever sold, age runs from the oldest remaining batch's arrival and `neverSold` says so. `asOf` pins the instant ages are measured from, so a re-run against the same date gives the same answer.

### Food Safety Checks (`/admin/inventory/food-safety` staff · `/admin/food-safety` management)
Temperature monitoring (the cold chain) and HACCP due-diligence records, on one model: a temperature reading is a check with a number and limits, an opening check is one with a yes or no. Legal basis (England): Food Safety and Hygiene (England) Regulations 2013 Sch.4 (chilled ≤ 8 °C, hot-held ≥ 63 °C), Reg (EC) 852/2004 art.5 (HACCP-based procedures), Food Safety Act 1990 s.21 (these records are the due-diligence defence).

*Store staff* (any staff role, by path — a storekeeper or a deli cashier takes the reading):
- `GET /admin/inventory/food-safety/points?storeId&includeInactive` — a store's monitoring points, each with its check type, limits, last check, `dueStatus` (`OK`, `DUE` for the last quarter of the interval, `OVERDUE`) and `openFailures` (failures with no corrective action).
- `GET /admin/inventory/food-safety/check-types` — the platform's reference types (chilled/frozen storage, hot holding, cooking core, chilled/frozen delivery, opening/closing checks, cleaning, pest check) and the tenant's own. `statutory` is true only where the limit is law rather than FSA guidance.
- `POST /admin/inventory/food-safety/records` — record a check: `value` (°C) for a temperature check, `passed` for a pass/fail check, never both. **The server decides the result** and stores the limits it judged against, so a later change to a limit never rewrites a past record. A reading is judged at the precision it is stored at: more than two decimal places is refused (`FOOD_SAFETY_TOO_PRECISE`) rather than rounded, because `NUMERIC(6,2)` would otherwise store 8.004 as 8.00 on a record judged a failure against 8.00. Honours `Idempotency-Key` (201 first time, 200 with the same record on replay). A store-restricted caller may only record at their own stores (`STORE_ACCESS_DENIED`). A switched-off point takes no checks (`FOOD_SAFETY_POINT_INACTIVE`).
- `GET /admin/inventory/food-safety/records?storeId&pointId&result&openOnly&from&to&after&limit` — the diary, newest first, cursor-paginated; `from` inclusive, `to` exclusive.
- `GET /admin/inventory/food-safety/records/{id}` — one record with its corrective actions.
- `POST /admin/inventory/food-safety/records/{id}/corrective-actions` — what was done (`action`) and what happened to the food (`foodDisposition`: `NONE|MOVED|DISCARDED|REHEATED|RECOOKED|OTHER`). A failure stays open until one is recorded; more than one may be. 409 `FOOD_SAFETY_RECORD_PASSED` on a check that passed.

*Management* (under `/admin/` outside the warehouse subtree, so gated to OWNER/MANAGER by path):
- `POST /admin/food-safety/points` · `PUT /admin/food-safety/points/{id}` — a chiller, freezer, hot cabinet, goods-in bay or checklist at a store. Limits default to the check type's and **may only be stricter** — 422 `FOOD_SAFETY_LIMIT_LAXER_THAN_TYPE` for a chiller set to 10 °C when the law says 8. A check is judged against the tighter of the point's limits and its type's current ones, so tightening a type later still binds older points. Store and check type are fixed once created.
- `POST /admin/food-safety/points/{id}/deactivate` · `/activate` — with a required `reason`, kept in an append-only trail; 409 `FOOD_SAFETY_ALREADY_IN_STATE`.
- `POST /admin/food-safety/check-types` · `PUT /admin/food-safety/check-types/{id}` — the tenant's own types. Platform types are read-only (409 `FOOD_SAFETY_TYPE_READ_ONLY`), and a tenant's own type is never marked statutory.
- `POST /admin/food-safety/reviews` · `GET /admin/food-safety/reviews?storeId&after&limit` — a manager's periodic sign-off (the HACCP verification step), storing the record, failure and open-failure counts as they stood when signed.

Records, corrective actions, reviews and point switches are append-only. A background sweep (every 15 minutes, `shelfj.inventory.food-safety.overdue-sweeper.*`) raises `FoodSafetyCheckOverdue` once per missed due time.

### Withdrawals and Recalls (`/admin/inventory/recalls` staff · `/admin/recalls` management)
A withdrawal takes stock off sale; a recall also tells the customers who may have bought it. Legal basis: Reg (EC) 178/2002 art.19 (retained), and the FSA's guidance on traceability, withdrawals and recalls. A recall's scope is one or more lines, each a variant optionally narrowed to a lot (`batchNo`) and a best-before or use-by range; a line naming neither covers every pack.

*Management* (gated to OWNER/MANAGER by path):
- `POST /admin/recalls` — open one: `reference` (the notice's, unique per tenant, case-insensitive — 409 `RECALL_REFERENCE_TAKEN`, so a retried open never opens a second recall), `kind` (`WITHDRAWAL|RECALL`), `hazard`, `reason`, `customerNotice` (**required for a RECALL**, 400 `RECALL_NOTICE_REQUIRED`), `source` (`SUPPLIER|FSA|FSS|INTERNAL|OTHER`) and `sourceReference`, and `items` (1 to 100 lines). A RECALL also carries what it offers its buyers (05.10, GPSR arts.35–37): `remedies` (one or more of `REPAIR|REPLACEMENT|REFUND`, 400 `RECALL_REMEDIES_REQUIRED` without), `contactPhone` and/or `contactUrl` (an http(s) address; 400 `RECALL_CONTACT_REQUIRED` / `RECALL_CONTACT_URL_INVALID`), `singleRemedyReason` and `soldFrom` (ISO date; buyers of sales from that day are looked for, every sale of the packs in scope without it). Where GPSR's recall-notice rule binds any country the business trades in (`GPSR_RECALL_NOTICE`, via `Jurisdictions.inForceWhereTrading`), at least two remedies are required unless `singleRemedyReason` says why one (400 `RECALL_REMEDIES_INSUFFICIENT`), and a `customerNotice` that plays the risk down — *voluntary*, *precautionary*, *discretionary*, *in rare situations*, *no reported accidents* — is refused (400 `RECALL_NOTICE_MINIMISES_RISK`, the phrase in `error.details`). **Every batch in scope, at every store, is set to `RECALLED` in the same transaction**, so no sale or reservation can draw on it between the recall existing and the stock being held. A batch whose lot or date is not known is held too, as `LOT_UNKNOWN` or `DATE_UNKNOWN`: a pack nobody can rule out is withdrawn. A batch number this service writes itself (`ADJ`, `CC-…`, `MO-…`, `TO-…`, `RET-…`) names a movement, not a lot, and counts as unknown. Publishes `RecallOpened` naming the stores whose stock was held. **The sales that drew on the packs in scope are found in the same transaction** — every `SALE` movement of a scoped variant, live or archived, classified by its batch's lot and date exactly as the held batches are, so a sale from a pack with no lot is reached too — and kept in `recall_sales` (append-only). The response and the list carry `ordersAffected` and `qtySold`. A RECALL publishes `RecallSaleAffected` per order (keyed by the order: the recall's reference, hazard, reason, notice, remedies, contact, and the order's lines with lot, date, quantity and match), which order-svc turns into the notice to the buyer; a WITHDRAWAL records the sales and announces nobody.
- `POST /admin/recalls/{id}/close` — with optional close-out `notes`. **Refused with 409 `RECALL_STORES_OUTSTANDING` while any store still holds recalled stock with no final disposition**; `error.details` lists those store ids.
- `POST /admin/recalls/{id}/cancel` — a recall opened in error, with a required `reason`. Puts its stock back to the status it had before any recall held it, unless another open recall still holds the batch. 409 `RECALL_ALREADY_ACTIONED` once any store has returned or destroyed stock under it — that stock has left the books.

*Store staff* (any staff role, by path):
- `GET /admin/inventory/recalls?status&after&limit` — newest first, with each recall's scope-line count, stores affected, stores still to act and quantity held.
- `GET /admin/inventory/recalls/active` — every scope line of every open recall. **The till keeps this list and checks each item against it**, so a scan never waits on the network.
- `GET /admin/inventory/recalls/{id}` — scope, every batch held (with `match`, quantity at quarantine, remaining, `quarantinedOn` `OPEN|ARRIVAL`, and any release), every store action, and per-store progress.
- `POST /admin/inventory/recalls/{id}/stores/{storeId}/actions` — what a store found and did: `qtyFound`, `disposition` (`HELD_FOR_COLLECTION|RETURNED_TO_SUPPLIER|DESTROYED`), `noticeDisplayed`, `notes`. The response carries `systemQty`, what the system held off sale there, kept beside the count. **`RETURNED_TO_SUPPLIER` or `DESTROYED` takes the store's held stock off the books** — an `ADJUST` movement per batch with reference `RECALL` and reason `RECALL_WITHDRAWAL`, attributed to the caller, and `StockAdjusted` per variant. A store-restricted caller acts only at their own stores (`STORE_ACCESS_DENIED`).
- `POST /admin/inventory/recalls/{id}/batches/{batchId}/release` — a pack checked and found not to be affected, with a required `reason`. Only an uncertain match can be released: 409 `RECALL_BATCH_IN_SCOPE` for a batch whose lot and dates are in scope, `RECALL_BATCH_ALREADY_RELEASED` for a second release.

**Stock that arrives under an open recall is held as it arrives.** Every batch insert — a delivery, a transfer, a return, a count, an adjustment — checks the open recalls for its variant in the same transaction, so a delivery of the recalled lot the next day is never on sale for a moment; the receive response already says `RECALLED`. Scope lines, held batches, releases and store actions are append-only; only the recall's own status changes.

### Public Storefront Availability (`/inventory/availability`)
- `GET /inventory/availability` — public in-stock (yes/no) flag per variant for a store; no quantities are ever exposed.

**Business rules**
- `Idempotency-Key` is honored on receive/adjust/reserve so a retried POS or integration call can't double-move stock.
- Reservations follow hold → consume (fulfilled) or release (cancelled/expired); this is the checkout-time hold order-svc takes before stock is truly deducted.
- Transfer orders (inter-store) run create → ship → receive/cancel; move orders (intra-store, zone-to-zone) run create → pick → cancel.
- Cycle counts auto-approve variances within a configurable tolerance %; anything outside tolerance is flagged for manual adjustment.
- Kanban cards and ROP/EOQ plans both carry shared order-modifier fields (min/max order qty, lot multiplier) that constrain any suggested replenishment quantity.
- Public storefront endpoints expose only availability, never on-hand quantities.

**Events**
- Consumes: `GoodsReceived` (from purchase-svc), `OrderFulfilled`, `OrderReturned`, `OrderCancelled`, `OrderVoided` (from order-svc — deduct / restock / release hold / put back a voided till sale). A voided sale is received back as a `RECEIVE` movement with reference type `VOID` — distinct from a return's `RETURN` — because a sale voided after the money is taken and a customer return are different loss-prevention signals. It is received rather than reversed because the void and the fulfil arrive on different topics in either order, and a receipt and a deduction net to the same stock whichever lands first. Stock turn, gross margin, demand history and dead stock all exclude a sale whose order was voided. None of them nets it: the receipt goes into a new return batch, stock turn sums per batch, and a netted sale would leave its cost in one group and a negative sale in another. An `OrderVoided` from before this change has no lines and is skipped.
- Publishes: `StockReceived`, `StockReserved`, `StockReleased`, `StockDeducted`, `StockAdjusted`, `StockBelowThreshold`, `ReplenishmentSuggested`, `ReplenishmentResolved`, `SerialsRegistered`, `SerialStatusChanged`, `MaterialStatusChanged`, `TransferOrderShipped`, `TransferOrderReceived`, `TransferOrderCancelled`, `MoveOrderCompleted`, `MoveOrderCancelled`, `CycleCountAdjusted`, `PhysicalInventoryCreated`, `PhysicalInventoryCompleted`, `CostingMethodUpdated`, `AccountingPeriodOpened`, `AccountingPeriodClosed`, `KanbanTriggered`, `KanbanReplenished`, `KanbanCreated`, `RopPlanUpdated`, `RopComputed`, `LotSplit`, `LotMerge`, `FoodSafetyCheckFailed` (in the same transaction as the failing record; ids, reading and limits only), `FoodSafetyCheckOverdue`, `RecallOpened` (reference, kind, hazard and the ids of the stores whose stock was held; never the free-text reason or notice), `RecallSaleAffected` (05.10: one per order a RECALL reached — the notice and the offer travel with it, because the buyer is told what the recall said when it opened).

### Privacy under India's DPDP Act (`/customers/privacy`, `/customers/me/privacy`, `/customers/{id}/privacy`)
**13.12.** Consent, export and erasure were built to UK GDPR and PECR; India's Digital Personal Data Protection Act 2023 and the DPDP Rules 2025 (notified 13 November 2025; substantive duties from 13 May 2027, the register's `DPDP` obligation for `IN`) ask for more of the same shape, and it is offered to every business and enforced as the Act asks where it binds (`dpdp` true on the notice below). Everything a person is shown when they agree is kept with the consent; the log is append-only.
- `GET /customers/privacy/notice?language=` — **the notice, public**: read before signing up, resolved to the shop by the storefront header. In the language asked for when the business has published one, else in English, else `notice: null`; with `languages` (English and the twenty-two of the Eighth Schedule, ISO 639 codes, each `published` or not — `400 PRIVACY_LANGUAGE_UNKNOWN` for any other), the four `purposes` consent is asked for (`LOYALTY`; and `MARKETING`, `PERSONALISATION`, `ANALYTICS`, which `tracking` marks as never a child's), the grievance contact and `responseDays`, and `dpdp`/`dpdpFrom`. Fulfilling what was bought needs no consent (s.7(a)) and is stated, not asked.
- `GET /customers/privacy/settings` · `PUT /customers/privacy/settings` `{grievanceName, grievanceEmail, grievancePhone, grievanceAddress, responseDays}` — the business contact a person puts questions and grievances to (s.8(9), r.9) and the days it gives itself to answer a request: 1 to 90 (`400 PRIVACY_RESPONSE_DAYS_INVALID`, r.14(3)); `400 PRIVACY_GRIEVANCE_CONTACT_INVALID`. Owners and managers.
- `GET /customers/privacy/notices` · `POST /customers/privacy/notices` `{language, title, body}` → `201` — the current version per language, and a new version every publish (a consent names the version the person read; `409 PRIVACY_NOTICE_BUSY` for two publishes at once; `400 PRIVACY_NOTICE_TEXT_INVALID`). Owners and managers.
- `GET /customers/me/privacy` — the shopper's consents, purpose by purpose, against the notice version read; `child` (under eighteen by the date of birth held, s.2(f)), `guardian` (a standing guardian's consent, or null) and `canTrack` (false for a child with none).
- `PUT /customers/me/privacy/consents` `{choices:[{purpose, granted}], language}` — free, specific, informed, unconditional and unambiguous (s.6): each purpose on its own, against the notice in the language read. `400 PRIVACY_PURPOSE_UNKNOWN`, `PRIVACY_CHOICES_REQUIRED`; `409 PRIVACY_GUARDIAN_CONSENT_REQUIRED` for a child's tracking purpose without a guardian (s.9(3): no tracking, behavioural monitoring or targeted advertising at a child); `409 PRIVACY_NOTICE_REQUIRED` where the Act binds and no notice is published (consent is informed only against one, s.6(1), r.3). `DELETE /customers/me/privacy/consents` — every consent withdrawn in one call: as easy as giving it (s.6(4)). Staff take consent over the counter with `PUT /customers/{id}/privacy/consents` (recorded as the staff member's act, `source: STAFF`), read a customer's with `GET /customers/{id}/privacy`, and the evidence with `GET /customers/{id}/privacy/log` (`customers.privacy`).
- `POST /customers/{id}/privacy/guardian` `{guardianName, verification, reference}` · `DELETE` — a parent's or guardian's consent for a child, with how the parent's identity and age were verified (r.10: `DETAILS_HELD`, `DOCUMENT_SEEN`, `DIGITAL_LOCKER`); the reference notes what was seen, never a document's number (`400 PRIVACY_REFERENCE_IS_A_NUMBER`); `409 PRIVACY_NOT_A_CHILD` for a person of age. Withdrawn, the child's tracking consents fall with it, each withdrawal logged (`source: GUARDIAN`); `404 PRIVACY_GUARDIAN_CONSENT_NOT_FOUND`. Owners and managers.
- `GET /customers/me/privacy/requests` · `POST /customers/me/privacy/requests` `{kind, detail, nomineeName, nomineeContact}` → `201` — `ACCESS`, `CORRECTION`, `ERASURE`, `NOMINATION` (names who may act for the person, s.14: `400 PRIVACY_NOMINEE_REQUIRED`) or `GRIEVANCE` (ss.11–14), each `dueOn` the day the published period runs out and `overdue` past it; `400 PRIVACY_REQUEST_KIND_UNKNOWN`; `409 PRIVACY_REQUESTS_OPEN_LIMIT` at twenty open. `GET /customers/privacy/requests?status=&limit=` — the queue (`OPEN` soonest due first; any staff) and `POST /customers/privacy/requests/{id}/resolve` `{status: RESOLVED|REFUSED, resolution}` (`customers.privacy`; `409 PRIVACY_REQUEST_SETTLED`, `404`).
- `POST /customers/privacy/breach-intimations` `{noticeId, subject, body, customerIds}` → `201 {recipients, failures}` · `GET` — a breach told to each customer named, or to everyone reachable when none is (up to 500 named; `409 PRIVACY_NOBODY_TO_TELL`), by email where there is one and by text where there is only a phone, through notification-svc (`DATA_BREACH_INTIMATION`, one send per person deduped by the intimation); what was sent and to how many is kept for the report to the Board (r.7(1), r.7(2)(b)(vi)), a failure counted, never hidden. Owners and managers. The business then records the duty done on the platform's security notice (tenant-svc, below), the intimation's id as its reference.

## notification-svc

### Notifications (`/admin/notifications` + send)
Fan-in from Kafka events, plus a staff send path for POS receipts etc.
- `GET /admin/notifications/shortage-alerts` — list low-stock shortage alerts (by store or variant).
- `GET /admin/notifications` — in-app notification feed (welcome, order-confirmation, POS receipt, etc.), newest first.
- `POST /notifications/send` — staff-triggered send (order-svc uses this for EMAIL receipts). Body: `recipient`, `subject`, `body`, optional `type`/`eventId`/`customerId`/`category`. `category: MARKETING` (PECR reg.22) must name the customer and is sent only after customer-svc's `/marketing/allowance` says yes — otherwise `409 MARKETING_CONSENT_MISSING`, and also when the answer cannot be had (fail-closed: sending without provable consent is the offence). An allowed marketing message has the opt-out link appended by notification-svc itself (reg.23).

**Business rules**
- **Channels (13.7).** `POST /notifications/send` takes `channel`: `EMAIL` (the default: whatever `shelfj.notification.channel` configures, below), `SMS` (the recipient is an E.164 number, the body at most 1600 characters; `SMS_RECIPIENT_INVALID`, `SMS_BODY_TOO_LONG`), `PUSH` (the recipient is a login id; every device that login registered with this shop is pushed to; `PUSH_NO_DEVICE` when it has none, and a device the provider no longer knows is forgotten on the spot) or `APP`. `CHANNEL_UNKNOWN` (400) otherwise; `CHANNEL_UNAVAILABLE` (503) when the channel's provider is not configured. Marketing goes by `EMAIL` or `SMS` only, each gated on the customer's consent for that channel (`MARKETING_CHANNEL_UNSUPPORTED` for push or in-app). The response and the log name the channel; `GET /admin/notifications?channel=` narrows the feed. Providers are seams with a simulated twin: SMS via `shelfj.notification.sms.provider` = `SIMULATED` (default) or `TWILIO` (`…sms.twilio.account-sid`, `auth-token`, `from`); push via `shelfj.notification.push.provider` = `SIMULATED` or `FCM` (HTTP v1: `…push.fcm.project-id`, `service-account` as JSON or a file path; the service account's key signs the OAuth assertion, the token is cached). `GET /admin/notifications/channels` says what this deployment has.
- `POST /notifications/devices` `{platform: ANDROID|IOS|WEB, token}` · `GET /notifications/devices` · `DELETE /notifications/devices/{id}` — **the caller's own push devices**, keyed on the token's login: a shopper from a storefront (the gateway derives the tenant from `X-Storefront-Tenant` for these shapes) or a member of staff from their console. The same token again refreshes the device; at most ten per login per shop (`PUSH_DEVICE_LIMIT`); the whole token is never shown back; another login's device is not found. `OrderConfirmed` pushes to the customer's login when they registered a device (beside the email). The app-side token comes from the platform's push SDK (FCM on Android and iOS, a service worker on the web), which is deployment wiring a Firebase project supplies — the same way the Stripe account is the merchant's.
- Channel is selected by `shelfj.notification.channel`: `app` (default, in-app only), `email`/`smtp` (SMTP **plus** in-app via a composite channel so the feed still fills when email is on), or `mqtt` (device-facing push — POS terminals, kiosk/back-store displays, platform console — **plus** in-app; topic `shelfj/notifications/{tenantId}/{recipient}`).
- MQTT auth: every client (including this service's own publisher connection) presents a shelfj platform JWT as the MQTT password; the broker (EMQX) verifies it and ties the connecting username to the JWT's `tenant` claim, then ACL-scopes reads to that tenant's own topic subtree — see `infra/emqx.conf` / `infra/emqx-acl.conf`.

**Events**
- Consumes: `OrderConfirmed` (order-confirmation notice), `StockBelowThreshold` (shortage alert), `FoodSafetyCheckFailed`, `FoodSafetyCheckOverdue` (store alerts, addressed to the store's devices like a shortage alert, once per event), `RecallOpened` (one alert per store whose stock was held, each deduplicated on an id derived from the event and the store), `RecallNoticeIssued` (05.10: the written recall notice to a buyer — by email to the shop's customer record, else by text to an E.164 number the order or the record holds, and a push to the login's devices besides; the body carries what GPSR art.36 lists: the headline *Product safety recall*, the product and its lot, the hazard in plain words, what to do, the remedies to choose from, where to turn, and a request to pass it on; each send keyed on the event, so a redelivery tells nobody twice; a buyer with no email and no usable number is logged, and order-svc keeps the notice for when they come back), `UserRegistered` (welcome/registration notice), `CustomerErased` (SJ-D43; redacts the recipient/subject/body of that shop's messages to the customer), `AccountDeleted` (SJ-D43; redacts the platform's own messages to the deleted account, e.g. `WELCOME` — a shop's own messages are redacted by its own `CustomerErased` instead).
- Publishes: none.

## order-svc

### Order Lifecycle (`/orders`)
- `GET /orders` — list orders for the tenant (filter by store/channel/status/date range).
- `GET /orders/mine` — the signed-in customer's own order history (never another customer's, never the tenant's full book).
- Order lines (`items[].weighingInstrumentId`) — for a line sold by weight, the certified instrument the reading came from, from tenant-svc's register; the till refuses to sell by weight from one that is not certified, and the line records which it was, so an inspector can go from a receipt to a certificate. Null for a line sold by the each.
- `POST /pos/age-checks` — the due-diligence record behind an age-restricted sale (Licensing Act 2003 s.139 and its equivalents: the defence is "all reasonable precautions", and a precaution nobody can show was taken is none). One append-only entry per check the till made, pass or refusal, carrying the rule that applied at that moment (category, minimum age, country, whether it was store policy), the cashier from the token, and — required on a refusal — why: `UNDER_AGE`, `NO_ID`, `ID_REJECTED`, `PROXY_SALE`, `BORN_AFTER_CUTOFF`, `OTHER`; optionally what was shown on a pass (`PASSPORT`, `DRIVING_LICENCE`, `PASS_CARD`, …). Any staff role, at a store the cashier is assigned to. A refusal with no reason, a pass with one, or a value outside the vocabulary is a 400. A check against a birth-date cut-off also carries `bornBefore` and `bornBeforeStorePolicy`, copied from product-svc's answer; a `BORN_AFTER_CUTOFF` refusal or a cut-off policy without the date is `AGE_CHECK_CUTOFF_REQUIRED`, and a malformed or impossible date `AGE_CHECK_BORN_BEFORE_INVALID`. The customer's own date of birth is never sent or stored.
- `GET /admin/audit/events?store=&actor=&type=&from=&to=&after=&limit=` — **the business audit trail (20.11)**: every discount granted, sale voided, drawer opened without a sale, order cancelled and return taken, newest first, each naming the member of staff responsible (`actorId`), the store, the order, the money (`amount`: the discount or the refund) and the reason, plus the log's own qualifier in `detail` (the role that authorised a discount, the status a cancel came from, a return's refund method, the supervisor who authorised a no-sale). One `UNION ALL` over the five append-only logs, tenant-filtered in every branch, cursor-paged on `(occurredAt, id)`. `type` is `DISCOUNT|VOID|NO_SALE|CANCEL|RETURN` (`AUDIT_TYPE_UNKNOWN` otherwise); `from` must be before `to` (`AUDIT_RANGE_EMPTY`). Management-only by path; a store-bound manager reads their own stores, and a `store` outside their scope is `403`. Read-only: the resource has no writing method. Stock adjustments live on inventory-svc's movements ledger (`actorId` on each row) and the admin Audit screen reads both.
- `GET /admin/pos/age-checks?store=&outcome=&from=&to=&after=&limit=` · `GET /admin/pos/age-checks/summary?store=&from=&to=` — the register and its counts (total, passed, refused, refusals by reason, checks by category): what a licensing officer asks for first. Management-only.
- `GET /orders/export?customer=&login=` — every order one person placed here, with lines, for a data export (art.20). Staff-only, and read service-to-service by customer-svc, which assembles the whole document. Both ids are accepted because a person has both: an online sale is filed under their login and a till sale under the shop's customer record (SJ-D44). Neither id is a 400; a shopper token is a 403 — the read allowlist no longer takes a literal such as `export` for an order id, and the resource requires a staff role itself.
- `POST /orders` — place a new order (POS or ONLINE channel); requires an `Idempotency-Key`.
- `POST /pos/log/orders/{orderId}` — journal a completed POS sale to the transaction log. **Staff-reachable** (CASHIER/MANAGER/OWNER) and idempotent on the order, so a retry or a replayed offline sale returns the existing entry. This write used to sit under `/admin/pos-log`, which is management-gated — the cashier who took the sale could not journal it, so nothing ever did and the table was empty for the life of the product. The read side stays at `GET /admin/pos-log`.
- `GET /admin/reports/exceptions?from&to&storeId&groupBy=ACTOR|STORE` — staff exception report: discounts, voids and no-sale drawer opens per staff member or store, with journalled sales as the denominator. Check `journalCoverage` before reading any rate; when false, nothing journalled a sale in the period and the counts have nothing to divide by.
- `GET /admin/reports/sales-by-hour?from&to&storeId&channel&tz` — takings bucketed by hour of the trading day, so a manager can staff to the actual peak. `tz` takes an IANA zone name (`Europe/London`) or a bare ISO offset (`+05:30`); without it the hours are counted in UTC, which puts a shop outside UTC at the wrong time of day. Only CONFIRMED and FULFILLED orders count. Hours with no trade are absent rather than returned as zero.
- `GET /admin/reports/deposits?from&to&storeId` — **container deposits (09.16):** deposits charged on sales that stand (cancelled and voided excluded) and refunded at the till over [from, to), by material, with the VAT inside the deposits where the scheme taxes them and the unredeemed difference. OWNER or MANAGER; `400 ORDER_REPORT_PERIOD_INVALID`.
- `GET /admin/reports/sales-by-staff?from&to&storeId&limit` — takings per cashier with average basket and discount rate, biggest taker first. Read from the POS transaction journal, so **in-store only** — an online order has no cashier, and these totals will not reconcile to the sales summary for that reason. `UNATTRIBUTED` buckets journal entries naming nobody.
- `GET /orders/{id}` — get an order with its line items.
- `POST /orders` with `awaitingPrice: true` (POS only) — a **catalog-mode till order** (SJ-D41): the goods are known, the prices are not. It is placed as `AWAITING_PRICE`, which the stranded-order sweeper never touches (it cancels `PENDING` orders whose last change is older than `shelfj.order.pending-sweeper.ttl-hours`), and waits for a manager. Refused for an online order (`400 ORDER_AWAITING_PRICE_POS_ONLY`).
- `POST /orders/{id}/price` `{lines:[{variantId, unitPrice}], taxAmount}` — a manager prices it: every line on the order must get a unit price of at least zero (`400 ORDER_PRICE_LINE_MISSING` / `ORDER_PRICE_LINE_UNKNOWN` / `ORDER_PRICE_INVALID`), the totals are recomputed, the history records "priced: total X", and the order becomes `PENDING` — payable at the till or via *Collect payment*, and swept as stranded only if it then sits unpaid past the TTL. Management-only; `409 ORDER_NOT_AWAITING_PRICE` for any other state. An `AWAITING_PRICE` order can also be cancelled.
- `POST /orders/{id}/confirm` — confirm an order (e.g. once payment settles). A **till sale** — channel `POS`, fulfilment `INSTORE` or `PICKUP` — is confirmed *and* handed over in the same transaction, emitting `OrderFulfilled` so its stock is deducted.
- `POST /orders/{id}/cancel` — cancel an order pre-fulfilment.
- `POST /orders/{id}/fulfil` — hand an order over, or part of it (SJ-D35). Without a body, everything still outstanding goes — for an untouched order the plain all-or-nothing fulfilment this always was. With `{lines:[{variantId, qty}]}`, only those quantities go now: each line keeps a cumulative `fulfilledQty`, the order is `PARTIALLY_FULFILLED` until every line is complete and then `FULFILLED`, the status history records "part-fulfilled: 4 of 5 units handed over", and each call emits one `OrderFulfilled` carrying only that call's quantities, so inventory-svc deducts what left the store now and nothing twice (its per-line dedupe is keyed by event, so several events per order are fine; a checkout hold that does not match a partial line is released and the deduction taken directly). Refused: more than is outstanding (`409 ORDER_FULFIL_QTY_EXCEEDS_OUTSTANDING`, saying how much is), a variant not on the order (`400 ORDER_FULFIL_LINE_UNKNOWN`), a zero or negative quantity (`400`), an order that is not `CONFIRMED`/`PARTIALLY_FULFILLED` (`409 ORDER_NOT_FULFILLABLE`), a caller without access to the order's store (`403`). A part-fulfilled order cannot be cancelled (`409 ORDER_PARTLY_FULFILLED` — return the goods or hand over the rest); a short close of the remainder is not built. For online and delivery orders; a till sale never needs it, because it is handed over whole when it is paid for.
- `GET /orders/{id}/history` — order status history/audit trail.
- `POST /orders/{id}/void` — void a completed POS sale (post-fulfilment correction, distinct from cancel). **Puts the stock back**: `OrderVoided` carries `eventId`, `storeId` and the lines to restock — each line net of anything already returned, and empty when the sale was never handed over, so nothing that was not deducted is restocked. Decided under a row lock on the order, and "handed over" is read from the append-only status history rather than the current status, which a refund would have moved on. **Management roles only**: the shared `AdminAuthorizationFilter` refuses a `CASHIER` or `STOREKEEPER` with `403` before the resource is reached; `ORDER_VOID_ONLY_POS` (409) for an online order, `ORDER_CANNOT_VOID` (409) for a sale already voided or cancelled. The void is recorded against the caller in `pos_void_log`, which the staff exception report reads. The admin Orders screen offers it as *Void sale* on a till sale that is still standing (09.13).
- `POST /orders/{id}/returns` / `GET /orders/{id}/returns` — create/list returns against an order (full or partial). With `recallNoticeId`, the return settles that recall notice as `REFUNDED` in the same transaction (05.10): 409 `RECALL_NOTICE_ORDER_MISMATCH` when the notice is about another order, 409 `RECALL_NOTICE_RESOLVED` when already settled, and in either case no return is recorded.
- `POST /orders/container-refunds` / `GET /orders/container-refunds/{id}` — **deposit return (09.16).** Empties brought back to the till: `{storeId, tillSessionId, lines:[{material, volumeMl, count}]}` with an `Idempotency-Key`; the scheme in force where the store trades (from tenant-svc's register) says which containers it takes back and for how much, and the refund is recorded with one line per kind and published as `ContainerDepositRefunded`, which payment-svc books as a `PAY_OUT` on the till session once. `400 ORDER_CONTAINER_NOT_IN_SCHEME` for a container the scheme does not take back, `ORDER_CONTAINER_LINES_INVALID` for none or more than 20 kinds, `ORDER_CONTAINER_COUNT_TOO_MANY` past 500 of a kind or 2,000 in all, `MISSING_IDEMPOTENCY_KEY`; `409 ORDER_DEPOSIT_SCHEME_NOT_IN_FORCE` where no scheme is in force. A retry with the same key returns the first refund. CASHIER, MANAGER or OWNER.
- **Deposits on the sale (09.16):** `POST /orders` puts the return-scheme deposit on each item sold in a container the scheme covers — by the `depositMaterial`/`depositVolumeMl` product-svc records — as its own line (`deposits[]`: material, volume, qty, `depositEach`, `amount`, `vatTreatment` `OUTSIDE_SCOPE` or `STANDARD`, `vatRate`/`vatAmount`, `schemeScope`, `citation`) with `depositAmount` added to `total` and no part of `subtotal`, `taxAmount` or any discount. The UK deposit is outside the scope of VAT (VATA 1994 ss.55B–55D); Germany's Pfand is taxed as the drink (VerpackG §31), the VAT inside it shown on the line.

### Recall notices to buyers (`/orders/recall-notices`)
A recall's notice to the buyer of one order (05.10; GPSR (EU) 2023/988 arts.35–37: a direct written notice to every consumer who can be identified, saying what art.36 lists, and a remedy the consumer chooses under art.37). inventory-svc finds the sales that drew on a recalled pack and publishes `RecallSaleAffected` per order; this service knows who placed the order — the login, the shop's customer record, or a phone number the buyer left at checkout — and issues the notice: `recall_notices` (one per recall and order; the recall's text, remedies and contact as they stood, so what the buyer was told never changes under them) and append-only `recall_notice_lines`. `status` is `ISSUED` (someone to tell, and told), `UNIDENTIFIED` (an anonymous till sale, kept for the count and for the buyer who comes back with the receipt), `REMEDY_CHOSEN` or `RESOLVED`. An `ISSUED` notice publishes `RecallNoticeIssued`, which notification-svc writes to the buyer. The consumer is idempotent on the event and on (recall, order); a withdrawal, a malformed event and an order this service never saw are skipped. The buyer's phone never leaves the service and is forgotten with the customer's erasure; `buyerIdentified` — whether the order named anyone to write to — is fixed when the notice is issued (V29), so settling an anonymous sale at the counter never counts as a buyer told.
- `GET /orders/recall-notices/mine` — the signed-in shopper's own notices, newest first, keyed on the token's login like `/orders/mine` (401 `NO_CUSTOMER` without one). This and `POST /orders/recall-notices/{id}/remedy` are the two shapes the gateway's storefront whitelist and common-web's read/mutation allowlists open to a customer token with `X-Storefront-Tenant`; nothing else under `/orders/recall-notices` is. Each carries the headline material: reference, hazard, reason, `customerNotice`, `remedies`, `singleRemedyReason`, `contactPhone`/`contactUrl`, the order and when it was sold, and `lines` with `productName`, `sku`, `batchNo`, `expiryDate`, `qty` and `match`.
- `POST /orders/recall-notices/{id}/remedy` — `{ remedy }`. The shopper chooses on a notice issued to their login (any other notice is 404, so ids cannot be probed); staff choose for a buyer at the counter on any notice of the business (`remedyChosenVia` `SHOPPER|STAFF`). Once: 409 `RECALL_REMEDY_ALREADY_CHOSEN`; only what was offered: 409 `RECALL_REMEDY_NOT_OFFERED`; not once settled: 409 `RECALL_NOTICE_RESOLVED`. Twenty at once record one.
- `GET /orders/recall-notices?recallId&status&after&limit` — a recall's notices, newest first, cursor-paginated. Staff only.
- `GET /orders/recall-notices/progress?recallId` — `notices`, `identified`, `unidentified`, `remedyChosen`, `resolved`, and `chosen` per remedy. Staff only.
- `POST /orders/recall-notices/{id}/resolve` — `{ resolution: REPLACED|REPAIRED|DECLINED, notes }`. Staff only. A remedy nobody had chosen is recorded as the one the settlement implies. `REFUNDED` is refused here (400 `RECALL_REFUND_THROUGH_RETURN`): a refund is a return of the order naming the notice, so the goods, the money and the notice settle together — and the returned pack is held on arrival by the open recall.
- Publishes: `RecallNoticeIssued` (the notice's text and offer, the order, and the ids an address is resolved from: `customerId`, `loginId`, `buyerPhone`).
- Consumes: `RecallSaleAffected` (inventory-svc).

### POS Operations
- `POST /pos/parked-sales`, `GET /pos/parked-sales`, `GET /pos/parked-sales/{id}`, `DELETE /pos/parked-sales/{id}` — park (suspend), list, get, or cancel an in-progress POS sale so a cashier can serve another customer and resume later.
- `POST /pos/no-sale` — log a no-sale/open-drawer event.
- `POST /admin/pos-log/orders/{orderId}` — record the POSLog transaction-journal entry for a fulfilled POS order.
- `GET /admin/pos-log`, `GET /admin/pos-log/orders/{orderId}` — list the POS transaction journal, tenant-wide or per order.

- `POST /admin/orders/{orderId}/receipts`, `GET /admin/orders/{orderId}/receipts` — log/list receipt generation events. `receiptType` records how the receipt came out: `PRINT` (the browser's dialog), `THERMAL` (ESC/POS to a receipt printer, 09.12), `SAVE` (kept as a file), `EMAIL` (sent; `emailedTo` required). The frontend renders the receipt itself.

### Alternative Sale Types
- `POST /gift-cards` — issue a gift card. `GET /gift-cards/{code}` — look one up. `POST /gift-cards/{code}/reload` — top up balance. `POST /gift-cards/{code}/redeem` — spend from balance; **idempotent per `orderId`** (a repeat redemption against the same order returns the card unchanged rather than deducting twice, matching how a `STORE_CREDIT` tender is keyed in payment-svc). A redemption sent without an `orderId` is a manual adjustment and is not deduplicated. `GET /gift-cards/{code}/transactions` — transaction history. **Issuing and reloading say how the value was paid for (17.11):** `POST /gift-cards` `{storeId, amount, currency?, expiresAt?, paidBy}` and `POST /gift-cards/{code}/reload` `{amount, reference?, paidBy}`, where `paidBy` is `CASH`, `CARD`, `UPI` or `WALLET`, or `PROMOTIONAL` for value given away; missing is `400`, and another gift card, a voucher, store credit or anything else is `400 GIFT_CARD_PAID_BY_INVALID` — stored value bought with stored value would only move a liability. Each issue and reload publishes `GiftCardLoaded` (`shelfj.order.gift-card-loaded`: card, transaction, kind, amount, currency, paidBy, store) with the card write, which purchase-svc posts against the gift card liability.
- `POST /layaways` — create a layaway (reserve goods against installment deposits). `GET /layaways/{id}` — get with items/deposits. `POST /layaways/{id}/deposits` — record a deposit. `POST /layaways/{id}/complete` — final payment received, hand over goods. `POST /layaways/{id}/cancel` — cancel.
- `POST /admin/special-orders` — create a special order (customer order for future delivery, no immediate stock deduction). `GET /admin/special-orders`, `GET .../{id}` — list/get. `POST .../{id}/confirm`, `.../fulfil`, `.../cancel` — lifecycle actions.

**Business rules**
- Placing an order requires an `Idempotency-Key` (rejected with 400 otherwise) — the one hard requirement across the whole surface.
- `POS` channel orders require a `CASHIER`/`MANAGER`/`OWNER` role; `ONLINE` orders need no staff role — but the gateway only forwards order placement for a verified, signed-in customer token (there is no anonymous guest checkout). Only an `ONLINE` order is the caller's own: it carries their `loginId` and the customer record customer-svc links to it (SJ-D44). A `POS` sale names its customer only through `customerId`, whatever roles the cashier's token carries — every staff login carries `CUSTOMER` too, and linking on the role alone filed anonymous till sales under the cashier's own record (SJ-D59).
- Special orders deliberately skip immediate inventory deduction, unlike regular POS/online orders.
- Void, cancel, and return are three distinct lifecycle actions: void corrects a completed sale, cancel stops an unfulfilled order, return is a post-sale reversal.
- **A till sale is handed over the moment it is paid for (SJ-D40).** The capture that completes it moves it `PENDING → CONFIRMED → FULFILLED` in one transaction and writes `OrderFulfilled` alongside `OrderConfirmed`. Before this, inventory-svc deducted stock only on `OrderFulfilled` and nothing ever fulfilled a till sale — the till places the order, payment capture confirmed it, and there it stopped. Stock moved only if a manager later opened each sale and clicked *Mark fulfilled*. `PICKUP` counts as a till sale as well as `INSTORE` because the till sent `PICKUP` for every tendered sale until the fix, and sales already queued offline replay with it. `DELIVERY` is not: goods leaving on a van are handed over when they arrive. A partial tender or a redelivered capture writes nothing, so a sale is fulfilled — and deducted — exactly once.
- The POS stock-position projection is explicitly documented as eventually consistent and must not be used to make reservation decisions.

- **A customer this shop erased keeps their delivery details only until an open order finishes (SJ-D43).** `CustomerErased` redacts a settled order's contact/delivery fields and any parked-sale/special-order name at once; an order still in flight is left alone until it reaches a settled state (fulfilled, cancelled, voided, refunded) and is caught by an hourly sweep — the address is still needed to deliver it. The sale record itself (amounts, tax, lines) is never touched; only what identifies the customer is.

**Events**
- Consumes: `StockReceived`, `StockDeducted`, `StockAdjusted` (feeds the POS stock-position projection), `PaymentCaptured`, `PaymentFailed`, `PaymentRefunded` (order confirmation/refund status), `StoreStatusChanged`, `TenantStatusChanged`, `CustomerErased` (SJ-D43).
- Publishes: `OrderPlaced`, `OrderConfirmed`, `OrderCancelled`, `OrderFulfilled`, `OrderReturned`, `OrderVoided`, `LayawayCreated`, `LayawayCompleted`, `LayawayCancelled`.

### Fiscal receipts (`/admin/fiscal-receipts`)

A **gapless legal receipt sequence** — required by fiscal law in Italy, Germany (KassenSichV), Portugal, Poland, Brazil and India, and required to be demonstrable to an inspector. Distinct from `/admin/orders/{id}/receipts`, which logs how many times a document was printed or emailed; this is the document itself.

- `POST /admin/orders/{orderId}/fiscal-receipt?series=` — issue the numbered receipt. **Normally unnecessary**: the number is taken automatically when the sale completes — by the payment capture that completes a till sale, or by `confirm`. (The first version hooked only `confirm`, which the till never calls, and so numbered almost no till sales.) This is the recovery path for a sale that completed while issuance was failing, and it is idempotent — a second call returns the number already issued, because a reprint is not a sale and two numbers for one sale is how a day's takings get counted twice. Refused for a `PENDING` or `CANCELLED` order (`ORDER_NOT_SELLABLE`): numbering a basket that is never paid for is where gaps come from.
- `GET /admin/orders/{orderId}/fiscal-receipt` — the number, when it was issued, and whether the sale was later voided.
- `GET /orders/{orderId}/fiscal-receipt` — the same, authorized like the order it belongs to: any staff member, or the customer who placed it. In practice a staff read today: a signed-in customer's token carries no tenant, and the gateway derives one only for its storefront paths, which include `/orders/mine` but no read by id. The authorization filter runs at the gateway as well as in order-svc, so both had to be redeployed for this path to be reachable. This is what the till reads to print the legal number — the admin route above is management-only, so a cashier could never reach it. The number is issued when the payment that completes the sale reaches order-svc, so for a few seconds after a sale this answers `404 ORDER_RECEIPT_NOT_ISSUED`. **`?wait=N`** holds the request up to N seconds (capped at 20) for the number to be issued, so the till prints with the number after one round trip instead of polling and giving up; before payment lands a bounded wait still ends in `404`, and the cap is tested — asking for an hour gets twenty seconds. A customer who did not place the order gets the same `404`, at once.
- `GET /admin/fiscal-receipts/series?storeId=` — the counters a store runs: series code, fiscal period, the next number it will hand out, and the prefix it prints. Management-only; a cashier gets `403`, another tenant an empty list.
- `PUT /admin/fiscal-receipts/series` `{storeId, seriesCode, period, prefix}` — what is printed in front of the number, e.g. `GB-LDN-01` → `GB-LDN-01-2026-000042`. Opens the series if it is new. **The counter is never touched**: a prefix change affects the documents issued after it, and every document already issued keeps the full number it was printed with — the test issues under `OLD`, changes to `NEW`, and checks the count runs 1, 2. Prefix is letters, digits and hyphens, at most 16, upper-cased (`RECEIPT_PREFIX_INVALID`); period is a year, `2026` or `2026-04` (`RECEIPT_PERIOD_INVALID`); a refusal opens nothing. Management-only.
- `GET /admin/fiscal-receipts?storeId=&series=&period=` — the register, by number. `series` defaults to `MAIN`, `period` to the current fiscal year.
- `GET /admin/fiscal-receipts/export?storeId=&series=&period=&format=csv|json` — the register as a file (18.4): every document in number order with `prevHash` and `hash`; JSON adds the order lines behind each document. The in-repo input an accountant or a SAF-T / KassenSichV / corrispettivi export needs; **not itself a certified file** — those need a tax-authority signing key, a certified TSE, or an SDI channel this repo cannot supply. Management-only.
- `GET /admin/fiscal-receipts/settings?storeId=` / `PUT /admin/fiscal-receipts/settings` `{storeId, regime, taxRegistrationNumber, certificateNumber, seriesValidationCode, tseProvider, tseTssId, tseClientId}` — **the fiscal regime a store trades under (18.5)**, behind a seam the way payments are: `NONE` (the register alone, every store's start), `DE_KASSENSICHV` (every sale is a transaction a security module signs — §146a AO, KassenSichV §2/§6; the receipt prints the module's serial, transaction number, signature counter, start and end, signature and the DSFinV-K QR; an outage is recorded on the document, which is what `TSE_TA_FEHLER` is for) or `PT_SAFT` (every document carries an RSA-SHA1 signature over `InvoiceDate;SystemEntryDate;InvoiceNo;GrossTotal;PreviousHash` per Despacho 8632/2014, computed under the same lock as its number so the chain is as gapless as the numbers; the receipt prints characters 1, 11, 21 and 31 and "Processado por programa certificado n.º NNNN/AT"). The read returns what the deployment offers beside the settings: the regimes deployed, the module providers configured (`SIMULATED` always — a module in software whose key lives in `tse_devices`, which is exactly why it is not certified; `CLOUD` when `shelfj.fiscal.tse.cloud.api-key/api-secret` are set — a fiskaly-shaped REST module whose certificate covers the signing), and whether the Portuguese signing key (`shelfj.fiscal.pt.private-key`) is installed. What each regime refuses, by code: `FISCAL_REGIME_UNKNOWN`, `FISCAL_TAX_NUMBER_REQUIRED`, `FISCAL_TSE_REQUIRED`, `FISCAL_TSE_PROVIDER_UNKNOWN`, `FISCAL_TSE_CLIENT_ID_INVALID`, `FISCAL_TSE_ID_REQUIRED`, `FISCAL_TSE_CLOUD_NOT_CONFIGURED` (409), `FISCAL_NIF_INVALID` (mod-11 check), `FISCAL_SERIES_CODE_INVALID`, `FISCAL_PT_KEY_NOT_CONFIGURED` (409), `STORE_NOT_OPERATIONAL` (409, another tenant's store). A refusal stores nothing. Documents already issued keep the stamps they were issued with; the change applies from the next sale, and the audit's hash chain covers the stamp (a swapped device signature breaks it at that document). Management-only; another tenant reads its own unset view of the store id.
- `GET /admin/fiscal-receipts/export?…&format=dsfinvk|saft-pt` — **the inspector's file for the regime (18.5).** `dsfinvk` is the German DSFinV-K 2.3 zip: `cashpointclosing`, `location`, `cashregister`, `tse`, `vat`, `businesscases`, `payment`, `transactions`, `transactions_tse`, `transactions_vat`, `lines`, `lines_vat`, `datapayment` and the GDPdU `index.xml` describing them — semicolon-separated, decimal comma, CRLF, one cash-point closing per day the store traded (this register has no separate end-of-day document, so the day is the closing); not written: the tables for agencies, vouchers, sub-items, allocation groups and references, which this register has nothing to put in. `saft-pt` is the Portuguese SAF-T (PT) 1.04_01 sales-invoice file: header, the final consumer (NIF 999999990), the products the lines name, the tax table, and every `Invoice` with its `Hash`, `HashControl`, `ATCUD` (the AT series validation code joined to the number; `0-n` until the series is registered), lines by rate and the payment mechanism. Both name the business as tenant-svc holds it (legal name via `GET /admin/tenant`, the store's address via `GET /admin/stores/{id}`, the caller's identity forwarded) and the products as product-svc names them, and refuse with `503 FISCAL_EXPORT_DEPENDENCY_UNAVAILABLE` rather than write a file naming nobody. Lines carry `vat_amount` since 18.5 (what the quote priced; apportioned from the order's tax when a line was placed with pricing enforcement off), so both files list the sale by rate. **What is code and what is not:** the German module's certificate and the Portuguese producer's certification are market gates a deployment passes with configuration — the cloud provider's credentials, the AT-issued key and certificate number — not with code; the software half of each, including the file an inspector reads, is here and driven live in `k6/compliance-flow`.
- `GET /admin/fiscal-receipts/audit?storeId=&series=&period=` — **the inspector's question, answered by the database rather than by assertion.** Returns the first and last numbers, how many were issued, how many the span implies, and every gap with its range. `intact: true` with an empty `gaps` array is the proof. Since 18.4 the same call gives a second, independent verdict: every document issued carries a SHA-256 over its own figures and the hash of the document before it (`prevHash`, `GENESIS` for the first), and the audit re-derives every hash in the series — `chainIntact`, `chainFrom` (documents issued before the chain existed are passed over), `chainBrokenAt` (the first document whose stored figures no longer match). A missing number and an altered figure are different findings, and now each has its own line. Contiguous holes come back as one gap with a range, because "2 to 3" is what gets explained, not two separate findings.

**Why not a Postgres `SEQUENCE`.** Sequences deliberately do not roll back: two transactions take 41 and 42, the first aborts, and 41 is gone forever. That is right for a surrogate key and wrong for a legal document, where the missing number is exactly what an inspector asks about. The counter is a row updated with `UPDATE … RETURNING` inside the sale's own transaction, so a rollback puts the number back and concurrent tills serialise on the row lock. That trade — concurrency for gaplessness — is the one every fiscal system makes, and a test drives eight tills at once to prove it holds.

**A voided sale keeps its number**, marked void with a reason. Deleting or renumbering it would close the hole, and closing the hole is the trick the numbering exists to expose: ring the sale, take the cash, void the receipt, and a till that balances hides a theft.

Numbering restarts per `period` (fiscal year) and runs per `(store, series)`, so a jurisdiction that numbers per till — Italy does — uses one series per device.

## payment-svc

### Invoices and credit notes to business buyers (`/admin/sales-invoices`)
**18.9.** A sale to a customer recorded as a VAT-registered business is owed an invoice — in Belgium, France, Poland and (from 2027) Germany a structured EN 16931 one, in India one reported to the Invoice Registration Portal, in the UK a full VAT invoice on request — and the till's receipt is not it: it names no buyer and is numbered per store. Issued **without anyone asking** when the sale completes (on `PaymentCaptured` for a till sale, on `POST /orders/{id}/confirm` otherwise), in the background so the till never waits on four services; and again for a return, as a credit note. The business is named as tenant-svc's identity holds it (`legalName`, `vatNumber`, `einvoiceScheme`/`einvoiceId`) at the store's address; the buyer as pricing-svc's `customer-vat-status` records it (`legalName`, `vatNumber`, `countryCode`, `reverseChargeEligible`, its e-invoicing address) at its customer-svc `BILLING` address (else its default); every line at the rate its quote applied (`order_items.vat_code`/`vat_rate`, recorded at placement), named as product-svc names it, with its HSN code. Numbered gaplessly per series and calendar year (`INV/2026/000001`, `CRN/2026/000001`; short enough for the IRP's 16 characters) from `sales_invoice_series`, moved under its row lock inside the issuing transaction: a refusal gives its number back, and ten requests at once for one sale answer with one document. The document is checked against EN 16931 — and Peppol BIS Billing 3.0 when both parties have a network address and the order is referenced — before its number is kept, and stored as the UBL issued; CII and Factur-X are written from it on request. A till discount is taken off what the customer pays, VAT included, after the tax was worked out; the invoice states it **net** (`SalesInvoiceDraft.netDiscount`), as an allowance on every rate it came off, so the VAT follows what was actually paid and the document comes to exactly what the sale charged — a sale whose recorded tax does not follow from its lines' rates is refused rather than made to look as if it did. An Indian business's document is also written as the IRP's INV-01 v1.1 (CGST+SGST within a state, IGST across; discounts spread into the lines, since the portal takes no document allowance), or kept with what the portal would refuse.
- `POST /admin/orders/{orderId}/invoice` — issue the invoice by hand, or read back the one issued: idempotent. `404 ORDER_NOT_FOUND`; `409 ORDER_INVOICE_NOT_SOLD` (a basket never paid for), `ORDER_INVOICE_NO_BUYER`, `ORDER_INVOICE_BUYER_NOT_REGISTERED`, `ORDER_INVOICE_BUYER_NOT_FOUND`, `ORDER_INVOICE_BUYER_ADDRESS_MISSING`, `ORDER_INVOICE_SELLER_VAT_MISSING`, `ORDER_INVOICE_SELLER_NAME_MISSING`, `ORDER_INVOICE_STORE_NOT_FOUND`, `ORDER_INVOICE_TOTALS_DIFFER`, `ORDER_INVOICE_NOT_COMPLIANT` (the rules broken in `details`); `503 ORDER_INVOICE_DEPENDENCY_UNAVAILABLE` when pricing-svc, customer-svc, product-svc or tenant-svc could not be reached — the document can be issued once it is. Management-only, like everything under `/admin`.
- `GET /admin/orders/{orderId}/invoices` — the sale's invoice and credit notes, newest first; empty when never invoiced.
- `POST /admin/returns/{returnId}/credit-note` — credit a return against an invoiced sale, by hand or read back: the returned goods at the rates they were sold at, the invoice named as the preceding document (BG-3). `404 ORDER_RETURN_NOT_FOUND`; `409 ORDER_CREDIT_NOTE_NO_INVOICE`.
- `GET /admin/sales-invoices?after=&limit=` · `GET /admin/sales-invoices/{id}` — the register, newest first, cursor-paged on `(issued_at, id)`; one document's facts (`kind`, `fullNumber`, amounts, `peppol`, the `formats` it offers, its `irpProblems`). Another tenant's is `404`.
- `GET /admin/sales-invoices/{id}/document?format=UBL|CII|FACTURX|IRP` — the file, with `Content-Disposition` (named by the number), `nosniff` and `no-store`: the UBL as issued (default), the same document as CII, a Factur-X PDF/A-3, or the INV-01 JSON. `400 ORDER_INVOICE_FORMAT_UNKNOWN`; `404 ORDER_INVOICE_IRP_NOT_APPLICABLE` outside India; `409 ORDER_INVOICE_IRP_NOT_READY` with the portal's objections in `details`. Sending over a network (Peppol access point, France's PDP, Poland's KSeF, the IRP itself) is the transport seam, not built yet.

### Where e-invoices leave (`/admin/einvoicing/transport`, the transport seam)
**The seam behind 07.13 and 18.9.** An EN 16931 document is only the format; the mandates name a network. A business chooses one — `PEPPOL` (an access point: Belgium now, Germany 2027, the UK 2029), `FR_PDP` (France's approved platform), `KSEF` (Poland), `IRP` (India) — and the provider behind it: `SIMULATED` on every network (the platform stands in for the network and nothing leaves it; a receiver whose identifier contains `REJECT` is refused as unknown, one containing `LATER` is taken and answered when asked after), or a real one once the deployment holds its credentials, each deployed always and choosable only configured: the Peppol `ACCESS_POINT` (the HTTP facade certified providers put in front of AS4: `shelfj.einvoice.peppol.base-url`, `.api-key`), France's approved platform `PDP` (`shelfj.einvoice.fr-pdp.base-url`, `.api-key`; the document deposited with the business's SIREN as its account and the buyer's directory address, its life read back as the reform's statuses — 200 déposée and 201 émise on their way, 210 refusée by the buyer and 213 rejetée by the platform final, every other status with the buyer's platform), and India's `NIC` portal (`shelfj.einvoice.irp.base-url`, `.client-id`, `.client-secret`, `.public-key`; the business signs in as the taxpayer with its portal user as its account and its password as its **secret** — the password and a fresh AppKey sealed under the portal's RSA key, the session key back sealed under the AppKey, the INV-01 AES-sealed with it, and the IRN, acknowledgement, signed invoice and QR code back the same way; an invoice already registered is registered with the portal's own IRN; wrong credentials are refused, not retried). A provider's credential (`providerSecret`) is kept sealed under the deployment's `shelfj.einvoice.secrets-key` (AES-GCM) and never shown; `hasSecret` says one is kept, leaving it out keeps it, blank removes it; `409 EINVOICE_SECRETS_KEY_MISSING` on a deployment with no key, `409 EINVOICE_PROVIDER_SECRET_REQUIRED` for a provider that signs in without one. Poland's `KSEF` (KSeF API 2.0, `shelfj.einvoice.ksef.base-url`; the business's KSeF token as its **secret**, its NIP from its VAT number): KSeF alone takes no EN 16931 document, so the invoice as issued is read back and written as **FA(3)** (`shared/einvoice` `Fa3`: the header naming schema FA (3) 1-0E, Podmiot1 by NIP, Podmiot2 by NIP, EU VAT number or none, the totals per rate bucket P_13_x/P_14_x, the annotations, VAT or KOR naming the corrected invoice, one FaWiersz per line with its rate as the schema spells it — 23, 8, 5, 0 KR, zw, oo, np I — and a document allowance spread over its lines as P_10; a credit note's lines are the differences, negative; `Fa3.check` refuses what KSeF would: a seller without a valid NIP, a rate Poland has not); the token is sealed with the challenge's timestamp under the ministry's RSA-OAEP key, the access token opens an interactive session whose AES key is sealed under the ministry's other key, the FA(3) goes in AES-256-CBC-encrypted with its hashes and sizes, the session is closed, and the system is asked after by session and invoice reference until it gives the KSeF number (`ACCEPTED`, the reference becoming the number), refuses (4xx with its description and details, final), reports a duplicate (its number) or fails on its own side (5xx, asked again). A contract with a certified provider is not code. **Delivery in** is the other half of the seam: a network delivers a supplier's document to purchase-svc's `POST /e-invoices/inbound/{network}` (below), and on the simulated network, delivered means delivered — when the deployment holds `shelfj.einvoice.inbound.key`, the simulated provider hands every document it takes to that route as an access point would, so a receiver that is a business on this platform finds it in its inbox (`ACCEPTED`, "delivered into the receiver's inbox on this platform", the inbox's receipt kept in the attempt's `response`), a receiver nobody here holds is delivered the simulated way (`ACCEPTED`, "no business on this platform holds …"), an inbox that cannot be reached or refuses the key is a network that is down (tried again later), and an inbox that refuses the document is a refusal with its reason. Every document issued while a network is chosen is queued (`sales_invoice_transmissions`) and sent by a worker (every 15 s, `shelfj.order.einvoice-transport.*`) that takes due rows under `SKIP LOCKED`; a network that could not be reached is tried again, later each time (30 s doubling, an hour at most, 8 attempts, then `FAILED`); a network that took the document but has not answered is asked after (`PENDING`); a network that refused is `REJECTED` for good, until someone sends the document again by hand. The database holds one open or delivered attempt per document, so ten sends at once send once.
- `GET /admin/einvoicing/transport` — the settings: `network`, `provider`, `providerAccount`, the business's `senderAddress`, `suggestedNetwork` (what tenant-svc's obligations say the business's country asks for today), the `networks`, the `providers` deployed per network and the `available` ones (configured). Management-only.
- `PUT /admin/einvoicing/transport` `{network, provider, providerAccount, providerSecret}` — choose; `NONE` clears. The response also lists the providers `needingSecret`, by network. `400 EINVOICE_NETWORK_UNKNOWN`, `EINVOICE_PROVIDER_REQUIRED`, `EINVOICE_PROVIDER_UNKNOWN`, `EINVOICE_PROVIDER_ACCOUNT_INVALID`; `409 EINVOICE_PROVIDER_NOT_CONFIGURED`, `EINVOICE_SENDER_ADDRESS_MISSING` (Peppol without the business's own electronic address).
- `GET /admin/sales-invoices/{id}/transmissions` — every attempt for a document, newest first; `POST /admin/sales-invoices/{id}/transmissions` — send now, the first time or again after a refusal; the answer is the attempt with what the network said (`ACCEPTED`, `REJECTED` with `detail`, `PENDING`). `409 EINVOICE_TRANSPORT_NOT_SET`, `EINVOICE_ALREADY_SENT`, `EINVOICE_RECEIVER_ADDRESS_MISSING`, `EINVOICE_PROVIDER_UNKNOWN`. The document itself (`GET /admin/sales-invoices…`) carries its newest `transmission`.
- `GET /admin/einvoicing/transmissions?status=&after=&limit=` — the outbox, newest first, cursor-paged; `400 EINVOICE_TRANSMISSION_STATUS_UNKNOWN`.

### Chargebacks (`/admin/disputes`, 11.9)
OWNER or MANAGER throughout.
- `GET /admin/disputes?status=&storeId=&after=&limit=` — the register, newest first. `status` is `NEEDS_RESPONSE`, `UNDER_REVIEW`, `WON`, `LOST` or `ACCEPTED` (`400 DISPUTE_STATUS_UNKNOWN`). Each row says `overdue` when an answer is still owed past its date.
- `POST /admin/disputes` — record a chargeback the acquirer has told the business about, for a card taken on a terminal the platform does not talk to: `{paymentId, amount?, feeAmount?, currency?, reason, networkReasonCode?, caseReference, evidenceDueBy, fundsWithdrawn?}` with an `Idempotency-Key` (a retry is the same chargeback). `404 PAYMENT_NOT_FOUND`; `409 DISPUTE_NOT_DISPUTABLE` (only a captured card, UPI or wallet tender), `DISPUTE_ALREADY_OPEN` (one open dispute per payment); `400 DISPUTE_AMOUNT_EXCEEDS_PAYMENT`, `DISPUTE_DUE_DATE_PAST`, `DISPUTE_REASON_UNKNOWN`. A payment provider's own disputes arrive on `POST /payments/webhooks/{provider}` and are never recorded this way.
- `GET /admin/disputes/{id}` — the dispute with its append-only history (`OPENED`, `FUNDS_WITHDRAWN`, `EVIDENCE_SUBMITTED`, `WON`/`LOST`/`ACCEPTED`, `FUNDS_REINSTATED`) and the answer given.
- `POST /admin/disputes/{id}/evidence` — the business's answer: `{productDescription?, customerName?, customerEmail?, receiptReference?, fulfilmentProof?, customerCommunication?, refundPolicy?, notes?}`. Once, and not after its date: `409 DISPUTE_NOT_AWAITING_RESPONSE`, `DISPUTE_EVIDENCE_LATE`; `400 DISPUTE_EVIDENCE_EMPTY`. A provider's dispute is sent to the provider and submitted (`502 PAYMENT_PROVIDER_REFUSED` if it will not take it); the acquirer's is kept here and sent by the business.
- `POST /admin/disputes/{id}/accept` — not contested: lost by the business's own decision. `409 DISPUTE_CLOSED`.
- `POST /admin/disputes/{id}/resolve` `{outcome: WON|LOST, note?}` — how a dispute the acquirer told the business about ended. `409 DISPUTE_DECIDED_BY_PROVIDER` for a provider's dispute, `DISPUTE_CLOSED`; `400 DISPUTE_OUTCOME_UNKNOWN`.
- `GET /admin/disputes/summary?from=&to=&storeId=` — opened, by standing, amounts disputed and lost, fees, the card payments of the period, `disputeRatio` and `aboveMonitoringThreshold` (0.9%, where the card schemes start monitoring a merchant).

### Settlement reconciliation (`/admin/settlements`, 11.10)
OWNER or MANAGER throughout. The gateway gives `POST /admin/settlements` its own 6 MB body cap; a file carrying a full card number is refused there (`400 CARD_DATA_NOT_ACCEPTED`) like any other request.
- `POST /admin/settlements` — import one payout's file: `{provider, format, reference?, payoutDate?, currency?, declaredNet?, storeId?, content}`. `format` is one of `GET /admin/settlements/formats` (`SHELFJ`, `STRIPE`, `ADYEN`). What the file says about itself — payout number, date, currency, the sum paid — wins over what is typed; `SHELFJ` says none of it, so `reference` and `payoutDate` are needed. Takes an `Idempotency-Key`. `201` with the batch: `RECONCILED` when every line matched, else `EXCEPTIONS` with `openExceptions`. `400 SETTLEMENT_FORMAT_UNKNOWN`, `SETTLEMENT_FILE_WRONG_LAYOUT`, `SETTLEMENT_FILE_INVALID` (says which line), `SETTLEMENT_FILE_MANY_PAYOUTS`, `SETTLEMENT_REFERENCE_MISSING`, `SETTLEMENT_PAYOUT_DATE_MISSING`/`_INVALID`, `SETTLEMENT_CURRENCY_MIXED` (not the business's currency, or a converted line), `SETTLEMENT_OUT_OF_BALANCE` (the lines do not add up to `declaredNet`), `SETTLEMENT_STORE_UNKNOWN`; `409 SETTLEMENT_ALREADY_IMPORTED`; `413 PAYLOAD_TOO_LARGE`.
- The `SHELFJ` layout: CSV columns `type, reference, original_reference, gross, fee, net, occurred_at` (`fee`, `net`, `original_reference`, `occurred_at` optional). `type` is `SALE`, `REFUND`, `CHARGEBACK`, `CHARGEBACK_REVERSAL`, `FEE` or `ADJUSTMENT`; amounts are signed from the business's side — a refund or a chargeback is negative — and `net = gross - fee`.
- `GET /admin/settlements?status=&after=&limit=` — payouts, the newest import first; `status` is `EXCEPTIONS`, `READY` or `RECONCILED` (`400 SETTLEMENT_STATUS_UNKNOWN`).
- `GET /admin/settlements/{id}?open=&after=&limit=` — the batch with a page of its lines in file order (`limit` ≤ 500); `open=true` keeps to the lines waiting for a decision. Each line: `type`, `reference`, `gross`, `fee`, `net`, `matchStatus` (`MATCHED`, `UNMATCHED`, `AMOUNT_MISMATCH` with `expectedAmount`, `DUPLICATE`, `NOT_APPLICABLE` for a fee), what it matched (`tenderId` / `refundId` / `disputeId`), and the decision on it (`resolution`, `resolvedBy`, `resolvedAt`, `note`).
- `POST /admin/settlements/{id}/lines/{lineId}/resolve` `{resolution, targetId?, note?}` — `MATCHED_BY_HAND` (needs `targetId`: the payment for a sale, the refund, or the dispute; the sums must agree), `DIFFERENCE_ACCEPTED` (keeps the link, or takes `targetId`; needs `note`), `UNALLOCATED` (lets go of any link; its money goes to unallocated receipts; needs `note`). May be changed until the batch is reconciled. Answers the batch with its open lines. `404 SETTLEMENT_TARGET_NOT_FOUND` (not there, another business's, or cash); `409 SETTLEMENT_ALREADY_SETTLED`, `SETTLEMENT_AMOUNT_DIFFERS`, `SETTLEMENT_NOTHING_TO_ACCEPT`, `SETTLEMENT_LINE_NOT_AN_EXCEPTION`, `SETTLEMENT_RECONCILED`; `400 SETTLEMENT_TARGET_REQUIRED`, `SETTLEMENT_NOTE_REQUIRED`, `SETTLEMENT_RESOLUTION_UNKNOWN`.
- `POST /admin/settlements/{id}/reconcile` — sign a `READY` batch off; the ledger is told in the same transaction. `409 SETTLEMENT_HAS_EXCEPTIONS`, `SETTLEMENT_RECONCILED`.
- `GET /admin/settlements/unsettled?olderThanDays=&storeId=&after=&limit=` — captured card, UPI and wallet payments no settlement line has, the oldest first, with `daysOutstanding` (`olderThanDays` 0–365, 3 when absent).
- Publishes `SettlementReconciled` → `shelfj.payment.settlement-reconciled`.

### Tender Mix (`/admin/reports`)

Refunds are subtracted **within their own method** rather than netted globally — a card sale refunded to store credit is not a zero-card day, and the split is what a merchant statement reconciles against. `shareOfNet` is null when the window's total is zero or negative, where a percentage would be misleading rather than merely odd.

## pricing-svc

### Pricing (`/price-lists`, `/admin/price-lists`, `/admin/price-overrides`, `/prices`)

**Writes are management-only, reads are not.** Setting a price used to sit on `/price-lists`, outside `/admin/`, where `AdminAuthorizationFilter`'s mutation tier asks only for *some* staff role — so a CASHIER could create a price list and set what customers are charged (proved against the running stack: 201). The writes moved under `/admin/`; the reads stayed, because the POS and storefront need them and neither runs as management.

- `POST /admin/price-lists` — create a price list. `effectiveFrom` is an **ISO-8601 instant** (`2026-01-01T00:00:00Z`); the column is `TIMESTAMPTZ` and a bare date is refused with `INVALID_DATE`.
- `POST /admin/price-lists/{id}/items` — set a single variant's price on a list.
- `POST /admin/price-lists/{id}/items/batch` — set many variants' prices in one call (partial-failure tolerant).
- `POST /admin/price-lists/{id}/deactivate` · `POST /admin/price-lists/{id}/activate` — switch a price list off or on, `{"reason": "..."}` **required in both directions**. `409 PRICING_ALREADY_IN_STATE` if it is already in that state, so two people stopping the same list are not both told they did it. The resolve query filters on `active`, so a stopped list stops setting prices from the next request; orders already placed keep what they were charged. Before this, `price_lists.active` had no writer of any kind and a wrong price could only be corrected by editing the database.
- `GET /admin/price-lists/{id}/status-history` — append-only on/off trail, newest first: who switched it, when, and why.
- `GET /price-lists`, `GET /price-lists/{id}`, `GET /price-lists/{id}/items` — reads, open to any staff role.
- `POST /admin/price-overrides`, `GET /admin/price-overrides` — log/list staff-approved ad-hoc POS price overrides (an append-only audit trail, not a mutable price).
- `POST /prices/resolve` — compute the effective price + VAT breakdown for one variant/channel/quantity. Applies **line-level** promotions only: basket rules are excluded deliberately, because this answers "what does this item cost" for a product page and quoting a spend-threshold price against one item advertises a total the shopper will not be charged.
- `POST /prices/resolve-batch` — resolve prices for several lines in one call. Each line is still priced **independently**, so no basket rule can apply; use `/prices/quote` at checkout.
- `POST /prices/quote` — **price a whole basket.** Resolves every line, then runs the promotion engine over the basket as a unit, returning per-line net prices, the whole-basket discount, every promotion that applied, and the VAT computed after discounts (the basket discount is apportioned across lines by value first, so it is not VAT-free money). Takes `couponCodes`; any that do not apply come back in `rejectedCoupons` with a reason — `NO_SUCH_COUPON`, `NOT_APPLICABLE`, `COUPON_EXHAUSTED` or `COUPON_LIMIT_REACHED` — rather than being silently ignored. **Quoting never spends a coupon**: a basket is quoted on every change a shopper makes, so redemption is a separate call. A line's `qty` may be a fraction — a weighed, poured or measured line arrives as its weight or volume — and price-list tiers are matched as if it were at least one, so 0.375 kg is charged 0.375 of the list price rather than refused; a list holding only a bulk tier (say `minQty` 100) still gives one item, or half of one, no price (SJ-D55).
- **Unit prices (03.13).** `POST /prices/resolve`, `/prices/resolve-batch` and every `/prices/quote` line carry `unitPricing` `{amount, unit, quantity, label}` — the price per kilogram, litre, metre, square metre or item (`KG`, `L`, `M`, `SQM`, `EA`; label *per kg*, *per litre*, *per metre*, *per m²*, *each*) of **what the shopper pays**: `totalWithVat` after line promotions on resolve, the line's net plus VAT per one on a quote — so a promotional price is unit-priced too, as the Price Marking Order 2004 (as amended, from 6 Apr 2026) and Directive 98/6/EC art.3 require. Rounded half-up to the currency's minor unit (whole yen for JPY). It is computed from the variant's measure, which product-svc announces as `VariantMeasured` (topic `shelfj.catalog.variant-measured`) with a `version` taken under the variant's row lock; pricing-svc's projection (V10 on `catalogue_variants`) keeps a measure only when its version is newer, so an older announcement arriving late never stands. No declared measure means `unitPricing` is absent — never a guessed unit. Resolve also returns `unitPriceRequired`: whether `UNIT_PRICING` binds the business today by tenant-svc's jurisdiction rules (the UK row, or the EU regime's), taken as true when the rules cannot be read, so a price is never refused over it and a missing unit price is never excused.
- `POST /prices/shelf-labels` `{variantIds, storeId?, channel?}` — **shelf-edge labels** (staff): for each distinct variant (1–200), the regular selling price with its unit price and, while a promotion applies at that store and channel (POS by default), the promotional price with its own unit price and the promotion's name, plus `measureDeclared` and `unitPriceRequired`. A variant with no price in force is a label saying `priced: false`, not a failed batch. `400 PRICING_LABELS_INVALID` for none or more than 200; `400 INVALID_UUID` for an id that is not one. **Prior price (03.12):** while a promotion applies, each label also carries `priorPrice`, `priorPriceStatus`, `priorPriceRequired` and `reductionAnnounceable`; a label shows a was price only when that is true — and then the prior price, never the regular price, where art.6a binds.
- `GET /admin/unit-pricing/gaps` — **priced items that cannot show a unit price** (management): variants with a price in a list in force and no declared measure, with `catalogued` (whether product-svc has announced the variant at all) and `required`. The fix is the variant's net content and unit in product-svc.
- **The prior price of a reduction (03.12, Directive 98/6/EC art.6a).** pricing-svc records every price a shopper is offered — per variant, channel (`ONLINE`, `POS`) and, where a store-scoped promotion applies, store — in an append-only **applied-price ledger** (V11 `applied_prices`; UPDATE and DELETE refused by trigger). Every change that can move a price queues an evaluation in its own transaction (`price_evaluations`): a list price set (whose history is now kept, append-only, in `price_list_item_prices`), a list or promotion made, scoped or switched, a VAT rate or category, the catalogue feed; a scheduled start or end queues one for its moment. A worker (every 5 s; a price or VAT-category write also records its own change before it answers) takes each variant's evaluations **in order** — one is claimed only when nothing earlier for that variant, or for the whole tenant, is still queued — evaluates each **as the definitions stood at its moment** (lists, promotions, scopes and switches by when they were made and thrown, list prices from their history, on the database's clock) and appends a row only when the offer changed. What cannot be read as of an earlier moment — a VAT rate or category overwritten in place, or the catalogue where a category-scoped promotion lets it move a price — makes a still-queued earlier evaluation of the same variant **uncertain** (`uncertainSince`), as does an evaluation made visible after a newer one was worked; the next certain evaluation closes the span. `POST /prices/resolve` returns `priorPrice` (the lowest price applied, VAT included, in the 30 days before the reduction began), `priorPriceStatus`, `reductionStartedAt`, `priorPriceRequired` and `reductionAnnounceable`. Statuses: `ANNOUNCEABLE`; `NO_HISTORY` (reduced from its first recorded price); `SHORT_HISTORY` (under 30 days recorded before it — so in a bound business nothing is announceable for its first 30 days on the ledger); `NOT_LOWER` (it sold at this price or less in the window); `PENDING` (an evaluation covering it is still due); `UNCERTAIN` (the window crosses a span the ledger could not establish). A reduction increased step by step keeps the price before its first step **only where every bound country has taken up art.6a(5)** (`PRICE_REDUCTION_PROGRESSIVE`: Germany); elsewhere each step is measured against the 30 days before it. Whether art.6a binds is asked of **every country the offer reaches** — the business's and, at a store, the store's; with no store, every store's — so a British business with a German shop is bound there and online. Where it does not bind, a promotional price may be announced against the regular price.
- `GET /admin/prices/history?variantId=&limit=` — a variant's ledger, newest first (management): `channel`, `storeId`, `priced`, `price`, `netPrice`, `regularPrice`, `promotionName`, `appliedFrom`, `uncertainSince`, `recordedAt`, `cause`, and `pending` (evaluations due for the business). `400 INVALID_UUID`; another business's variant has no rows.
- `GET /admin/prices/reductions?channel=ONLINE|POS` — **every reduced price on offer**, as the ledger records it, with `priorPrice`, `priorPriceStatus`, `reductionStartedAt`, `priorPriceRequired`, `reductionAnnounceable` and `pending` (management). `400 PRICING_CHANNEL_INVALID`.
- `POST /prices/redemptions` — record that an order used these promotions, spending their usage caps. Idempotent on `(tenant, promotion, order)`, so a retried checkout or a replayed offline sale cannot burn a second use; `recorded: 0` is a successful replay, not a failure.

### Promotions (`/promotions`, `/admin/promotions`)

Same split, and for the same reason: creating a promotion is money leaving the business, and a CASHIER could do it. Writes are under `/admin/`; the storefront read is not.

- `POST /admin/promotions` — create a time-bounded promotion. Seven types: `PERCENT` and `FLAT` (per line), `BASKET_PERCENT` and `BASKET_FLAT` (whole basket), `SPEND_THRESHOLD` (a flat amount once the basket clears `minOrderAmount`), `BOGO` (`buyQty` / `getQty` / `getDiscountPct`, where 100 = free), and **`MIX_MATCH` (03.8): any `buyQty` units from the scope for `value`** — "any 3 for £10". Whole bundles only; the dearest in-scope units make up the bundles, so the saving is the one the offer promises; the units left after the last whole bundle are charged in full; a bundle priced above its units saves nothing; each bundle's saving is split across its lines by price. `buyQty` is a whole number of at least 2 and `getQty` / `getDiscountPct` do not apply (`400 PRICING_INCOMPLETE_MIX_MATCH`, `PRICING_INVALID_PROMOTION_SHAPE`). Also takes `priority` (ascending, lower runs first), `exclusive` (stops every promotion after it), `couponCode` (unique per tenant, matched case-insensitively), and the `maxRedemptions` / `maxPerCustomer` caps.
- `GET /promotions` — list active promotions (also powers the public storefront offers banner). Each carries `reductionAnnounceable` (03.12): a basket, spend-threshold, coupon, buy-one-get-one or mix-and-match offer is a condition, not a reduced price, and is always `true`; a `PERCENT` or `FLAT` item promotion, where art.6a binds, only while every reduced price on the storefront is `ANNOUNCEABLE` and nothing is pending — a banner never says *20% off* over a product whose own page may not call its price reduced.
- `POST /admin/promotions/{id}/items` — scope a promotion to `ALL`, a `VARIANT` or **a `CATEGORY` (03.8)**. A category scope resolves at quote time to the variants of every product whose category path carries it — so a promotion on *Drinks* reaches the products of *Soft drinks* beneath it — through the catalogue product-svc announces (`ProductCategorised`, `VariantCreated`; see product-svc). A category nothing has been announced for discounts **nothing**, not everything (the engine now tells an empty scope from no scope). `VARIANT` and `CATEGORY` need a `scopeId` (`400 PRICING_INVALID_SCOPE`). *Before this branch `CATEGORY` was accepted, stored and silently never applied, then refused with an explanation; it is honoured now.*
- `POST /admin/promotions/{id}/deactivate` · `POST /admin/promotions/{id}/activate` — stop a running promotion or start a stopped one, `{"reason": "..."}` **required in both directions**; `409 PRICING_ALREADY_IN_STATE` if it is already in that state. Before this there was no route, no service method and no SQL statement anywhere that wrote `promotions.active` — `endsAt` is nullable, so a promotion created without one ran forever and could only be stopped by editing the database.
- `GET /admin/promotions/{id}/status-history` — append-only on/off trail, newest first. A table rather than a pair of columns on the row, because a promotion can be switched repeatedly and a record keeping only the last change cannot answer "who turned this back on?".

### Date-code markdown — reduce to clear (`/markdowns`, `/prices/markdown-labels`, `/prices/markdown-redemptions`)
The single most common daily task on a fresh counter (05.4, 03.9): a batch coming up to its date is stickered at a lower price, the sticker carries a new barcode, and the till sells it at that price. Nothing here is a promotion — a sticker is the reduction, and no promotion applies on top of it.
- `GET /markdowns/ladder?storeId=` / `PUT /markdowns/ladder` `{storeId?, steps:[{daysToExpiry, percentOff}]}` — **the ladder (03.9)**: how much off at how many days to expiry. A store's own steps, else the business's, else the default (`3` days `25 %`, `1` day `50 %`, the day itself `75 %`); `source` says which (`STORE`, `TENANT`, `DEFAULT`). The step that applies at *n* days is the tightest whose threshold is at or above *n* — two days out takes the three-day step. `PUT` replaces the steps wholesale; two steps at the same day are `400 PRICING_LADDER_DUPLICATE_STEP`, a percentage over 100 or an empty ladder `400`. Reading is for warehouse and management roles; setting is **management-only** in the resource itself — how much margin the counter may give away is a policy.
- `GET /markdowns/plan?storeId=&withinDays=7` — **what to sticker this morning**: every batch at the store expiring within the horizon (1–60 days, `PRICING_INVALID_HORIZON`), read from inventory-svc's `/admin/inventory/batches/expiring` with the caller's identity forwarded, with its current POS price, the ladder step for its days to go, the suggested price (half-up to the penny) and the live markdown already on it if any. `inventoryReachable: false` with an empty list when inventory-svc could not be read — the screen says so rather than showing nothing to do. Warehouse and management roles, assigned to the store (`403 STORE_ACCESS_DENIED` otherwise); a cashier is `403`.
- `POST /markdowns` `{storeId, variantId, batchId?, batchNo?, expiryDate, qty, percentOff | markdownPrice, reason}` — **sticker a batch**: records the decision and issues the sticker's code — an EAN-13 in the shop's own range, prefix `21`, five digits of item number from the tenant's series (a counter row moved under its lock), five digits of the reduced price in pence, and the check digit — so a plain scanner reads it like any pack. Give `percentOff` or `markdownPrice`, not both (`PRICING_MARKDOWN_AMOUNT_REQUIRED` / `_AMBIGUOUS`); the other is derived from the current POS price (`404 PRICING_MARKDOWN_NO_PRICE` when there is none); the result must be below it (`PRICING_MARKDOWN_NOT_A_REDUCTION`) and fit the code (`999.99`, `PRICING_MARKDOWN_LABEL_RANGE`); a batch already past its date cannot be stickered (`PRICING_MARKDOWN_EXPIRED_DATE`); `reason` is `SHORT_DATED`, `CLEARANCE`, `DAMAGED_PACK` or `OVERSTOCK` (`PRICING_MARKDOWN_REASON_UNKNOWN`). Warehouse and management roles at the store; a cashier is `403`.
- `GET /markdowns?storeId=&status=`, `GET /markdowns/{id}` — a store's markdowns, newest first, each with `qty`, `redeemedQty`, `remainingQty` and its `status`: `ACTIVE`, `EXPIRED` (active but past its date — shown, never stored) or `CANCELLED`. Another tenant's is `404`.
- `POST /markdowns/{id}/cancel` `{reason}` — **take the stickers off**: the code stops scanning; what already sold at the price stays sold. Not active (already cancelled) is `409 PRICING_MARKDOWN_NOT_ACTIVE`; an expired one can still be cancelled to tidy up. The code is then free for a new sticker (uniqueness is on live codes only).
- `GET /prices/markdown-labels/{code}` — **what the till calls when it scans a sticker**: the live markdown behind the thirteen digits — `markdownId`, the product, the store, the reduced and the original price, the date, how many packs are left at that price. `404 PRICING_MARKDOWN_LABEL_UNKNOWN` for a code no live sticker carries (the till then looks it up as an ordinary barcode); `409 PRICING_MARKDOWN_EXPIRED` when the batch is past its date, `409 PRICING_MARKDOWN_EXHAUSTED` when every stickered pack has sold. Any staff role including the cashier; another tenant does not know the code. **03.12:** also `wasPrice` — the price the till may strike through, before VAT — with `reductionAnnounceable`, `priorPrice`, `priorPriceStatus`, `priorPriceRequired` and `perishableExempt`. Where art.6a does not bind, or every bound country exempts goods reduced as they near their date (`PRICE_REDUCTION_PERISHABLE_EXEMPT`, art.6a(3): Germany) and the sticker's reason is `SHORT_DATED`, the was price is the original price; otherwise it is the prior price the ledger proves for the variant at that till (the sticker's price with VAT against the 30 days before), and absent when none is proven. A sticker's price is not itself a row of the ledger: it prices marked packs of one batch, not the product's offer.
- `POST /prices/quote` lines now take `markdownId` — the line is priced at the sticker's price and **stands outside the promotion engine**: no line or basket promotion touches it, and the last promotable line, not the last line, takes the rounding remainder. pricing-svc checks the markdown as the till would: `404 PRICING_MARKDOWN_NOT_FOUND`; `400 PRICING_MARKDOWN_VARIANT_MISMATCH` / `_STORE_MISMATCH` when the sticker is for another product or was issued at another store; `409 PRICING_MARKDOWN_CANCELLED` / `_EXPIRED` / `_EXHAUSTED` (the line's `qty` against what is left). Each response line carries `markdownId` back. order-svc's `POST /orders` items take the same `markdownId`, forward it in the quote, keep it on the stored line (`order_items.markdown_id`, read back as `items[].markdownId`) and pass these refusals through with their own code instead of a `503` — the cashier is told the sticker is sold out, not that pricing is down.
- `POST /prices/markdown-redemptions` `{orderId, lines:[{markdownId, qty}]}` — **what an order sold at reduced prices**, called by order-svc once the order stands (quietly, like promotion redemptions: the order is placed and paid, and a counter that could not be written is caught up, not a reason to lose the sale). Once per `(markdown, order)`: a replay records `0`. This is what makes `remainingQty` fall and a sticker run out.
- Parked sales carry `markdownId` per line (`POST /pos/parked-sales`), so a resumed sale still rings at the sticker.

**Business rules**
- **Ordering is explicit.** Line-level promotions run first in `priority` order against each line's original price, then basket-level ones against the subtotal that remains. Two line-level percentages therefore compound on the original price — two 10% offers take 20%, not 19%.
- Nothing can drive a line or a basket below zero, and the clamp is **per line**, so an oversized flat discount on a cheap item cannot eat into another line's value.
- A `BOGO` counts across every line it is scoped to, not within one line — three different shirts on a buy-2-get-1 is the common case a per-line implementation gets wrong — and discounts the **cheapest** qualifying units.
- `minOrderAmount` is tested against the basket **after** line-level discounts. A basket that only clears £100 before a half-price offer has not spent £100.
- Four defects were fixed in this rebuild, all of which failed silently: `minOrderAmount` was never read, `CATEGORY` scope never matched, `store_id` was never filtered (so a store promotion ran everywhere), and the winner was chosen by `ORDER BY value DESC`, which compared a percentage against a sum of money.

### VAT & Tax Compliance
- `POST /customer-vat-status`, `GET /customer-vat-status/{customerId}` — upsert/look up a B2B customer's VAT registration & reverse-charge status. Since 18.9 also the buyer an invoice names: `legalName` (BT-44), `countryCode`, and an e-invoicing address (`einvoiceScheme` + `einvoiceId`, a Peppol EAS code with its check digits, both or neither: `400 PRICING_EINVOICE_ADDRESS_INVALID`). The VAT number is parsed for its country — a GSTIN for IN (state code, PAN, Luhn mod-36 check character), a VAT identifier elsewhere: `400 PRICING_VAT_NUMBER_INVALID`. A customer recorded here as registered is invoiced by order-svc when a sale to them completes. Quote lines (`POST /prices/quote`) carry `vatCode` and `vatRate` so the sale records the rate each line was taxed at.
- `POST /product-vat-categories`, `GET /product-vat-categories/{variantId}` — upsert/look up a variant's HMRC VAT tax code.
- `POST /vat-rates`, `GET /vat-rates`, `GET /vat-rates/{code}`, `PUT /vat-rates/{code}` — create/list/get/update the business's VAT rates (T1/T5/T0/etc.). The code is at most 8 characters and the rate a fraction from 0 to 1; outside those, `400 VALIDATION_FAILED`. **SJ-D56:** `T1` is the business's standard rate, charged on any variant with no VAT category; rates are written by management only (`403` to a cashier or storekeeper, and the same for `POST /product-vat-categories`) and read by any staff role. **No rate is ever assumed:** until the code a price needs has a rate, `POST /prices/resolve`, `/prices/resolve-batch`, `/prices/quote`, shelf labels and a scanned sticker's prior price answer `409 PRICING_VAT_RATE_NOT_CONFIGURED` — pricing used to charge a literal 20% — order-svc relays that refusal to the till and the shop rather than a 503, and the applied-price ledger records the variant as not offered. A business that charges no VAT sets `T1` exempt.
- `POST /tax-transactions`, `GET /tax-transactions?orderId=` — record/list a POSLog-style tax transaction journal entry per order.
- `GET /vat-return/mtd/registration` / `PUT /vat-return/mtd/registration` `{vrn, provider}` — **Making Tax Digital for VAT (18.5): the digital link.** The number the business files under (nine digits with HMRC's modulus-97 or 9755 check; `GB` and spaces allowed; `MTD_VRN_INVALID`) and the path it files through: `SIMULATED` (HMRC as its sandbox behaves — quarterly obligations, the nine-box rules the API enforces, one accepted return per period, a form bundle number back; nothing reaches HMRC) or `HMRC` (the VAT (MTD) API, offered only when `shelfj.mtd.hmrc.client-id/client-secret` and `shelfj.mtd.token-key` are configured — `MTD_PROVIDER_NOT_CONFIGURED` 409 otherwise). The read returns `registered: false` with the offer until a number exists. `GET /vat-return/mtd/hmrc/authorize-url?redirectUri=` and `POST /vat-return/mtd/hmrc/connect {code, redirectUri}` complete HMRC's OAuth grant for the taxpayer; the tokens are held AES-GCM encrypted under the configured key and refreshed when about to expire; `MTD_NOT_HMRC` (409) for a simulator registration.
- `GET /vat-return/mtd/obligations?from=&to=` — the periods HMRC expects a return for (`periodKey`, start, end, due, `O`pen or `F`ulfilled). `MTD_NOT_REGISTERED` (404) before a number is registered.
- `POST /vat-return/mtd/submissions` `{periodKey, from, to, finalised, client}` — **files the return**: the nine boxes are computed from the period by the same method `GET /vat-return` uses (nobody re-keys them), boxes 6–9 rounded down to whole pounds as the API requires, sent with `finalised: true` (`MTD_NOT_FINALISED` 400 otherwise) and the fraud-prevention headers HMRC mandates — what the server knows plus what the manager's browser sent in `client` (`timezone`, `screens`, `windowSize`, `userAgent`, `deviceId`, `doNotTrack`, `publicIp`). What HMRC answers is recorded in `vat_return_submissions`, append-only, accepted or refused: `201` with `processingDate`, `formBundleNumber`, `paymentIndicator`, `chargeRefNumber`, `receiptId`; `422` with HMRC's own code when it refused (the row is kept as `REJECTED`); `503 HMRC_UNREACHABLE`; `409 MTD_DUPLICATE_SUBMISSION` before any call when the period is already accepted (HMRC would refuse it too); `MTD_PERIOD_KEY_INVALID` for a key that is not HMRC's four characters. `GET /vat-return/mtd/submissions` and `/{id}` read the record, tenant-scoped. Every route is management-only in the resource itself: the path is not under `/admin/`, and the default-deny filter would let a cashier file a VAT return.
- `GET /vat-return?from=&to=` — the boxes of an HMRC Making Tax Digital VAT return for a date range. Management-only (`PLATFORM_ADMIN`/`OWNER`/`MANAGER`), enforced in the resource rather than by path. Boxes 1, 3, 5 and 6 come from `tax_transactions` (output VAT at sale); **boxes 4 and 7 from `input_tax_transactions`** — the projection of purchase-svc's `SupplierInvoiceCaptured`, one row per invoice by invoice date, idempotent on the event id (SJ-D39 closed). Boxes 2, 8 and 9 are zero: no Northern Ireland protocol acquisitions or supplies are modelled. The response says so itself: `computedBoxes: [1,3,4,5,6,7]`, `notComputedBoxes: [2,8,9]`, `fitToFile: true` and a `caveat` naming the NI assumption.

**Business rules**
- `POST /prices/resolve(-batch)` is deliberately open with no staff-role requirement — it's a service-to-service call order-svc makes without identity headers during checkout pricing.
- The customer-VAT-status GET endpoint has its own explicit role check (`PLATFORM_ADMIN`/`OWNER`/`MANAGER`/`STOREKEEPER`/`CASHIER`) because non-`/admin` GETs aren't covered by the shared default-deny filter (see Platform-wide conventions).
- Price overrides are append-only audit records, never edited or deleted.

**Events**
- Consumes: none.
- Publishes: `PriceChanged`, `PromotionActivated`.

## product-svc

### Public Storefront Catalog (`/catalog`)
- `GET /catalog/products` — browse/search products (category, free-text, SKU, or barcode; separate POS vs. online channel filtering).
- `GET /catalog/categories` — browse categories.
- `GET /catalog/products/{id}` — get a product.
- `GET /catalog/products/{id}/variants` — list a product's variants.
- `GET /catalog/products/{id}/image` — fetch the product's primary image.
- `GET /catalog/variants/by-barcode/{code}` — POS barcode-scan lookup (variant + parent product in one round-trip).
- `GET /catalog/scan?code=` — **one lookup for every kind of scanned code (07.15)**. A linear EAN or UPC is matched as it always was; a **GS1 element string** (DataMatrix, GS1-128, GS1 QR — `010950600013435210LOT-7`, or the bracketed form a person writes) and a **GS1 Digital Link URI** (`https://id.gs1.org/01/09506000134352/10/LOT-7?17=261231`, or the same on the brand's own domain, which the standard expects) are read first and the item is then found by **the GTIN they carried**. That is the point: GS1's rule is that GTIN-8, -12 and -13 *are* the 14-digit form with leading zeros, so `product_variants.gtin14` (generated, check-digit verified, V25) lets the packet whose 2D code says `05012345678900` find the variant a shop entered as `5012345678900` — and the other way about. The column is **generated** rather than written by the service so it cannot drift from the barcode: no write path can forget it. Returns `{item, code}`: `item` is the same variant shape `by-barcode` returns, and `code` is what the code itself carried — `format` (`PLAIN_GTIN`/`ELEMENT_STRING`/`DIGITAL_LINK`), `gtin`, `batch` (AI 10), `serial` (21), `sscc` (00), `expiry` (17), `bestBefore` (15), `productionDate` (11), `netWeightKg` (310n), `netWeightLb` (320n, **not** converted — a conversion is a decision about which unit the shop sells in), `amountPayable` (392n/393n) and `currencyNumeric`. Money and measures are strings, scaled by the AI's own decimal places. `code` is **absent** when the scan was not a GS1 code at all (an internal code, a PLU, a shelf label), which still matches exactly. Nothing is half-read: a code the reader cannot read exactly is treated as an opaque string, and an application identifier the platform does not know **refuses** the code rather than skipping it, because skipping means guessing where its data ended and a wrong guess reads the rest of a food label as different fields. A GTIN failing its own check digit fails the reading — the alternative is selling a different item at a different price. `400 INVALID_BARCODE` for a blank code; `404 VARIANT_NOT_FOUND` naming the **GTIN** when the code carried one; `409 PRODUCT_NOT_ON_SALE_YET` for a listed line before its launch date, the same refusal `by-barcode` gives. A public catalogue read, like the rest of `/catalog`. The parser is `shared/gs1` (`Gs1Reader`, `Gtin`, `ApplicationIdentifier`), a standards module with no service state, so inventory-svc's goods-in reads a case label the same way the till reads a packet.

### Food safety, origin and age-restricted sales

Four capabilities that are law rather than product strategy. The reads sit on `/catalog` deliberately — a shopper is entitled to allergen information before buying, and a till needs the age check — while every write is management-only under `/admin/`.

- `GET /catalog/allergens` — the fourteen allergens Regulation (EU) 1169/2011 Annex II names. Reference data, seeded, read-only: a tenant that could edit the list could quietly delete one.
- `PUT /admin/products/variants/{variantId}/allergens` — declare a variant's allergens. **Replaces** the whole declaration, so a mistake can be corrected; merging would make "we were wrong, it has no celery" unsayable. Each entry is `CONTAINS` or `MAY_CONTAIN`, and the distinction is legal rather than cosmetic — `MAY_CONTAIN` is a cross-contamination warning. Declaring the same allergen twice is refused (`PRODUCT_DUPLICATE_ALLERGEN`) rather than silently resolved to the stricter one.
- `GET /catalog/variants/{variantId}/allergens` — the declaration, open to shoppers. **Read the `status`, not the list length.** `UNDECLARED` with an empty list means nobody has checked; `DECLARED` with an empty list means the product has been checked and contains none of the fourteen. Sending an empty list to the PUT is how the second is said — a positive statement, not an omission. Treating the first as the second is how an allergic customer is told a product is safe when nobody knows.
- `GET /admin/products/by-allergen/{code}?presence=` — every product carrying one allergen; the query a recall runs. Both presences by default, because a withdrawal usually has to cover the may-contains too.
- `GET /admin/products/allergen-gaps` — food products nobody has declared yet, oldest first. The list an inspector asks for. An item counts as food once it is marked so: `"food": true` on the compliance PUT moves it from `NOT_APPLICABLE` to `UNDECLARED`, and it leaves this list when its allergens are declared. `"food": false` makes it `NOT_APPLICABLE` and removes any declaration; omitting the flag leaves the status alone, and re-marking a declared item as food never turns its declaration back into an unknown. (SJ-D42: until the flag existed nothing wrote `UNDECLARED` — the column defaults to `NOT_APPLICABLE`, whatever V17's comment says — so this list could never return a row.)
- `GET /admin/products/{id}/safety-information` · `PUT …` · `GET /catalog/products/{id}/safety-information` — **product safety information for online offers (01.12)**: what Regulation (EU) 2023/988 (GPSR) art.19 requires an online offer to show — the manufacturer's name, postal address and electronic address (`manufacturerContact`: an e-mail address or an `https://` URL) and country (ISO 3166-1 alpha-2); where the manufacturer is outside the EU, the same for the EU responsible person; and the `warnings`, or `noWarnings: true` stating none apply (not both, `SAFETY_WARNINGS_CONFLICT`). The PUT replaces the statement; blank fields are absent; `SAFETY_TEXT_INVALID` (length or control characters), `SAFETY_CONTACT_INVALID`, `SAFETY_COUNTRY_INVALID`. Reads return `recorded`, `required` (whether GPSR binds this business's online offers today) and `missing`. The public read is open to shoppers, shown with the offer. Whether the regulation binds a business, and whether a manufacturer's country is inside it, are asked of tenant-svc's jurisdiction rules (`GPSR_ONLINE_OFFER`) through `Jurisdictions` — never a list of EU members here — and `503` when they cannot be read. Where it binds, **a product is not offered online without it**: `POST /admin/products` accepts `safetyInformation` and refuses `sellableOnline` without enough (`400 PRODUCT_SAFETY_INFORMATION_REQUIRED`, the missing items in `details`); `PUT /admin/products/{id}` refuses to keep or put an active product online while its stored statement lacks something; the safety PUT refuses to thin the statement of a product that is online; a bulk import refuses rows that would create an online product (import them with `sellableOnline: false`, then state the information). Each check runs under the product's row lock, so a statement cleared while the product goes online cannot leave an online offer without one. A product sold only at the till needs none of it.
- `GET /admin/products/safety-information/missing` — active online products that GPSR requires safety information for and that lack some, with what each lacks (products listed before the rule was enforced); empty where it does not bind the business.
- `PUT /admin/products/variants/{variantId}/compliance` — country of origin (ISO 3166-1 alpha-2, mandatory for unprocessed meat, fish, fruit, veg, honey, olive oil and wine under EU 1169/2011 art.26), ingredients, the age-restriction category, and the weighed-item fields: `soldBy` (EACH/WEIGHT/VOLUME/LENGTH), `netContent` + `netContentUom` for the unit price a shelf edge must display (Price Marking Order 2004), `tareWeight` a scale deducts, and `catchWeight` for items whose price is not knowable until they are weighed. An item not sold by the each with no unit named is refused — a shelf edge could not price it. **Unit pricing (03.13):** the price buys `netContent` of `netContentUom` (one of that unit when sold by weight, volume or length and no content is given); every save announces the resulting measure in standard units as `VariantMeasured` with the next `measure_version` (V21), in the same transaction, and `POST /admin/products/republish-catalogue` re-announces every variant's at its current version. Where `UNIT_PRICING` binds the business, a **food** item (marked food, or already food) must state a measure convertible to kg, litre, metre, m² or items — a single loose item states `1 EA` — or the save is refused `400 PRODUCT_UNIT_PRICE_MEASURE_REQUIRED`; a bag, a measure of nothing, or weight in litres gives no measure. Since 18.9 also `hsnCode` — the HSN code (or SAC code for a service), 4, 6 or 8 digits (`400 PRODUCT_INVALID_HSN_CODE`), which India's e-invoices name every line by; returned by `GET /admin/products/variants/resolve` for the invoice.
- **Drinks container (09.16):** the same route takes `depositMaterial` (`PET`, `ALUMINIUM`, `STEEL` or `GLASS`) with `depositVolumeMl` (1–10,000), both or neither: what the drink comes in, so the scheme where a store trades can price the deposit. `400 PRODUCT_DEPOSIT_CONTAINER_INCOMPLETE`, `PRODUCT_DEPOSIT_MATERIAL_UNKNOWN`, `PRODUCT_DEPOSIT_VOLUME_OUT_OF_RANGE`. `GET /catalog/variants/by-barcode/{code}` and `GET /admin/products/variants/resolve` carry both, so a till knows at the scan.
- **Item lifecycle:** a product's `status` is `NEW_LINE`, `ACTIVE`, `DISCONTINUED` or `DELISTED`. `POST /admin/products` takes `status: NEW_LINE` with an optional `launchOn` (ISO date) for a line listed before it goes on sale (`400 PRODUCT_STATUS_INVALID`, `PRODUCT_LAUNCH_ON_NEEDS_NEW_LINE`, `PRODUCT_LAUNCH_ON_INVALID`); `POST /admin/products/{id}/launch` (NEW_LINE → ACTIVE), `POST /admin/products/{id}/discontinue` (ACTIVE → DISCONTINUED: sold while stock lasts, never reordered), `POST /admin/products/{id}/reinstate` (DISCONTINUED → ACTIVE), `DELETE /admin/products/{id}` (any → DELISTED); a move a line cannot make from where it is is `409 PRODUCT_LIFECYCLE_INVALID`. `ProductResponse` carries `launchOn` and `discontinuedAt`. The public catalogue and search list what is on sale or being run down; `GET /catalog/variants/by-barcode/{code}` is `409 PRODUCT_NOT_ON_SALE_YET` for a new line (naming its launch day) and `404` for one delisted. Each move goes out as `ProductLaunched`, `ProductDiscontinued`, `ProductReinstated` (topic `shelfj.catalog.product-lifecycle`) or `ProductDelisted`, with the `variantIds` it covers; inventory-svc takes a discontinued or delisted line's variants out of the low-stock report and the planning run.
- `GET /catalog/variants/{variantId}/compliance` — the same, for a shelf edge and a scale.
- `GET /catalog/variants/{variantId}/age-check?country=GB` — what the till must ask before taking payment. **Read `restricted`, never the absence of `minimumAge`**: a null field is omitted from the JSON entirely, so a client inferring "no age given, therefore sell it" cannot tell an unrestricted item from a field that went missing. `restricted` is always present. **A date of birth, not an age (10.8):** from the day a birth-date cut-off takes effect, `bornBefore` (yyyy-mm-dd) says to refuse anyone born on or after it, whatever their age — the UK's generational tobacco ban (Tobacco and Vapes Act 2026: nobody born on or after 1 Jan 2009) appears from 1 Jan 2027 — and `bornBeforeTenantOverride` is true when the date is the business's own earlier policy. The strictest cut-off wins; a tie is reported as the law's.
- `GET /admin/age-restriction-rules?country=` · `PUT /admin/age-restriction-rules` — the statutory defaults with this tenant's overrides shadowing them. A tenant rule may be **stricter than the statute and never laxer** (`PRODUCT_AGE_BELOW_STATUTORY`): a chain adopting Challenge-25 is making a policy decision, a chain setting alcohol to 16 in the UK is committing an offence, and a system that lets them configure it has helped. A rule may also carry `bornBefore`: a business may adopt the law's cut-off early or choose an earlier date, never a later one (`PRODUCT_BORN_BEFORE_LAXER`); a malformed, pre-1900 or future date is `PRODUCT_INVALID_BORN_BEFORE`. The listing shows the strictest cut-off per category, with `bornBeforeFrom` — the day a statutory one takes effect, null for a business's own, which applies at once. Setting a rule replaces it, so a rule set without `bornBefore` clears the business's date; the law's still applies.

**Why the age is not on the product.** The same bottle of wine is 18 in the UK, 18 in China, 20 in Japan and 21 in the US. The variant carries the *category* (`ALCOHOL`, `TOBACCO`, `KNIVES`, `SOLVENTS`, `FIREWORKS`, `LOTTERY`, `VIDEO_18`, `NICOTINE_VAPE`, `CORROSIVES`, `PETROL`) and the age is resolved per country at the till. India's drinking age varies by state, so the seeded default is the conservative 21 and a tenant trading where it differs overrides it. The endpoint takes the country rather than a store id on purpose: this is asked for every restricted line scanned, and a second network hop belongs nowhere near a queue.

A restricted item in a country with **no** rule for it returns `400 PRODUCT_NO_AGE_RULE` rather than "no restriction" — a missing rule is a gap in configuration, not a licence to sell.

## purchase-svc

### Suppliers & Purchase Orders
- `POST /suppliers`, `GET /suppliers`, `GET /suppliers/{id}`, `PUT /suppliers/{id}` — onboard/list/get/correct suppliers. `PUT` (management-only) replaces name, VAT details, country, currency and terms — SJ-D34 found none of them could be corrected after creation, which mattered once purchase orders inherited the supplier's currency. The currency can change only while no purchase order against the supplier is open (`409 PURCHASE_SUPPLIER_CURRENCY_IN_USE`, with the count); orders already raised keep the currency they were raised in. A name already taken is `409 PURCHASE_SUPPLIER_DUPLICATE`. `currency` is the currency **this supplier invoices in**, defaulting to the tenant's own declared currency; set it explicitly for an overseas supplier (a Japanese supplier billing a UK tenant in JPY). **Payment fields (17.10):** `remittanceEmail` (where remittance advice goes; on `PUT` an empty string clears it, and one that is not an email is `400 PURCHASE_REMITTANCE_EMAIL_INVALID`) and the bank details `bankAccountName`, `bankSortCode` + `bankAccountNumber` (UK, six and eight digits, dashes and spaces allowed) and/or `bankIban` (check digits verified) with an optional `bankBic`. They are validated as one set — half a UK account, a BIC without an IBAN or no holder name is `400 PURCHASE_BANK_DETAILS_INVALID` — and on `PUT` a set that is given replaces the old one whole, while `clearBankDetails: true` removes them. Setting, changing or clearing them needs `finance.payments` (`403 PERMISSION_DENIED`): a storekeeper may add a supplier, not the account its money goes to. Only an actual change moves `bankDetailsChangedAt`. Responses never carry the full account: `bankAccountNumberMasked` and `bankIbanMasked` show the last four characters, with `hasBankDetails` and `bankDetailsChangedAt`.
- `POST /purchase-orders` — create a purchase order for a supplier. **The order's currency comes from the supplier**, not the tenant and not a default — a purchase order is a commitment to pay whoever invoices (SJ-D24). Naming a currency that contradicts the supplier's is refused with `PURCHASE_CURRENCY_MISMATCH` rather than silently overridden; a non-ISO-4217 code is `PURCHASE_INVALID_CURRENCY`.
- `GET /purchase-orders`, `GET /purchase-orders/{id}` — list/get purchase orders.
- `POST /purchase-orders/{id}/submit` — submit a draft PO. Lands in `SUBMITTED` when the order's **net** value is within the submitter's own spend authority, and in `PENDING_APPROVAL` when it is not; either way the submission is recorded in the order's append-only approval trail. Spend authority is configured per **currency and role** (`shelfj.purchase.approval.limits`, e.g. `GBP:MANAGER:5000,JPY:MANAGER:800000,GBP:OWNER:UNLIMITED`) — there is no FX handling in Shelf-J, so a ceiling in one currency cannot be compared against an order in another. **Unconfigured means off**: with no limits at all, any staff role may submit any amount, exactly as before the feature existed. Once anything is configured, a currency with no entry **fails closed** rather than granting unlimited authority.
- `POST /purchase-orders/{id}/approve` — release a `PENDING_APPROVAL` order to the supplier. The approver's own authority is checked against the same figure by the same rule, so **separation of duties falls out of the limits**: an order is only pending because it exceeded the submitter's ceiling, so that same person is refused with `PURCHASE_APPROVAL_EXCEEDS_AUTHORITY`. There is deliberately no separate self-approval rule — it would be redundant, and would deadlock a single-owner shop.
- `POST /purchase-orders/{id}/reject` — send it back to `DRAFT` with a **required** reason. Needs no spend authority: refusing to commit money is not itself a commitment, and requiring it would strand an order too large for anyone configured.
- `GET /purchase-orders/{id}/approvals` — the append-only approval trail, newest first. Each row carries the net value and the authority **as they stood at the time**, so it still answers "was that person allowed to commit that much?" after the configuration changes — and because a rejected order can be edited before resubmission, the figure a decision was made against is not necessarily the one the order carries now.
- `GET /purchase-orders/spend-authority?currency=GBP` — what the caller may commit, so a buyer learns their ceiling before building the order rather than after trying to submit it.
- `POST /supplier-invoices` — **capture a supplier's invoice and match it three ways.** Quantity is matched against what was **received**, not ordered — you pay for what turned up, and an order for 100 that delivered 60 and invoiced 60 is correct. Price is matched against the **order**, because a goods receipt records quantity only. Invoiced quantity is compared **cumulatively across every invoice on the order**, so a supplier who delivers and bills in two parts is not flagged on the second (the same shape partial receipt established for the received leg). The invoice is stored either way: `MATCHED` or `FLAGGED`. **Flagging never blocks capture** — an invoice that arrived is a fact, and refusing to record one that disagrees destroys the evidence of the disagreement. A duplicate invoice number for the same supplier is `409 PURCHASE_INVOICE_DUPLICATE`, matched case-insensitively because the reference is printed on paper and typed by a human. An invoice in a currency the order was not placed in is `400 PURCHASE_CURRENCY_MISMATCH` — that is a different document, not a variance.
- `GET /supplier-invoices`, `GET /supplier-invoices/{id}` — list (optionally `?poId=` and `?status=MATCHED|FLAGGED|APPROVED|REJECTED`; `?status=FLAGGED` is the queue awaiting a decision, another value `400 PURCHASE_INVOICE_STATUS_UNKNOWN`) and get, each line carrying ordered / received / previously-invoiced / invoiced and both unit prices. Variances are the ones **stored at capture**, not recomputed: a purchase order can be amended after an invoice is flagged, and re-matching on read would silently erase the disagreement it was flagged for. Codes: `INVOICED_ABOVE_RECEIVED`, `NOT_RECEIVED`, `NOT_ON_ORDER`, `PRICE_ABOVE_ORDER`, `PRICE_BELOW_ORDER`; header-level `TOTAL_MISMATCH` in `headerVariances`. **Tolerance is SAP-shaped (07.7)**: percentage *and* absolute, with separate upper and lower bands on price, the stricter governing — `shelfj.purchase.match.tolerance.price-percent` (upper), `.price-lower-percent` (defaults to the upper), `.price-absolute`, `.qty-percent`, `.qty-absolute`, `.total-absolute`. Every band defaults to exact, which surfaces every difference; widening one is a procurement policy made in configuration. The response also carries `dueDate` (invoice date + the supplier's `paymentTermsDays`), `statedGross`, `postedAt`, `payable` (MATCHED, or FLAGGED then APPROVED), the decision (`resolvedAt`, `resolvedBy`, `resolutionReason`), and whether a payment run has settled it (`paid`, `paidAt`, `paymentRunId`).
- **Capture posts to the nominal ledger** — `Dr 2109 Goods Received Not Invoiced` (net), `Dr 2201 VAT Input` (VAT), `Cr 2100 Trade Creditors` (gross), dated the invoice date, on the order's store — **whether or not the invoice matched**. This is SAP's model rather than "post on approval": the liability exists the moment the supplier has invoiced, whatever the buyer thinks of the figures; what a variance blocks is *payment* (`payable=false`). `statedGross`, when keyed, is the total printed on the document and is checked against the supplier's own lines plus VAT; a difference beyond `.total-absolute` flags `TOTAL_MISMATCH`, because an invoice that does not add up is wrong before any line is compared. An invoice dated in a month whose accounting period is closed is `409 PURCHASE_PERIOD_CLOSED`.
- `POST /supplier-invoices/{id}/resolve` `{action: APPROVE|REJECT, reason}` — **the decision on a flagged invoice (07.7).** Management only, reason required. `APPROVE` releases it for payment and leaves its posting as it is. `REJECT` reverses its posting line for line on a new journal dated today (`INVOICE_REVERSAL`), publishes `SupplierInvoiceRejected` so pricing-svc takes its input VAT back out of the return, and frees the quantities it billed so the supplier's corrected invoice matches cleanly. Only a `FLAGGED` invoice can be decided (`409 PURCHASE_INVOICE_NOT_FLAGGED`), and only once — the status condition is inside the `UPDATE`, so twenty managers deciding together produce one decision and nineteen `409 PURCHASE_INVOICE_ALREADY_RESOLVED`. An action that is neither is `400 PURCHASE_RESOLUTION_UNKNOWN`.
- `POST /purchase-orders/{id}/lines`, `GET /purchase-orders/{id}/lines` — add/list PO line items. **Adding a line restates the order's totals** in the same transaction (SJ-D22): `totalNet` from the lines, `totalVat` from each line's VAT code rated against pricing-svc's table for the tenant, `totalGross` from the two. Before this the three columns were inserted as zero and never written again, so every purchase order in the product reported a value of `0.00`. A VAT code with no configured rate contributes zero rather than refusing the line — VAT rates are tenant configuration nothing seeds, so a fresh tenant genuinely has none.
- `POST /purchase-orders/{id}/cancel` — cancel a DRAFT or SUBMITTED order with a required reason. A RECEIVED one is refused: stock is booked against it (SJ-D3).
- `GET /purchase-orders/{id}/progress` — **ordered against received, line by line, with the balance still due.** This is what a `PARTIALLY_RECEIVED` status does not tell you: a buyer chasing a supplier needs to know *what* is missing. Receipts are matched to order lines by variant rather than by line id, because a delivery note names products, not order rows.
- `POST /purchase-orders/{id}/close` — short-close a `PARTIALLY_RECEIVED` order with a required reason: the balance is never arriving and we have stopped waiting. Refused on any other status — nothing delivered is a cancellation, everything delivered is already RECEIVED.
- `POST /goods-receipts` — record goods received against a purchase order. Accepts partial deliveries. **Posts `Dr Stock / Cr 2109 Goods Received Not Invoiced`** for the quantity received at the order's own prices, in the receipt's transaction (an idempotent replay posts nothing twice). The stock code is **the store's zone-to-GL mapping in inventory-svc** (17.3: the store-level row of `PUT /admin/inventory/zone-gl-mappings`, read service-to-service) or `1001 Stock` when the store has none; when inventory-svc cannot be reached the default is used, so a discovery outage changes which code a receipt posts to, never whether it posts. A receipt into a month whose accounting period is closed is `409 PURCHASE_PERIOD_CLOSED` (04.7), and the order is untouched.
- `GET /goods-receipts?poId=` — list goods receipts for a PO.
- `POST /vendor-returns` `{poId, reason, notes, lines:[{variantId, qty}]}` — **return to vendor and the debit note (07.8)**, the reverse SJ-D3 named. Goods go back against an order something was received on (`PARTIALLY_RECEIVED`, `RECEIVED` or `CLOSED`; otherwise `409 PURCHASE_RTV_NOTHING_RECEIVED`), from the order's store, at the order's own price for each variant with VAT at the order's VAT code — so the debit note and the invoice it offsets agree to the penny. No variant may go back in more than was received less what already went back (`422 PURCHASE_RTV_OVER_RETURN`, checked under the order's lock); a variant not on the order is `422 PURCHASE_RTV_NOT_ON_ORDER`; `reason` is one of `DAMAGED`, `WRONG_ITEM`, `OVER_DELIVERED`, `QUALITY`, `EXPIRED`, `RECALL`, `OTHER` (`400 PURCHASE_RTV_REASON_UNKNOWN`). The debit note takes the next number in the tenant's series (`DN-000012`, a counter row moved under its lock like a receipt number). `ReturnedToVendor` is written in the same transaction and inventory-svc deducts the stock FIFO from the store's available batches as `RTV` movements against the return; when inventory-svc can be reached, on-hand is checked first and a return of goods already sold is `422 PURCHASE_RTV_INSUFFICIENT_STOCK` here rather than a skipped line there. **The purchase order's status is untouched**: what was received was received, the three-way match still compares the invoice to it, and the debit note is the offset — which is how accounts payable expects it; `GET /purchase-orders/{id}/progress` now carries `qtyReturned` per line. `Idempotency-Key` makes a retried raise return the same document. Warehouse and management roles (`STOREKEEPER` and up), assigned to the order's store; a cashier is `403`.
- `GET /vendor-returns?poId=`, `GET /vendor-returns/{id}` — the returns, newest first, each with its lines: the debit note as a document. Any staff role; another tenant's is `404`.
- `POST /vendor-returns/{id}/credit` `{creditNoteNumber, creditNoteDate, amount?}` — record the supplier's credit note, closing the return (`RAISED` → `CREDITED`; `amount` defaults to the debit note's gross). **Posts `Dr 2100 Trade Creditors` for the credit, `Cr 2201 VAT Input` for its VAT share (the return's own VAT ratio applied to the amount, so a partial credit splits the way the debit note did) and `Cr Stock` for the rest**, dated the credit note, on the return's store; `409 PURCHASE_PERIOD_CLOSED` when that month is closed. Once only: a second is `409 PURCHASE_RTV_ALREADY_CREDITED` naming the first. Management-only — matching money received to money owed is a finance decision.
- `POST /e-invoices` — **receive a supplier's e-invoice (07.13).** The body is the document itself: UBL 2.1 or CII D16B XML (`application/xml`, `text/xml`) or a Factur-X / ZUGFeRD PDF (`application/pdf`), up to 20 MB. It is read by `shared/einvoice` with DTDs refused and its size, depth and element counts capped (`400 PURCHASE_EINVOICE_<code>` naming what was wrong — `NOT_AN_INVOICE`, `DTD_REFUSED`, `PDF_UNREADABLE`, `PDF_ENCRYPTED`… — `400 PURCHASE_EINVOICE_EMPTY`, `413 PURCHASE_EINVOICE_TOO_LARGE`, `415 PURCHASE_EINVOICE_MEDIA_TYPE`), checked against EN 16931 and, when it says it is one, Peppol BIS Billing 3.0, and kept byte for byte: the same bytes again answer `200` with `alreadyReceived` and the first receipt. Then it is matched. **Supplier:** the electronic address it was sent from, else a seller VAT number exactly one supplier holds. **Order:** the id in its order reference (BT-13). **Lines:** the order line each references (id or position), then an item code a person matched before, then the buyer's own variant id on the order. Complete, it is captured through the three-way match exactly as `POST /supplier-invoices` captures a keyed one (`CAPTURED`, `supplierInvoiceId`), or its credit note closes the only open return on the order, or the one for its gross (`CREDITED`); a number the supplier already has captured is `DUPLICATE`. Otherwise it waits with `problem` in words: `NEEDS_SUPPLIER`, `NEEDS_ORDER`, `NEEDS_LINES`, `NEEDS_RETURN`, or `NEEDS_DECISION` when the capture itself was refused. A fatal rule makes it `NOT_COMPLIANT` with its `violations`; a buyer VAT number or electronic address that is not this business's makes it `MISDIRECTED`. The business's own are tenant-svc's `vatNumber`, `einvoiceScheme` and `einvoiceId` on `PUT /admin/tenant` (empty removes one; `400 TENANT_VAT_NUMBER_INVALID`, `400 TENANT_EINVOICE_ADDRESS_INVALID`); a supplier's are `einvoiceScheme` and `einvoiceId` on `POST`/`PUT /suppliers` (both or neither, a Peppol EAS code with its check digits: `400 PURCHASE_EINVOICE_ADDRESS_INVALID`; one supplier per address: `409 PURCHASE_SUPPLIER_EINVOICE_ADDRESS_TAKEN`). Any staff role.
- `GET /e-invoices?status=&limit=`, `GET /e-invoices/{id}`, `GET /e-invoices/{id}/document` — newest first (`limit` up to 100; a status that does not exist is `400 PURCHASE_EINVOICE_STATUS_INVALID`); one with its lines, what each was matched by (`ORDER_LINE`, `ITEM_CODE`, `PERSON`) and the rules it broke; and the original as it arrived, with its media type, `Content-Disposition` and `nosniff`. Another tenant's is `404 PURCHASE_EINVOICE_NOT_FOUND`.
- `POST /e-invoices/{id}/match` `{supplierId, poId, returnId, lines:[{position, poLineId}], remember}` — **a person finishes a waiting e-invoice.** Anything left out is found again as on arrival; what is chosen is checked (`400 PURCHASE_EINVOICE_ORDER_NOT_SUPPLIERS`, `PURCHASE_EINVOICE_LINE_UNKNOWN`, `PURCHASE_EINVOICE_LINE_NOT_ON_ORDER`, `PURCHASE_EINVOICE_LINE_CHOSEN_TWICE`, `PURCHASE_EINVOICE_RETURN_NOT_OPEN`). `remember` keeps the supplier's electronic address and which of its item codes are which variant, so its next invoice matches on its own. A settled, non-compliant or misdirected document is `409 PURCHASE_EINVOICE_SETTLED`, `…_NOT_COMPLIANT`, `…_MISDIRECTED`. Two people at once is `409 PURCHASE_EINVOICE_BUSY`: the first takes a claim that lapses after two minutes, so ten matches sent together make one invoice.
- `POST /e-invoices/{id}/refuse` `{reason}` — kept, not captured (`REFUSED`, with the reason and who decided). Needs `purchasing.invoices.decide`; a settled document is `409 PURCHASE_EINVOICE_SETTLED`. 
- `POST /e-invoices/inbound/{network}` — **a network delivers a supplier's e-invoice (the transport seam).** What a Peppol access point, France's approved platform or this platform's own simulated network calls, `network` being `peppol`, `fr_pdp` or `simulated` (`400 PURCHASE_EINVOICE_NETWORK_UNKNOWN` for anything else: KSeF is pulled by the buyer and India's portal delivers nothing). Public at the gateway and in the service like a payment webhook — the provider holds no token and names no tenant — and authenticated instead by the deployment's delivery key, presented as `X-EInvoice-Key` and held in constant time against `shelfj.einvoice.inbound.key` before a byte is read (`401 PURCHASE_EINVOICE_KEY_REFUSED`; `503 PURCHASE_EINVOICE_DELIVERY_OFF` on a deployment with no key, which takes no deliveries). The receiver is the business the document itself names as its buyer — by electronic address (BT-49), else by VAT identifier (BT-48) — found platform-wide through tenant-svc (`GET /platform/tenants/by-einvoice-address`), never by anything in the request: identity headers on a delivery choose nothing. `422 PURCHASE_EINVOICE_RECEIVER_UNNAMED` for a document naming neither; `404 PURCHASE_EINVOICE_RECEIVER_UNKNOWN` when no active business holds what it names; `409 PURCHASE_EINVOICE_RECEIVER_SHARED` when more than one does, since a delivery to a shared address lands nowhere. The network's own reference, `X-EInvoice-Reference` (up to 200 characters: `400 PURCHASE_EINVOICE_REFERENCE_TOO_LONG`), is kept as the document's `deliveryRef`. Then the document goes through the intake exactly as an upload does — the same media types, caps and refusals, the same matching and capture, written by nobody — with the network as its `channel`; and the network learns `{id, network, reference, alreadyReceived, receivedAt}` and nothing of the receiver's own: `201` when delivered, `200` when the same bytes were already there. Ten deliveries at once of one document make one row.

### Supplier payment runs (`/payment-runs`, 17.10, 17.12)
Every route needs a management role **and** `finance.payments`; a storekeeper or cashier is `403`, another tenant's run `404 PURCHASE_PAYMENT_RUN_NOT_FOUND`.
- `POST /payment-runs` `{payUpTo, paymentDate, currency?}` — **propose a run.** Collects every invoice that may be paid — `MATCHED`, or `FLAGGED` then `APPROVED`; posted; unpaid; in the run's currency (the tenant's own when omitted); due on or before `payUpTo`; not held by another open run — and each supplier's unallocated credit notes (vendor returns `CREDITED`), which are offset against what that supplier is paid. A supplier with no bank details, or whose credits cover its invoices, is not paid and is listed under `excluded` with `NO_BANK_DETAILS` or `NET_NOT_POSITIVE`; a supplier whose bank details changed in the last 14 days is paid but carries the warning `BANK_DETAILS_CHANGED_RECENTLY`, because a changed account on a supplier about to be paid is the pattern payment-diversion fraud leaves. The run gets a reference such as `PAY260913-3F9A1C` (at most 18 characters, for a BACS reference) and holds its documents: a partial unique index lets a document sit in one open run at a time, so a second proposal does not pick them up and ten racing proposals produce one run and nine `409`s (`PURCHASE_PAYMENT_RUN_NOTHING_DUE` or `PURCHASE_PAYMENT_RUN_CONFLICT`). `paymentDate` before today, or either date more than a year ahead, is `400 PURCHASE_PAYMENT_DATE_INVALID`. Nothing payable is `409 PURCHASE_PAYMENT_RUN_NOTHING_DUE` with each supplier left out, and why, in `details`. `201` with the run.
- `GET /payment-runs?status=&limit=`, `GET /payment-runs/{id}` — runs newest first, each with `suppliers` (per supplier: `net`, `warnings`, `remittanceEmailOnFile` and its `documents`, invoices paid and credit notes offset) and `excluded`. An open run is judged against the suppliers as they stand, so one that can no longer be paid moves to `excluded`; a paid or cancelled run is shown as it was. Bank details never appear. An unknown status is `400 PURCHASE_PAYMENT_RUN_STATUS_UNKNOWN`.
- `POST /payment-runs/{id}/approve` — `PROPOSED` → `APPROVED`, by someone other than the proposer (`403 PURCHASE_PAYMENT_RUN_SELF_APPROVAL`) unless the approver is the owner, because a one-person business still has to pay its suppliers. A supplier in the run that can no longer be paid is `409 PURCHASE_PAYMENT_RUN_STALE`; a run already approved `409 PURCHASE_PAYMENT_RUN_ALREADY_APPROVED`.
- `GET /payment-runs/{id}/bank-file?format=` — **the file for the bank**, named from the run reference, `Cache-Control: no-store`. Only for an `APPROVED` or `PAID` run (`409 PURCHASE_PAYMENT_RUN_NOT_APPROVED`, `409 PURCHASE_PAYMENT_RUN_CANCELLED`), and refused with `409 PURCHASE_PAYMENT_RUN_BANK_DETAILS_CHANGED`, naming the suppliers, when any supplier's bank details changed after the run was approved. An unknown format is `400 PURCHASE_BANK_FILE_FORMAT_UNKNOWN`.
  - `CSV` (the default) — for a bank's bulk upload (`text/csv`): `payee_name,sort_code,account_number,iban,bic,amount,currency,reference`, one payment per supplier, CRLF line endings. Every text cell is guarded against formula injection (a payee named `=SUM(A1)` is written `'=SUM(A1)`).
  - `PAIN001` — an ISO 20022 `pain.001.001.09` SEPA credit transfer (`application/xml`) for a euro run: one payment block from the euro paying account (service level `SEPA`, charge bearer `SLEV`, batch booking, the payment date as the requested execution date) and one transaction per supplier, carrying the creditor's IBAN (and BIC when known), the run reference as message id and remittance, and an end-to-end id derived from the run and the supplier — the same in every file for the run, so the bank's report matches back to it. Names and references are written in the SEPA Latin character set and cut to the scheme's lengths. Refused with `409`: a run not in euro (`PURCHASE_BANK_FILE_FORMAT_UNSUPPORTED`), no euro paying account (`PURCHASE_PAYING_ACCOUNT_MISSING`), a supplier with no IBAN (`PURCHASE_BANK_FILE_PAYEE_UNSUPPORTED`, naming them).
  - `BACS18` — a Bacs Standard 18 file (`text/plain`) for a sterling run: `VOL1`, `HDR1`, `HDR2` and `UHL1` labels (the processing day one banking day before the payment date, on the three-day cycle), one 100-character standard record per supplier (transaction code `99`), the contra record (`17`) debiting the paying account, then `EOF1`, `EOF2` and `UTL1` with the totals. The file's serial and number are derived from the run, so a file sent twice carries the same serial and the bank refuses the second. Refused with `409`: a run not in sterling, no sterling paying account with a service user number, a payment date before the earliest a file made today can pay (`PURCHASE_BANK_FILE_TOO_LATE`, that date in `details`), a supplier with no sort code and account number (`PURCHASE_BANK_FILE_PAYEE_UNSUPPORTED`).
  - Both bank formats are refused with `409 PURCHASE_PAYMENT_RUN_PAYING_ACCOUNT_CHANGED` when the account the run pays from changed after approval: a run pays from the paying account in force when it was approved or, approved before any was set, the first one set after.
- `GET /payment-runs/paying-accounts`, `PUT /payment-runs/paying-accounts/{currency}` `{accountName, sortCode?, accountNumber?, iban?, bic?, serviceUserNumber?}` — **the accounts supplier payments are made from**, one per currency: the latest set, earlier ones kept. The holder's name with a UK sort code and account number or an IBAN (check digits verified), a BIC optional; a euro account needs its IBAN; a six-digit Bacs service user number goes with a UK account. Account numbers and IBANs come back masked. Anything else is `400 PURCHASE_PAYING_ACCOUNT_INVALID` naming what is wrong; a currency that is not ISO 4217 is `400 PURCHASE_INVALID_CURRENCY`.
- `POST /payment-runs/{id}/status-report` (the bank's ISO 20022 `pain.002` customer payment status report as `application/xml`) — **the bank's answer to a file**, for an `APPROVED` run (`409 PURCHASE_PAYMENT_RUN_NOT_AWAITING_BANK` otherwise). Each payment is matched by its end-to-end id, and its status, reason code and the Verification of Payee result the bank returns (`MTCH`; `CMTC` with the name the bank holds; `NMTC`; `NOAP`) are recorded; a payment with no status of its own takes the report's group status. A rejected payment (`RJCT`), a payee the bank could not match (`NMTC`) or matched only closely (`CMTC`) is **held**, as each supplier's `bankCheck` in the run shows, and the run is not paid while it is. The latest report on a payment is the one in force; a report is recorded once by its message id, so uploading it again changes nothing. Refused: not well-formed, a DTD or entity, more than 2,000,000 characters or 10,000 payments, an unknown status (`400 PURCHASE_STATUS_REPORT_INVALID`); a report whose original message id is not the run reference (`409 PURCHASE_STATUS_REPORT_NOT_FOR_RUN`); a report naming a payment the run does not make (`409 PURCHASE_STATUS_REPORT_UNKNOWN_PAYMENT`).
- `POST /payment-runs/{id}/payments/{supplierId}/release` `{reason}` — **release a held close match** a manager has checked, saying what was checked. Once: ten concurrent releases release it once and the rest are `409 PURCHASE_PAYEE_ALREADY_RELEASED`. A payment the bank did not hold is `409 PURCHASE_PAYEE_NOT_HELD`; a rejected payment or a payee the bank could not match is `409 PURCHASE_PAYEE_NOT_RELEASABLE` — cancel the run, or upload the bank's later report once the supplier's details are right.
- `POST /payment-runs/{id}/pay` — **pay an approved run**, all in one transaction: the run `PAID`, every invoice it holds `paid` with the run's id, every credit note allocated, and `Dr 2100 Trade Creditors / Cr 1200 Bank` posted per supplier and store, dated the payment date, source `SUPPLIER_PAYMENT` with the run as `sourceRef` (a store whose credits exceed its invoices posts the other way round). `SupplierRemittanceIssued` is written per supplier with an event id derived from the run and the supplier. The state condition is inside the `UPDATE`, so twenty concurrent calls pay once and the rest are `409 PURCHASE_PAYMENT_RUN_ALREADY_PAID`; a document that changed under the run is `409 PURCHASE_PAYMENT_RUN_STALE` and nothing is written. Also refused: `PURCHASE_PAYMENT_RUN_PAYEE_HELD` while the bank holds a payment no manager has released, naming each supplier and why; `PURCHASE_PAYMENT_RUN_NOT_APPROVED`, `PURCHASE_PAYMENT_RUN_CANCELLED`, `PURCHASE_PAYMENT_RUN_BANK_DETAILS_CHANGED` and `PURCHASE_PERIOD_CLOSED` for a store whose period covering the payment date is closed.
- `POST /payment-runs/{id}/cancel` `{reason}` — a `PROPOSED` or `APPROVED` run to `CANCELLED` with a required reason, releasing its documents for the next run. A paid run is `409 PURCHASE_PAYMENT_RUN_ALREADY_PAID`, a cancelled one `409 PURCHASE_PAYMENT_RUN_CANCELLED`.

### Intercompany & Ledger
- `POST /intercompany-invoices` — raise a matched AR/AP invoice pair for an inter-org inventory transfer.
- `GET /intercompany-invoices`, `GET /intercompany-invoices/{id}` — list/get intercompany invoices.
- `POST /intercompany-invoices/{id}/settle` — settle an intercompany invoice.
- `GET /nominal-ledger` — the double-entry nominal ledger line by line (filter by `?code=&from=&to=`, cursor-paged). Every line now carries `journalId` (the lines of one posting share it), `sourceType` (`GOODS_RECEIPT`, `SUPPLIER_INVOICE`, `INVOICE_REVERSAL`, `CREDIT_NOTE`, `SUPPLIER_PAYMENT`, `SALE`, `SALE_TENDER`, `SALE_REFUND`, `LOYALTY_DEFERRAL`, `LOYALTY_RELEASE`, `GIFT_CARD_LOAD`, `GIFT_CARD_BREAKAGE`, `INTERCOMPANY`, `SETTLEMENT`, `JOURNAL`; null for rows written before postings existed) and `storeId`. Readable by any member of staff, as before.
- `POST /nominal-ledger/journals` `{entryDate, description, storeId?, lines:[{nominalCode, nominalName?, debit?, credit?}]}` — **a manual journal (17.1).** Management only. Two to fifty lines, each a debit or a credit and never both (`400 PURCHASE_JOURNAL_LINE_INVALID`), a nominal code of one to ten letters or digits, balancing to the penny (`422 PURCHASE_JOURNAL_UNBALANCED`). A store, when named, must be one the caller may operate in (`403 STORE_ACCESS_DENIED`) and its accounting period for the date must be open (`409 PURCHASE_PERIOD_CLOSED`); a tenant-level journal answers to no store's period. Returns the journal with its `journalId` and totals.
- `GET /nominal-ledger/journals/{journalId}` — one posting, whole. Management only; another tenant's is `404`.
- **Sales and tender posting (17.7).** The ledger now records what the business sells, from events rather than a route: each `PaymentCaptured` posts **Dr the tender's control account / Cr 1105 Sales Receipts Clearing** — `1210 Cash in Tills` for cash, `1250 Card and Wallet Clearing` for card, UPI and wallet, `2310 Gift Card and Voucher Liability`, `2320 Store Credit Liability`, and `1299 Unallocated Receipts` for a method nobody mapped — and the confirmed sale (`OrderConfirmed`, which now carries `taxAmount`) posts **Dr 1105 with the total / Cr 4010 Sales net / Cr 2200 VAT Output**. A sale paid in full therefore nets 1105 to zero for its order. A `PaymentRefunded` (now carrying each tender's share) credits the control account each share came from and debits 4010 and 2200 in the sale's own VAT ratio, or debits 1105 when the ledger never saw the sale confirmed. Every posting names the order as `sourceRef` and its store; each event, and each sale or tender announced twice, is posted once. Postings are dated the day received and are not refused in a closed period — the sale has happened; a late one is what the clearing report is for.
- `GET /nominal-ledger/sales-clearing?storeId=&limit=` — **the orders whose receipts clearing did not net to zero**: taken but never confirmed, confirmed for more than was taken, or refunded against a sale the ledger never saw, each with its balance (debit less credit: negative is money nobody's sale has claimed) and the first and last day posted, oldest first. Management only; a store the caller cannot operate in is `403`, a storeId that is not one `400`.
- `GET /nominal-ledger/trial-balance?from=&to=&storeId=` — **the trial balance (17.1):** every nominal code's debits, credits and balance (debit less credit) over the range, with `totalDebit`, `totalCredit` and `balanced`. Management only. `balanced` is the ledger's own invariant — every posting the service writes balances, so `false` is a fault to investigate, not a figure to report. A range that ends before it starts is `400 PURCHASE_INVALID_PERIOD`.
- `GET /nominal-ledger/deferred-revenue` — **deferred revenue for loyalty points and gift cards (17.11; FRS 102 s.23 as revised for periods from 1 Jan 2026, IFRS 15 B39–B47):** the estimates in force (`settings`: `pointValue`, `pointsBreakagePct`, `giftCardBreakagePct`, `reason`, `setBy`, `setAt`, `currency`; absent until first set) and their `history`; `pointsOutstanding`, `deferredIncome` (2330), `pointsUnmatched` (points spent before their earning reached the ledger) and `eventsAwaitingEstimates`; `giftCardsLoaded`, `giftCardsRedeemed`, `giftCardBreakage` (4031) and `giftCardLiability` since the ledger began to follow gift cards. Management only.
- `PUT /nominal-ledger/deferred-revenue/settings` `{pointValue, pointsBreakagePct, giftCardBreakagePct, reason}` — **the tenant accountant's estimates.** Management only. A point's value above 0 and at most 1000 to four decimal places (`400 PURCHASE_POINT_VALUE_INVALID`), each breakage estimate 0 to 95 to two decimal places (`400 PURCHASE_BREAKAGE_OUT_OF_RANGE`), and a reason. Append-only; a change applies from then on. Loyalty events that arrived before any estimates are posted in the same transaction, oldest first. From customer-svc's `LoyaltyEarned/Redeemed/Adjusted` (by `eventId`), order-svc's `GiftCardLoaded` (by card transaction) and a `GIFT_CARD` tender (by payment), once each, the ledger posts: points earned with a sale `Dr 4010 / Cr 2330`, the points' share of the sale's net revenue by standalone selling price (points × value × (1 − breakage)); points given away `Dr 6410 / Cr 2330`; points spent `Dr 2330 / Cr 4020`, their share of what is deferred against the points expected to be spent, and the rest `Cr 4030` once no points remain; a gift card sold or reloaded `Dr` the tender's control account, or `6420` when given away, `/ Cr 2310`; a gift card spent `Dr 2310 / Cr 4031` breakage of amount × b / (1 − b), never more than b of what was loaded and reversed when spending overtakes the estimate.

**Business rules**
- Purchase orders run create (draft) → add lines → submit before goods can be received against them.
- **The status vocabulary is `DRAFT → SUBMITTED → PARTIALLY_RECEIVED → RECEIVED`**, with `CLOSED` (short-closed, balance abandoned) and `CANCELLED` (nothing ever received) as the two terminal exits. `CLOSED` is deliberately not `RECEIVED`: "we got it all" and "we gave up on the rest" are different facts, and a supplier scorecard that cannot tell them apart is worthless.
- **A partial delivery no longer closes the order.** A receipt is compared against what was ordered — under a `FOR UPDATE` lock on the order, so two deliveries arriving at once cannot both book the same balance — and the order lands in `PARTIALLY_RECEIVED` or `RECEIVED` accordingly. Previously the status was set to `RECEIVED` with no reference to quantity, so 6 of 10 closed the order *and the second delivery of the remaining 4 was then refused*, stranding the balance with no PO to receive it against.
- **Over-receipt is refused** (`422 PURCHASE_OVER_RECEIPT`), cumulatively across deliveries rather than per delivery. Accepting more than was ordered would book stock nobody asked for against an order that cannot account for it, and a mistyped 60 for 6 would do it silently. Whether a tolerance band should be allowed is a per-tenant procurement policy, not something to invent.
- Goods receipt posting accepts an `Idempotency-Key`; a replayed receipt does not count its quantity twice.
- **The nominal ledger is written by the documents** (goods receipt, supplier invoice, rejection, credit note, intercompany invoice and settlement) **and by manual journals; every posting balances.** The balance is checked where lines are made — a `LedgerPosting` that does not balance does not build — rather than trusted to each caller, and the lines of one posting share a `journalId` so it can be read back whole and reversed line for line. Nothing is ever updated or deleted: a rejection is a reversal, not an erasure.
- **Period control (04.7)** reads the store's accounting periods from inventory-svc. A period is the calendar month of its `periodDate`; a month with no period is not controlled (periods are optional, and a business that has never opened one must not find its goods receipts refused); a month whose period is `CLOSED` refuses every posting dated in it. Unreachable is treated as open and logged: a discovery outage that refused every goods receipt would be a far larger outage than a posting landing in a month finance has closed.
- Invoices captured before the ledger was wired in have `postedAt` null and were not back-posted: a posting dated today for an invoice dated months ago would land in the wrong period, and inventing one is finance's decision, made with a journal.

**Events**
- Consumes: `OrderConfirmed`, `PaymentCaptured`, `PaymentRefunded` (17.7: posted to the nominal ledger as sales, tenders and refunds, deduped per event and per sale or tender). Also `PaymentDisputeOpened`, `PaymentDisputeFundsWithdrawn`, `PaymentDisputeClosed` (11.9): the disputed amount out of card clearing (1250) into card receipts in dispute (1255) with the acquirer's fee to 6511, back on a win, to chargeback losses (6510) otherwise; source type `CHARGEBACK`, once per event. And `SettlementReconciled` (11.10): a journal per store the payout covers — Dr 1200 bank for what the acquirer paid and Dr 6500 card processing fees / Cr 1250 card clearing for the payments covered and Cr 1299 unallocated receipts for money that answered to nothing; a negative figure changes sides; source type `CARD_SETTLEMENT`, dated the day it was reconciled and naming the payout and when it was paid; once per event.
- Publishes: `PurchaseOrderCreated`, `GoodsReceived`, `IntercompanyInvoiceRaised`, `SupplierInvoiceCaptured` (SJ-D39: invoice id as event id, net/VAT/gross, invoice date as tax point — pricing-svc projects it into the VAT return's boxes 4 and 7), `SupplierInvoiceRejected` (07.7: the same figures on the same topic, projected as their negative so the rejected invoice leaves boxes 4 and 7), `ReturnedToVendor` (07.8: return id as event id, the store and the lines going back — inventory-svc deducts them as `RTV` movements, once per line), `SupplierRemittanceIssued` (17.10: one per supplier a payment run pays, on `shelfj.purchase.supplier-remittance-issued` keyed by the run — the run reference, payment date, supplier, remittance email, currency, total and each document settled; notification-svc emails it as the remittance advice).

## tenant-svc

### Onboarding (`/onboarding`)
- `POST /onboarding` — single-call signup: create a tenant and its first store atomically. `storeTimezone` is required (an IANA zone such as `Europe/London`) and is checked before the tenant is created, so a refused zone leaves no business without a store.
- `GET /admin/tenant/obligations?country=&on=` — **which laws bind this business**: the legal obligations that reach a country, directly or through a regime it belongs to (the EU), each with a stable `code` services check (such as `PRICE_REDUCTION_PRIOR_PRICE`), its `scope` (`EU` or the country), `citation`, `summary`, `effectiveFrom`, `effectiveTo` and `status` — `IN_FORCE` on the day asked about, then `UPCOMING`; anything that had ended is left out. A regime's obligation is narrowed to the country's membership, so a British business is not handed EU law made after 31 Jan 2020, and `?on=2019-06-01` shows the GDPR window ending that day. `country` defaults to the business's own (`409 TENANT_COUNTRY_MISSING` if it never declared one), `on` to today; `400 COUNTRY_INVALID` / `400 OBLIGATION_DATE_INVALID` otherwise. Reference data in tenant-svc's V9 — regimes, EU membership with its dates, and the obligations with their citations (V9; V12 the EU's unit pricing; V13 Germany's take-up of art.6a's options, `PRICE_REDUCTION_PROGRESSIVE` and `PRICE_REDUCTION_PERISHABLE_EXEMPT`) — read by any staff role (the till obeys them) and never written through the API: the law changes by migration. Services ask it through `common-service`'s `Jurisdictions` rather than keeping a list of countries. **Cash limits (09.17):** the sheet also carries `cashLimits` — every cash payment limit that reaches the country, its own and its regimes', as `{scope, currency, fromAmount, effectiveFrom, effectiveTo, citation, summary, status}`: the amount at and above which cash is refused, in the currency the law names (the Union's EUR 10,000 from 10 July 2027 under Regulation (EU) 2024/1624 art.80; France's EUR 1,000, Belgium's and Portugal's 3,000, Italy's 5,000, Spain's 1,000, Greece's 500; India's two lakh rupees under s.269ST), `IN_FORCE` or `UPCOMING` on the day asked about. Reference data (`cash_limits`), never a literal in code. A country whose currency is not the law's (a Polish business under the EU cap) meets no limit until the register carries a row in its currency: the equivalent is a matter of rate, not of law.
- `GET /admin/tenant/statutory-returns?asOf=` — **what this business owes each authority, and when (07.14)**. The obligations sheet above says what the law *asks*; this says what this business *owes and when*, period by period, and holds the evidence that it went. Returns `{asOf, obligations, outstanding}`: each obligation is one period of one return — `returnCode`, `name`, `scopeKind`/`scope`, `frequency`, `periodStart`, `periodEnd` (exclusive), `dueOn`, `state`, `citation`, `exportService`/`exportPath` and the `filing` that stands. `state` is `NOT_DUE` (the period is still running), `DUE` (ended, unfiled, on or before its date), `OVERDUE` (past its date) or `FILED`; **`outstanding`** is the same list filtered to `DUE`/`OVERDUE`, oldest first. **Nothing is stored** — the date and the state are derived from the return's frequency and its statutory offset on every read, because a deadline in a column goes stale the first time a rule changes. The calendar reaches 24 periods back. Which returns reach a business is asked of `jurisdiction_members` **of the period**, not of today: a Portuguese business owes the EU's recapitulative statement, a British one owes it for no period after 31 January 2020, and a leaving member still owes the quarters it was a member for. Reference data in tenant-svc's V25 (`statutory_returns`) with the instrument named: Portugal's monthly SAF-T (PT) by the 5th of the following month (`P4D`), the UK VAT return under MTD by the 7th of the second month after the quarter (`P1M6D`, which is what HMRC publishes — a fixed day count cannot produce the 7th for all four quarters), the EU statement by the 20th (`P19D`), and Germany's DSFinV-K as a **monthly checkpoint and not a filing**, because KassenSichV sets no periodic date and an inspector can arrive any morning. `exportService`/`exportPath` are a **link, never a proxy**: the SAF-T and DSFinV-K are order-svc's (`/admin/fiscal-receipts/export?format=…`) and the VAT return is pricing-svc's (`/admin/vat-return`), and serving their bytes from tenant-svc would be one service reading another's data. A return the platform cannot produce carries neither, which the console shows as a gap to close with an accountant rather than an empty export. Management-only (`OWNER`/`MANAGER`): a statutory filing is a statement to a tax authority, and the person who makes it is the person answerable for it. `400 STATUTORY_DATE_INVALID` for an `asOf` that is not a date.
- `GET /admin/tenant/statutory-returns/filings` — everything this business has filed, newest period first, **superseded rows included**: a correction replaces a filing and both stay on the record, for the same reason an invoice is never edited. Each carries `stands` (false once a correction replaced it) and `supersedes`.
- `POST /admin/tenant/statutory-returns/{code}/filings` `{periodStart, provider, reference?, payloadDigest?, supersedes?, note?}` — **records that a return went.** The platform does not file on a business's behalf: nothing here is authorised to speak to a tax authority unprompted, so this records what a person did — the authority's `reference` where it gives one, and `payloadDigest` (SHA-256, base64) so the filing can be proved against an export produced later. `provider` is `HMRC_MTD`, `MANUAL` or `SIMULATED` (`SIMULATED` says on the record that nothing left the building). The period is **named, not inferred**, so filing for the wrong month is a mistake somebody makes on purpose. Refusals: `404 STATUTORY_RETURN_UNKNOWN` (no such return in force for a period beginning then), `400 STATUTORY_PROVIDER_UNKNOWN`, `400 STATUTORY_PERIOD_NOT_A_PERIOD` (a date that does not begin one of that return's own periods — a filing against an invented period would sit on the calendar for ever looking unfiled), `409 STATUTORY_PERIOD_NOT_ENDED` (the figures do not exist yet, so a filing recorded against them would be evidence of something that had not happened), `409 STATUTORY_FILING_EXISTS` (already filed; a correction must name what it replaces) and `409 STATUTORY_FILING_NOT_STANDING` (`supersedes` is not the filing that currently stands — which is also what stops one business naming another's filing id, because the lookup is under the caller's own tenant). A correction marks its predecessor and inserts itself in one transaction; `uq_statutory_filing_period` (partial, `WHERE superseded_by IS NULL`) is what makes "exactly one filing stands per period" a database fact. Returns the period, re-derived, with its new `state` and the filing that now stands.
- **Deposit return schemes (09.16):** the same sheet carries `depositSchemes[]` — for each scheme that reaches the country: `scope`, `currency`, `depositEach`, `materials`, `minVolumeMl`/`maxVolumeMl`, `vatTreatment` (`OUTSIDE_SCOPE` or `STANDARD`), `effectiveFrom`/`effectiveTo`, `citation`, `summary`, `status`. Seeded: Germany's Pfand (EUR 0.25, PET, aluminium, steel and glass 100 ml–3 l, since 2003, taxed as the drink, VerpackG §31) and the UK scheme (GBP 0.20, PET, aluminium and steel 150 ml–3 l, from 1 October 2027, outside the scope of VAT, SI 2025/67 and VATA 1994 ss.55B–55D). `Jurisdictions.depositScheme(tenant, store, currency, day)` in common-service is how order-svc asks for the scheme in force where a store trades.

**Data retention (21.16)** — UK GDPR art.5(1)(e) storage limitation and art.30's record of the periods applied, with the statutory floors that stop a period being set too short.
- `GET /admin/tenant/retention` — the schedule: `country`, `countries` (the business's own and every store's), and every class of data — `TRANSACTIONS` (orders, receipts, returns, payments: `KEEP`, never purged by the platform), `ORDER_PERSONAL_DATA` (the delivery name, address, phone and notes on a settled order: `ANONYMISE`, by order-svc), `CUSTOMER_RECORDS` (a record nothing has happened on: `ANONYMISE`, by customer-svc, through the ordinary erasure), `NOTIFICATION_LOG` (messages sent: `DELETE`, by notification-svc) — each with `floorDays`, `floorScope`, `floorCitation` and `floorSummary`, the highest floor among the countries traded in (V14: GB six years, VATA 1994 Sch.11 para.6(3); DE eight, AO §147(3); FR ten, C.com L123-22; IN eight, Companies Act 2013 s.128(5)), and the `periodDays` the business set, absent until it decides; plus the `holds` in force. Readable by every staff role, because the purgers read it under a staff identity.
- `PUT /admin/tenant/retention/{dataClass}` — `{ periodDays }` (0–36500; 0 means as soon as settled). A longer period than the floor is allowed; a shorter one is `400 RETENTION_BELOW_LEGAL_MINIMUM` with the floor and its instrument in `error.details`. `400 RETENTION_CLASS_UNKNOWN` / `RETENTION_PERIOD_INVALID`. Every decision is kept (`retention_schedules`, append-only); the latest is in force. Management only.
- `GET /admin/tenant/retention/holds?active=` and `POST /admin/tenant/retention/holds` — `{ dataClass?, subjectKind: ALL|CUSTOMER|ORDER, subjectId?, reason }`: a matter that stops a purge of one customer, one order or everything, on one class or every class (`400 RETENTION_HOLD_SUBJECT` when the subject and kind disagree). `POST /admin/tenant/retention/holds/{id}/release` — `{ reason }`, once (`409 RETENTION_HOLD_RELEASED`, `404 RETENTION_HOLD_NOT_FOUND`). Management only.
- `GET /admin/tenant/retention/runs?after=&limit=` — the register: every purge a service ran for this business, newest first, with `service`, `dataClass`, `cutoff`, `rowsAffected` and `heldSkipped`. Recorded from `RetentionRunCompleted` events (tenant-svc's first consumer; topics `shelfj.{order,customer,notification}.retention-run-completed`), once per event id. Management only.
- The purgers share `common-service`'s `Retention` (the schedule cached ten minutes; a purge whose schedule cannot be read does not run, `503 RETENTION_UNAVAILABLE`) and `RetentionSweeperBase` (daily, `shelfj.retention-sweeper.enabled` / `interval-seconds`, first run one interval after start). Each also exposes `POST …/retention/sweep` to run now for the caller's business (management only; `409 RETENTION_PERIOD_NOT_SET` when no period is set), returning `{ dataClass, cutoff, rowsAffected, heldSkipped, startedAt, finishedAt }`: `POST /admin/orders/retention/sweep` (order-svc — settled orders older than the cutoff by `updated_at`; also the address a receipt was emailed to and the number a recall notice held), `POST /admin/customers/retention/sweep` (customer-svc — no profile change, loyalty movement or consent change since the cutoff; each record erased as the customer could have asked, `CustomerErased` and all), `POST /admin/notifications/retention/sweep` (notification-svc — log rows older than the cutoff; the service gained an outbox, V5, for the announcement). The rows, the held count and the announcement commit in one transaction; concurrent sweeps lock the same rows and never count one twice.
- `GET /admin/tenant/security-notices` · `POST /admin/tenant/security-notices/{id}/acknowledge` — **security notices** the platform has sent this business about an incident that affects it (21.15), newest first, with `acknowledged` and `acknowledgedAt`. Management only (the default tier for `/admin`): the owner or a manager answers for the business as controller. Acknowledging again returns the first acknowledgement; another business's notice is `404 SECURITY_NOTICE_NOT_FOUND`. **The business's own duties on a breach (13.12):** a notice of a `PERSONAL_DATA_BREACH` carries `regime` — `DPDP` where the register puts the business's country under India's Act, `binding` or not yet with `bindsFrom`; `GDPR` elsewhere — and `duties`, reference data with their citations (`breach_duties`): under the DPDP Rules r.7, `PRINCIPALS_TOLD` and `BOARD_INTIMATED` without delay and `BOARD_REPORTED` within 72 hours of the notice; under GDPR arts.33–34, `AUTHORITY_NOTIFIED` within 72 hours and `SUBJECTS_TOLD` without undue delay; each `DUE`, `OVERDUE`, `WAITING` (no fixed time) or `DONE`. `POST /admin/tenant/security-notices/{id}/reports` `{duty, doneAt, reference, note}` → `201` records a duty done, once (`409 SECURITY_NOTICE_DUTY_DONE`; `400 SECURITY_NOTICE_DUTY_UNKNOWN` for a duty the regime does not put on the business, `SECURITY_NOTICE_NO_DUTIES` for a notice of anything but a breach; owners and managers). Telling the customers is done through customer-svc's breach intimation, whose id is the reference.

### Plans and packaging (`/platform/plans`, `PLATFORM_ADMIN` only; 21.8)
The platform's price list. A plan is written as a draft, priced, given its allowances, and only then sold; one plan on sale is the one a business signing up starts on. A plan is never deleted — retiring it takes it off sale and leaves its subscribers where they are.
- `GET /platform/plans` — every plan, drafts and retired ones included, with its prices and what it includes.
- `POST /platform/plans` `{code, name, description?, billingInterval, trialDays?, isPublic?, sortOrder?}` → `201`, always `DRAFT`. `400 PLAN_CODE_INVALID` (2–40 of A–Z, 0–9, `-`, `_`), `PLAN_INTERVAL_UNKNOWN` (`MONTH` or `YEAR`); `409 PLAN_CODE_TAKEN` (case-insensitive).
- `GET /platform/plans/{id}`, `PUT /platform/plans/{id}` — read and change name, description, interval, trial, visibility and order. `409 PLAN_INTERVAL_IN_USE`: how often a plan bills cannot change while businesses are on it.
- `POST /platform/plans/{id}/prices` `{currency, amount, effectiveFrom?}` — the price in one currency from a date (today when absent). An earlier price is kept, never edited. `400 CURRENCY_INVALID`, `PLAN_PRICE_DATE_INVALID`.
- `PUT /platform/plans/{id}/includes` `{grants:[{key, limitValue?, enabled?}]}` — replaced whole: a key left out is one the plan no longer names. A limit carries `limitValue` (absent means unlimited), a feature carries `enabled`. `400 PLAN_ENTITLEMENT_UNKNOWN` for a key the platform does not enforce, `PLAN_ENTITLEMENT_SHAPE` for a limit written as a yes or no, or the reverse.
- `POST /platform/plans/{id}/activate` — put it on sale. `409 PLAN_HAS_NO_PRICE`, `PLAN_ALREADY_SOLD`.
- `POST /platform/plans/{id}/retire` — take it off sale; its subscribers keep it. `409 PLAN_NOT_SOLD`.

### What a business is allowed (`/admin/tenant/plan`; 21.8)
- `GET /admin/tenant/plan` (OWNER, MANAGER) — the plan it is on, with each limit against what it is using. `used` is absent where the owning service holds the count, and is shown as unknown rather than guessed at. A business on no plan carries no `plan` and a `note` saying so; it is unrestricted.
- `GET /admin/tenant/plan/available` (OWNER, MANAGER) — the plans on sale. Moving between them is the platform's to do.
- `GET /admin/tenant/plan/limits` (any staff role) — the allowances alone, no prices: what another service reads through `Entitlements` to enforce a limit it owns. Any staff role, because that is the identity a service-to-service read carries; the leaf is carved out of the management tier in `AdminAuthorizationFilter`, and without that line the read answers 403 and every limit outside tenant-svc silently enforces nothing (SJ-D65).
- Limits are refused with `409 PLAN_LIMIT_REACHED`, naming the ceiling and the count: stores and staff by tenant-svc, products by product-svc. A limit fails **open** — a business on no plan, or one whose allowances cannot be read this moment, is unrestricted — because a blip should not stop a shop taking on staff; that is the opposite of spend authority (11.x), which fails closed because it guards money leaving.

### Subscription billing and invoicing (21.9)

Billed **in advance, on the subscription's own anniversary** — not a calendar batch, which would make
every first period a stub and every proration a special case. The price is **locked when the business
is sold the plan**: a change to the price list reaches new subscribers only.

- `GET /platform/billing/profile` · `PUT /platform/billing/profile` (PLATFORM_ADMIN) — who the platform invoices as. **Nothing is billed until this is set:** an invoice with no seller is not an invoice anywhere the platform trades (`409 BILLING_PROFILE_NOT_SET`).
- `GET /platform/billing/vat-rates` · `PUT /platform/billing/vat-rates` (PLATFORM_ADMIN) — the rates it charges where it has no choice. A country with no rate **refuses the invoice** (`409 BILLING_RATE_NOT_SET`) rather than guessing: a guessed rate is VAT charged wrongly in somebody else's country.
- `POST /platform/billing/tenants/{tenantId}/vat-check` (PLATFORM_ADMIN) — records that a buyer's VAT number has been checked, and by what (`VIES` | `MANUAL` | `SIMULATED`). The reverse charge rests on the number being real, so **who checked it and when** is kept; an audit asks for the date.
- `POST /platform/billing/run?asOf=` (PLATFORM_ADMIN) — bills everything whose period has run out, catching up on every missed period in one call (bounded at 24). A business the platform **cannot** bill (no rate for its country, no price in its currency) is **passed over and named in `skipped`**, not allowed to stop everybody else's invoices — while that same business's own upgrade refuses loudly with the same code, because there somebody is waiting on the answer. An unbilled business is money not asked for, so it is named rather than silently dropped. Safe to run twice: a period is invoiced once by a unique index on (subscription, period start), not by a check somebody remembered. `asOf` is a **test facility** gated on `shelfj.billing.test-clock.enabled` — on in compose, off in k8s, `403 BILLING_TEST_CLOCK_DISABLED` otherwise.
- `GET /platform/billing/receivables` (PLATFORM_ADMIN) — what is still owed, most overdue first.
- `GET /platform/billing/invoices/{id}` · `POST .../payments` · `POST .../void` (PLATFORM_ADMIN) — one invoice with its lines, payments and both snapshots; money recorded against it (append-only, settling it when what has been paid reaches the total); and withdrawal. **An invoice is never edited.** A withdrawn one keeps its number — a gap is what an auditor asks about — and one that has taken money is corrected with a credit note, not voided (`409 INVOICE_NOT_VOIDABLE`).
- `GET /admin/tenant/billing` (OWNER, MANAGER) — the subscription this business is on and everything that has happened to it.
- `PUT /admin/tenant/billing/details` (OWNER, MANAGER) — where it is established, which is **not** the same question as where its shops are: it decides the VAT treatment. **Changing the VAT number discards the check against the old one**, or the reverse charge could be obtained by being checked on one number and quietly substituting another.
- `GET /admin/tenant/billing/invoices` · `GET .../invoices/{id}` (OWNER, MANAGER) — its own, and another business's answers `404` rather than `403`, because a 403 confirms to a guesser that the id is real.
- `POST /admin/tenant/billing/plan` (OWNER, MANAGER) — `when: NOW` bills the days left on the new price against what was billed for them on the old one, as **two lines** (a credit and a charge) because a net figure cannot be checked by the person paying it; `when: PERIOD_END` waits for the period already paid for. A subscription in `PAST_DUE` **prorates nothing** — the change takes effect, the credit does not, or a business that has not paid would be credited for time it never paid for.
- `POST /admin/tenant/billing/cancel` · `/resume` · `/plan/cancel-pending` (OWNER, MANAGER) — ends at the period end, never now: it has paid to the end of the period.

Four tax treatments, and the one that is easy to get wrong is the third: `DOMESTIC` (the platform's own country, its own rate) · `REVERSE_CHARGE` (another EU state with a **checked** number: no VAT, and the invoice carries both numbers and the words required by Directive 2006/112/EC art. 226(11a)) · `DESTINATION` (another EU state with **no checked** number: that country's rate — treating this as a reverse charge issues an invoice with no VAT that should have carried some, and the platform owes the difference) · `OUT_OF_SCOPE` (outside the EU). Membership is asked of the **invoice's date**, not of a list, from `jurisdiction_members` — the United Kingdom was a member until 31 January 2020.

### Dunning and suspend-for-non-payment (21.12)

Chase, then interrupt the service, then give up on the debt — **in that order**, and the order is part of the policy: suspending before the last reminder takes the platform away from a business that has not finished being told it is late.

- `GET /platform/billing/dunning/policy` · `PUT …/policy` (PLATFORM_ADMIN) — a platform that has set no policy still chases, on the published defaults (reminders on days **1, 3, 5, 7** after the due date, suspend at **14**, uncollectible at **30**), and says `set: false` rather than inventing somebody who chose them. Stages out of order are refused with `400 DUNNING_POLICY_INVALID`.
- `POST /platform/billing/dunning/run?asOf=` (PLATFORM_ADMIN) — **every notice a business missed is sent, once.** A run that has not run for a week owes each reminder it did not get; skipping to the latest step would suspend a business the platform never finished telling. Safe to run twice by `UNIQUE (invoice_id, step)`. A business it cannot act on is named in `skipped`, not allowed to stop the rest. Same test-clock gate as the billing run.
- `GET /platform/billing/dunning/overdue` (PLATFORM_ADMIN) — what is owed, most overdue first, with the stage reached and **what it earns next**, so an operator sees a suspension coming rather than hearing about it from the customer.
- `GET /platform/billing/dunning/invoices/{id}/events` (PLATFORM_ADMIN) — what has been done about one invoice, append-only.
- `GET /platform/billing/dunning/invoices/{id}/pay-link` (PLATFORM_ADMIN) — mints the link a notice carries. Returned once, because only its hash is kept; asking again replaces it.
- `PUT /platform/billing/invoices/{id}/due-date` (PLATFORM_ADMIN) — a promise to pay. **Outwards only, and only on an open invoice** — a date that could move inwards would shorten the time a business has to pay after the fact. Recorded, so an extension is on the file rather than a due date that quietly moved.
- `POST /billing/pay/{token}` — **unauthenticated, deliberately.** A suspended business cannot sign in, so a pay link that demands a session is a dead end; the same reasoning as the PECR opt-out link. The token is the whole capability: 256 bits, stored only as a hash, naming one invoice, able to do one thing to it. A token for an invoice no longer open answers `404 PAY_LINK_INVALID` — the same answer as a token nobody issued, because telling them apart tells a guesser which half they got right. Reachable only because **both** the gateway's public-path list and `AdminAuthorizationFilter` carve it out by shape; each comment points at the other.

**Paying up lifts only what the platform imposed.** `tenants.deactivated_reason` is `NON_PAYMENT` or `ADMINISTRATOR`, and reactivation-on-payment moves only the first. Before V24 the column did not exist and the two were indistinguishable, so a payment would have quietly overruled a decision somebody took. A CHECK pairs the reason to the status, so a stale reason cannot make the next payment lift a suspension nobody asked it to lift.

### Tenant data export and leaving (21.14)

A business may leave on notice and take its data with it, or have it erased (EU Data Act (EU) 2023/2854 art.25). Its data is exported through every service's `/admin/tenant-data` (see *Platform-wide conventions*); tenant-svc keeps the notice, starts the erasure and records what each service erased. The owner alone acts (anyone else `403`).

- `GET /admin/tenant/switching` — the latest notice with its dates (`noticeEndsOn`, `transitionEndsOn`, `retrievalEndsOn`, `erasureDueOn`, `extendedAt`, `cancelledAt`, `cancelReason`, `erasureStartedAt`), its `stage` (`NOTICE`, `TRANSITION`, `RETRIEVAL`, `ERASURE_DUE`, `ERASING`, `ERASED`, `CANCELLED`), and once erasure has started the `evidence` from each service (`service`, `rowsErased`, `tables`) and the services still `awaiting`. `404 SWITCHING_NO_NOTICE`.
- `POST /admin/tenant/switching` `{intent, noticeEndsOn}` → `201`. `intent` is `SWITCH`, to take the data elsewhere: notice of at most two months (art.25(2)(a)), then a transitional period of 30 calendar days while the service carries on, then at least 30 days to retrieve the data (art.25(2)(g)), and erasure the day after (art.25(2)(h)). `ERASE`, to have it erased: erasure when notice ends, which may be today (art.25(3)). One notice stands at a time. `400 SWITCHING_INTENT_UNKNOWN`, `SWITCHING_NOTICE_INVALID` (before today, not a date), `SWITCHING_NOTICE_TOO_LONG`; `409 SWITCHING_NOTICE_ALREADY_GIVEN`.
- `POST /admin/tenant/switching/extend` `{transitionEndsOn}` — extends a switch's transitional period once (art.25(4)), while it runs, to at most seven months after notice ends; the retrieval period and erasure move with it. `400 SWITCHING_EXTENSION_INVALID`, `SWITCHING_EXTENSION_TOO_LONG`; `409 SWITCHING_ALREADY_EXTENDED`, `SWITCHING_NOT_EXTENDABLE` (an erasure), `SWITCHING_TRANSITION_OVER`, `SWITCHING_CLOSED`.
- `POST /admin/tenant/switching/cancel` `{reason}` — withdraws the notice while it runs. `409 SWITCHING_TOO_LATE_TO_CANCEL` once notice has ended, `SWITCHING_CLOSED`.
- `GET /platform/tenants/switching/{tenantId}`, `POST /platform/tenants/switching/sweep` (`PLATFORM_ADMIN`) — a business's notice, and the sweep that starts every erasure due: the business is made `INACTIVE` (`TenantStatusChanged`) and `TenantDataErasureDue` published, in one transaction per business, once however many sweeps run. The sweep also runs hourly (`shelfj.switching.sweeper.interval-seconds`). `{started}` is how many it started.
- Each service's `TenantDataErased` is recorded once as evidence; the business's record, its notice and the evidence are kept at erasure as the platform's record that it left. Neither a notice nor the evidence is ever imported into another business.

### Security incidents (`/platform/security-incidents`, `PLATFORM_ADMIN` only)

The platform's register of what the Cyber Resilience Act (Regulation (EU) 2024/2847 art.14, reporting applies from 11 Sep 2026) and GDPR art.33(2) require of it as the manufacturer of the software and the processor of its businesses' customer data. The statutory stages and their clocks are reference data with citations (V11 `incident_reporting_stages`), not constants: an `EXPLOITED_VULNERABILITY` or `SEVERE_INCIDENT` owes an early warning within 24 hours of awareness and a notification within 72; a vulnerability's final report is due 14 days after a corrective or mitigating measure is available, a severe incident's one calendar month after its notification; a `PERSONAL_DATA_BREACH` owes each business affected notice without undue delay, since each is the controller with its own 72 hours. Every read computes each stage's `dueAt` and `state` — `DONE`, `DUE`, `OVERDUE`, `WAITING` (its anchor has not happened) or `NO_DEADLINE` — from the timeline as it stands. The register does not file with ENISA or a supervisory authority: the reports are made on their own platforms, and recorded here with their references.

- `POST /platform/security-incidents` `{kind, title, summary, awareAt, tenantIds?}` → `201` with its stages. `tenantIds` names the businesses affected (at most 500); none means every business. `400 INCIDENT_KIND_UNKNOWN`, `INCIDENT_TITLE_INVALID` (1–200), `INCIDENT_SUMMARY_INVALID` (1–4000), `INCIDENT_AWARE_IN_FUTURE`, `INCIDENT_TOO_MANY_TENANTS`, `INCIDENT_TENANT_UNKNOWN`, `INVALID_DATE`, `INVALID_UUID`.
- `GET /platform/security-incidents?status=OPEN|CLOSED&limit=` — newest first, each with `nextStage`, `nextDueAt` and `overdue`; `400 INCIDENT_STATUS_UNKNOWN`.
- `GET /platform/security-incidents/{id}` — the incident with its `stages`, append-only `events`, `noticesIssued` and `noticesAcknowledged`; `404 INCIDENT_NOT_FOUND`.
- `POST /platform/security-incidents/{id}/events` `{kind, occurredAt?, reference?, note?}` → `201` — record `EARLY_WARNING_SENT`, `NOTIFICATION_SENT`, `MITIGATION_AVAILABLE`, `FINAL_REPORT_SENT`, `NOTE` or `CLOSED`, with the authority's reference (≤120) and a note (≤2000). Decided under the incident's row lock and backed by a unique index, so twenty people recording one report at once record it once. `400 INCIDENT_EVENT_UNKNOWN`, `INCIDENT_EVENT_NOT_APPLICABLE` (not a stage of this kind; `TENANTS_NOTIFIED` is written only by issuing notices), `INCIDENT_EVENT_BEFORE_AWARE`, `INCIDENT_EVENT_IN_FUTURE` (five minutes' clock skew allowed), `INCIDENT_REFERENCE_INVALID`, `INCIDENT_NOTE_INVALID`, `INCIDENT_NOTE_REQUIRED`; `409 INCIDENT_STAGE_ALREADY_RECORDED`, `INCIDENT_FINAL_REPORT_TOO_EARLY` (before the notification, and for a vulnerability before a measure), `INCIDENT_STAGES_OUTSTANDING` (closing with a stage not done), `INCIDENT_CLOSED`. Nothing edits or deletes an incident or its timeline.
- `POST /platform/security-incidents/{id}/notices` `{message}` → `{issued, total, acknowledged}` — issues a notice to each business affected that has none, once per business, and records `TENANTS_NOTIFIED` the first time; `400 NOTICE_MESSAGE_INVALID`, `409 INCIDENT_CLOSED`.

### Public Storefront Config (`/storefront`)
- `GET /storefront/config?store=` — per-store storefront display config (e.g. whether to show prices). Carries `depositScheme` — the deposit return scheme in force where the store trades today, or absent (09.16) — so a shop and a till can say what the deposit is before the sale.
- `GET /storefront/active` — whether the tenant may currently transact (the gateway's storefront suspension gate).
- `GET /storefront/stores` — active stores for the tenant (storefront's store switcher).

**Business rules**
- Onboarding is designed as a single atomic call (tenant + first store) so a new signup needs no JWT refresh mid-flow.
- Platform-wide tenant visibility/suspension is restricted to `PLATFORM_ADMIN`.
- tenant-svc is the system of record for tenant/store/zone/staff state — it's a pure event publisher, never a consumer.

**Events**
- Consumes: none.
### Weighing instruments (`/admin/stores/{storeId}/weighing-instruments`)

The register of every instrument a store weighs for trade on (Weights and Measures Act 1985 s.11: using an instrument not passed as fit for use for trade, or one whose stamp a repair has broken, is an offence), and an append-only history of every verification, inspection and repair. Standing is derived on every read, never stored: **certified** means in service, latest history entry a pass, and not yet due again; otherwise `NEVER_VERIFIED`, `FAILED`, `REPAIRED_SINCE`, `OVERDUE`, `OUT_OF_SERVICE` or `RETIRED`. Reads need any staff role at the store (the till asks `?certified=true` before it sells by weight); writes are management-only.

- `GET /admin/stores/{storeId}/weighing-instruments?certified=` · `POST …` · `GET/PUT …/{id}` · `PATCH …/{id}/status` (`IN_SERVICE`, `OUT_OF_SERVICE`, `RETIRED`; retirement is final — a replaced or repaired-beyond-recognition scale is a new instrument). An instrument has an identifier unique in the store and a serial number unique in the tenant, a kind (`COUNTER`, `LABELLING`, `PLATFORM`, `HANGING`), capacity and scale interval as marked, the type-approval reference, and for a labelling scale the `labelScheme` JSON the till reads its barcodes with (`{prefixes, itemDigits, valueKind: PRICE|WEIGHT, valueDecimals, priceCheckDigit?}`), validated here once rather than trusted on every scan.
- `GET/POST …/{id}/verifications` — the history: `INITIAL`, `RE_VERIFICATION`, `INSPECTION` or `REPAIR`, with who did it, the certificate reference, whether it passed and when it is due again. A `REPAIR` is never a pass; a due date before the work, a date in the future, or an entry on a retired instrument is refused.

- Publishes: `TenantCreated`, `StoreCreated`, `ZoneCreated`, `StaffAssigned`, `TenantStatusChanged`, `StoreStatusChanged`, `UserRoleGranted`.
